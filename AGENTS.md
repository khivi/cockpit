# Privacy & Internal References

This is a public repository. Never include the following in commits, PRs, code comments, or documentation:

- Internal ticket IDs (Linear `ENG-123`, Jira `PROJ-456`, etc.)
- Internal GitHub PR/issue URLs from private repos
- Real names of teammates (use roles instead: "the reviewer", "the on-call engineer")
- Internal Slack channels, wiki URLs, or tool links
- Internal hostnames, service names, or infra identifiers
- Customer names or company-specific identifiers

When writing commit messages or PR descriptions:

- Describe *what* changed and *why*, not which ticket tracks it
- Reference public GitHub issues only (`#123` in this repo)
- If context requires an internal ticket, summarize the requirement instead of linking

Before committing, scan for cases gitleaks can't catch:

- Your team's real ticket prefixes (e.g. `ENG-123`, `LIN-456`)
- `@firstname` references that aren't GitHub handles

## Worktree discipline

Always use a dedicated git worktree for any code change. Never commit directly to `main`/`master` in the primary checkout, and never make in-place edits on a feature branch without a dedicated sibling worktree.

**Why**: The cmux + cockpit workflow keys off the one-worktree-per-branch invariant. In-place edits on the primary checkout pollute its `main` (which must always equal `origin/main`) and break PR-tracking — cockpit derives per-branch state from `git worktree list` and misattributes or drops cells for any branch not isolated in its own worktree.

**How to apply**: Before any Edit or Write, run `git branch --show-current` and `git worktree list`. If HEAD is `main`/`master`, or if the working-tree path is the primary checkout (first entry in `git worktree list`), stop and spawn a worktree via `cockpit new` before touching any file. If HEAD is already a non-main branch in a sibling worktree (not the first entry), proceed — do **not** spawn another worktree.

## Architecture notes

**How to read this (you're an agent editing this repo).** Each `###` is one invariant: the rule, its enforcing `file::symbol`, and the bug it prevents — obey the **Never** / **Do not** lines, they encode paid-for regressions. This is the *invariant* half of the design; `docs/state-machine.md`'s four Mermaid diagrams are the *control-flow* half. Keep both in sync.

### Keep `docs/state-machine.md` in sync — a stale diagram is worse than none

Four diagrams (orientation map, reconcile decision tree, nudge idle-gate, cell data-flow) map the three state sources (GitHub PR, Claude session, cmux workspace; + auxiliary Linear) onto the decision functions. Any change to those functions (`match_worktrees`, `_spawn_missing_workspaces`, `nudge_if_idle`, `_track_dev_done`, `_maybe_autoclose`), the `cache.py` cell writers, tick cadence, or the spawn/teardown/nudge/devdone/color rules MUST update the matching diagram in the same PR.

### Inventory is derived every cycle, never stored

Each cycle re-reads `git worktree list` and `cmux tree`. Only PR payloads are cached (`~/.config/cockpit/cache/<repo>__pr-<N>.json`, a network round-trip). **Never** add a stored identity file — cached-vs-real drift is the bug class this avoids.

### Packaged as the `cockpit` console script — invoke by subcommand, never by file path

- **Dispatch:** `[project.scripts] cockpit = cockpit.cli:main` → `cli.py` routes `watch / setup / teardown / statusline / starship / idle-pill / new / close / nudge` to each module's `main`, plus a top-level `--version`. `watch`/`setup` → `cockpit.cockpit` as `--watch`/`--setup`; `setup` re-wires the statusLine + Claude hooks without starting the daemon. **Add entry points as `cockpit <sub>` in `cli.py`**, not file-path invocations.
- **`teardown`** → `config.teardown_claude_integration`, the inverse of `setup`'s `~/.claude` writes. Run it *before* `brew uninstall` — brew removes only the Cellar binary, leaving the settings.json hooks/statusLine dangling at a now-missing `cockpit`.
- **Distribution:** a **brew formula** whose single source of truth is the tap repo `khivi/homebrew-cockpit` (`Formula/cockpit.rb`; `brew tap khivi/cockpit && brew install cockpit`, macOS + Linuxbrew) — **not** vendored back here (a copy would drift). The release CI (`.github/workflows/release.yml`) bumps the tap's `url`+`sha256` on every `v*` tag. There is **no** Claude Code plugin, marketplace, or self-update path (brew owns updates).
- **Version:** static in `pyproject.toml`, read at runtime via `importlib.metadata` (`version.running_version`). Must be installed on PATH; `preflight._warn_cockpit_not_on_path` soft-warns, never hard-fails.
- **Claude footprint** — three idempotent writes, all made by `cockpit setup`: two `~/.claude/settings.json` entries (the statusLine command + the idle-pill/statusline-stash hooks, via `config.install_cship_statusline_if_configured` + `config.install_claude_hooks`) and two files under `~/.claude/commands/` (`config.install_claude_commands`). The hooks invoke `cockpit statusline` / `cockpit idle-pill <phase>` off PATH.
- **`{python}` pin:** generated starship configs use `{python} -m cockpit.cli <sub>` (resolves off-PATH in starship's render env); `{python}` is `sys.executable` pinned at `cockpit setup` time. **Never run setup from inside a worktree venv** (`uv run cockpit setup`) — it bakes the worktree's ephemeral `.venv/bin/python`, which dies on cleanup (the "footer disappeared" bug); re-run `cockpit setup` through the brew-installed console script to re-pin.
- **Pin self-heals on upgrade:** a `brew upgrade` also staleness-breaks the pin (the Cellar libexec path is *versioned*, so the old interpreter vanishes), so `cockpit watch` re-pins on startup via `config.repin_interpreter_if_stale` — a **surgical** rewrite of only the interpreter prefix of `<interp> -m cockpit.cli …` in `~/.config/starship.toml` + the cockpit statusLine, preserving user colour/format edits (unlike `install_starship_default_config`, which re-seeds the whole file). Startup-only: a *running* daemon's `sys.executable` is still the removed path until restart, so a per-tick re-pin couldn't see the new interpreter. So running the daemon after an upgrade needs no manual `cockpit setup`.
- **idle-pill hook:** lives at `cockpit/hooks/cmux-idle-pill.sh` (inside the package, so it ships in the wheel), reached via the `idle-pill` subcommand, which `bash`-execs it (no reliance on the wheel preserving the exec bit).

**Slash commands are user commands, not a plugin.** `cockpit/claude_commands/{cockpit-new,cockpit-close}.md` (a package data dir with an `__init__.py`, same shape as `cockpit/prompts/`) are thin wrappers that just run `cockpit new $ARGUMENTS` / `cockpit close $ARGUMENTS`; `/cockpit:review` is not resurrected — it's the built-in `/review` now. `install_claude_commands` (`cockpit/lib/config.py`, called from `cockpit setup` right after `install_claude_hooks`) reads them via `importlib.resources` (same mechanism as `cockpit.lib.templates`, so it works from the installed wheel) and copies them verbatim into `~/.claude/commands/`, backing up an existing file only when its content changes and leaving unrelated user commands untouched. **They install as flat, hyphenated files (`cockpit-new.md` / `cockpit-close.md` → `/cockpit-new` / `/cockpit-close`), not a `cockpit/` subdirectory** — Claude Code's `.claude/commands/` convention names a command from its filename only (`deploy.md` → `/deploy`); the `plugin-name:command` colon-namespacing (`/cockpit:new`) is a plugin-only mechanism keyed off the plugin name, and cockpit isn't a plugin. `uninstall_claude_commands` is the inverse (removes only the bundled files, called from `teardown_claude_integration` alongside `uninstall_claude_hooks`). `tests/e2e/test_wheel_packaging.py` asserts the two `.md` files ride in the built wheel, same as the idle-pill hook script.

### `cockpit watch` is a Textual TUI, and the TUI *is* the daemon (`cockpit/tui/`)

- **No headless mode:** non-TTY `watch` exits 2. The app owns the pidfile (`daemon.claim_pidfile`/`release_pidfile`), claimed once before the TUI starts. **Pidfile self-heal:** `claim_pidfile` runs exactly once at startup; if the pidfile is later lost mid-run (a racing stale-cleanup in `kick_running`/`claim_pidfile`, or an external `rm`), nothing would otherwise rewrite it and every `cockpit close`/spawn kick reports "no daemon" for the rest of the process's life (they key off `PID_FILE.exists()` alone). The fast tick calls `daemon.reassert_pidfile` to rewrite it when missing/stale (idempotent, never clobbers a *different* live daemon's pidfile), so a lost pidfile recovers in ~30s — the same self-heal pattern as the name/colour/`idle=` re-asserts.
- **Ticks:** slow + fast run in `@work(thread=True)` workers; bodies (`cockpit.cockpit._once_with`/`_fast_tick`) are lock-free, serialized by the app's `_tick_lock` acquired *inside* the worker (blocked → `waiting`, holds → `running`). Startup is slow-first — `_start_fast` only after the first slow completes, so the first republish isn't a no-op vs empty caches.
- **Per-repo table republish:** `cycle_all` writes each repo's cells before fetching the next, so the slow tick hands it an `on_repo_done` hook (`_run_slow` → `_publish_inventory`, the same git+cells read its `finally` runs) fired after each repo — a finished repo surfaces in the table while later repos still round-trip `gh`, instead of all repos landing at once on tick end. The hook is a pure read (`_gather_inventory` + `call_from_thread(_render_table)`); a failing callback is logged and never aborts the remaining repos. **Never** let `on_repo_done` write a cell — only the daemon writes; this is a renderer refresh.
- **Signals:** `loop.add_signal_handler` only (SIGUSR1 → slow kick; SIGTERM/SIGHUP → clean exit). **Never** `signal.signal` — it raises off the main thread.
- **Table is read-only** (`worktree_table.py`, keyed by worktree path; worktrees are grouped under a per-repo group-header row — `HEADER_KEY_PREFIX`, a NUL-led sentinel key that can't collide with a path — with `sidebar_color` tinting both the header and the row labels; no `repo/label` collision prefix and no repo column. `current_path()` returns None on a header row so every row action no-ops there, and `current_capabilities()` returns `{HEADER_CAP}` which `FooterBar._skip` reads to hide every row-targeted key; on refresh the cursor auto-skips off a header onto the first worktree row). Reads only daemon-written flat cells (`cache.py::_write_pr_flat_cells`, republished fast): `pr-muted` → 🔇, `pr-nudge` → 🔔 (mute wins), `pr-author` → `@login`, `pr-comments` → 💬 count, `pr-base` → the stacked-PR `└` indent (see the stacked-PR invariant). The `pr-nudge` cell is `PR.nudge_issue` — the same actionable-issue value the slow tick's nudge decision reads, so the bell can't disagree with whether a nudge would fire; it clears automatically when the issue resolves (derived, never stored).
- **Row actions** (`f p t c C m N n`) live on the app, and — except `n` and `f` (which can spawn a workspace, *not* a cache cell) — never touch cmux/the cache. The **footer help text** is gated on three axes: (1) the resolved **backend** (`FooterBar.BACKEND_ACTIONS`, fed `resolve_tool()` at compose): `N`/Nudge is a cmux-only verb so its hint hides on limux/none; `f`/Focus works on cmux **and** limux (both can spawn — focus is the cmux-only bonus) and hides only on `none` (no backend to spawn into); (2) **workspace presence** — `N`/Nudge reaches an *existing* workspace so its hint shows only when the row **has** one (`ACTION_REQUIRES["nudge_row"] = "workspace"`); `f`/Focus is **not** workspace-gated — it focuses an existing session or spawns one first, so it shows on any backed row (the old `w`/Open key and its `ACTION_FORBIDS` gate are gone — `f` absorbed the spawn); and (3) the **highlighted row's content** (`FooterBar.ACTION_REQUIRES`, fed `WorktreeTable.current_capabilities()` via `app._refresh_footer_caps` on every row-highlight and table refresh): `p`/Open-PR + `m`/Mute hide on a row with no PR, `t`/Ticket hides on a row with no delivered ticket, and `m` reads **Unmute** when the row's PR is muted. `c`/`C` further hide on a **workspace-only primary checkout with no workspace** (`primary` cap without `workspace`) — its only close is workspace-only, pointless with nothing to close. Row caps are `{pr, ticket, muted, workspace, primary}` tokens: `pr`/`ticket`/`muted` read from the same daemon-written cells the cells render from (`row_capabilities`: `pr-num`, `pr-muted`, the cached delivery block) — never a network call; `workspace` reflects live backend state via a **single `workspace_cwds()` read per inventory refresh** (`app._live_workspace_paths`, degrades to empty on backend absence), cached into the row caps so per-keystroke footer gating stays a pure set lookup; `primary` is `wt.is_primary and wt.branch in MAIN_BRANCHES` — a `use_worktree: false` primary checkout sitting on its **default branch**, whose close is workspace-only. A primary checkout parked on a **feature** branch does **not** get the `primary` cap: its close tears the branch down (checkout default + `git branch -D`), so `c`/`C` stay advertised even with no workspace, exactly like a feature row. (The `MAIN_BRANCHES` test is a cheap, call-free "on the default branch" heuristic for the footer hint only — a miss never affects teardown's own authoritative `origin_head_branch` guard.) Caps `None` (empty table) shows the full legend, not an empty one. The `t` key is further gated globally by `show_tickets` (some repo has a provider). The actions stay bound and self-guard (pressing a hidden key still warns) — only the advertised hint follows backend + workspace + row state:
  - `f` focus → the single "take me there" verb (the former `w`/open-workspace folded in — focus was just spawn's trailing step). Ensure the row's worktree has a workspace, spawning one (reusing the daemon's `spawn_pr_workspace`/`spawn_orphan_workspace`, PR-payload-reconstructed via `_pr_from_payload`) when missing, then focus it (`cmux focus`). The cwd-keyed `find_cockpit_workspaces` adopts a freshly-spawned workspace next tick (no double-spawn) and `_dedupe_workspaces` reaps a race dupe. **Works on cmux *and* limux** (both can spawn); on cmux it focuses, on limux (no select verb) the user switches via limux's own UI. Reachable on any backed row including a `use_worktree: false` `master`; slow-kicks after a spawn (a pure focus of an existing session does not). **`use_worktree: false` repos** can host several sessions all rooted at the same checkout cwd, so cwd-matching can't single out "the repo's session" — there `f` resolves by **repo name** (`_workspace_ref_by_name`), switching to a workspace named after the repo, falling back to the cwd match, then a spawn. `p` opens the PR URL. `t`/Open-ticket is **provider-neutral** — it routes through the row's `TicketProvider.ticket_url` (`tickets.provider_for`): GitHub builds the issue URL deterministically from the delivered ref + the PR's repo nwo (parsed from the cached PR URL, no network); Linear reads the exact `Linear: [ID](url)` footer link out of the PR body via `gh.pr_body` (its canonical URL can't be hand-constructed). The delivery block is cached under the `ticket` key for **all** providers.
  - `c` close → `probe_blockers` gate → enqueue `TeardownRequest` → slow kick, so teardown flows through the daemon's `_drain_close_requests`. **Feature worktree:** refuses dirty/unpushed/open-PR, then closes workspace + removes the worktree. **Primary checkout** (a `use_worktree: false` repo, `worktree_path == repo_path` / `wt.is_primary`): `teardown` **always** skips `git worktree remove` (git refuses it on a primary checkout, and the user works there in place), then splits on the checkout's branch: (a) **on its default branch** — a **workspace-only close**: the unpushed guard relaxes (`worktree_state_blockers(is_primary=True)`; the checkout and its branch stay, so unpushed commits are safe), leaving only the dirty guard ("make sure it's all committed"); (b) **on a non-default (feature) branch** — the branch is **torn down**: after the workspace close, HEAD is moved back to the default branch (`checkout_branch`, git refuses `branch -D` of the checked-out ref) and the feature ref is deleted (`delete_local_branch`). Case (b) is **not** relaxed — the branch is going away, so its unpushed commits are not safe; the callers pass `is_primary` to the blockers as `wt.is_primary and on_default` (resolved via `origin_head_branch`; `default is None` off-GitHub keeps it workspace-only, since nothing can be deleted). Callers set `delete_branch = pr_is_merged or (wt.is_primary and not on_default)`; `teardown` reuses a single `origin_head_branch` read for both the relaxation and the `branch != default` delete guard, and the checkout+delete is soft-fail (a failed checkout leaves the branch for a retry, never aborting the already-run workspace close).
  - `C` force-close → overrides the *soft* open-PR block (`forced=True`) but still refuses the *hard* `worktree_state_blockers` (uncommitted; unpushed except on a **workspace-only** primary checkout — i.e. one on its default branch, where nothing is removed; a primary checkout on a feature branch is torn down, so its unpushed guard stands), so force never discards local work. The TUI's `c`/`C` and the `cockpit close` CLI (`cockpit/close.py` — defaults to the cwd's worktree, `--force` overrides the soft open-PR gate) are the two human entry points; both resolve the same `(state, blockers)` and `enqueue` the same `TeardownRequest`, thread `is_primary` into the gate, and the daemon's autoclose/orphan-reap enqueue alongside them — all draining through the one `orchestrators.teardown` path, which detects the primary checkout by `worktree_path == repo_path`. **Closing never runs teardown inline** (no daemon → the marker stays durably queued); only the daemon writes the cache.
  - `m` mute → writes a `NudgePref` (session state, not a cell) + slow kick to republish `pr-muted` + 🔇.
  - `N` nudge → `cmux.nudge_if_idle` with no pr/category (overrides mute + throttle) but still honours the idle gate — passive skip-with-toast when not at rest, never a forced `send`.
  - `n` new → modal (`NewWorkspaceScreen`), then `cockpit new <source>` detached via module dispatch (`python -m cockpit.cli new`, **not** `spawn.py` by path — that breaks imports); auto-detects bare/`#N`/URL/Linear-id/Slack-URL and routes to the modal's chosen repo (its `cwd`), then slow-kicks so the worktree surfaces later. `N` is off `n` so New gets the bare key.
  - **Row-action kicks are repo-scoped:** every state-changing row key (`f`-after-spawn/`c`/`C`/`m`/`n`) kicks `_kick_slow(<row's repo path>)` → `cycle_all(only_repo=…)`, which reconciles *only* that row's repo and skips the repo-spanning sweeps (`close_gone_cwd_workspaces`, `_reap_workspace_orphans`) + the plugin-update check — so the line refreshes without round-tripping `gh` for every other repo. The close queue is still drained (a `c`/`C` teardown lands there and the keypress is waiting on it). `s` sync, SIGUSR1, the periodic interval, and startup stay **full-cycle** (`only_repo=None`). An unknown `only_repo` path reconciles nothing (no fall-through to all-repos).
- **Global keys:** `s` sync, `o` output, `q` quit, plus the one repo-scoped key `h` (below). (Updates are handled by `brew upgrade`, not an in-TUI key — there is no `u`/self-update and no `r`/"What's new" release-notes key. The command palette's "Show config: all repos" / "Edit config" entries remain.)
- **`h` parks a repo — the one *repo*-scoped key, and the only user state that stops the daemon polling.** **One key, three meanings, read off the cursor row** (`app.action_hide_repo`, dispatching on `WorktreeTable.current_capabilities()`): on the `▸ N hidden` disclosure row it expands/collapses the parked set (`HIDDEN_CAP`, `_toggle_hidden_section`); on a revealed parked repo's row it un-parks (`PARKED_CAP`); anywhere else it parks the cursor row's repo. **Do not** re-introduce a second key (the old `H`) for reveal — unhiding must be reachable from the row that says something is hidden, not from a shifted key the user has to know exists. The footer's `h` hint relabels itself Reveal / Collapse / Unhide / Hide off those same caps (`FooterBar._label`), so the one key always announces which meaning is live. The hidden row is also the **one row a single click acts on** (`WorktreeTable.HiddenToggle`; every other row needs a double-click) — a disclosure triangle that needs a double-click doesn't read as one — and the one row where **Enter** opens the section instead of focusing a workspace (it has no path to focus). **`on_click` must resolve the clicked row from `event.style.meta`, never from the cursor:** Textual's MRO walk takes each class's `_on_click` *or* `on_click`, and `WorktreeTable` defines only the latter, so it is dispatched **before** `DataTable._on_click` moves the row cursor — a cursor read there tests the *previously* selected row, which silently demoted the single click to a double click. `h` toggles the cursor row's whole **repo** (resolved via `WorktreeTable.current_repo_name()`, so it works on a group header, a worktree row, or a revealed parked row) into a parked set persisted at `$COCKPIT_HOME/hidden-repos.json` (`cockpit/lib/hidden.py` — keyed by **resolved path**, never the mutable config `name`; a corrupt file fails *open*, i.e. nothing parked). Parking is **not** unregistering: the repo stays in `config.json`, untouched — this is deliberately *not* a config field, so parking never rewrites the user's hand-edited config (and it isn't in `config.example.json` / `docs/config.md`; the three-face config-sync rule doesn't apply). A parked repo goes **dormant**, not merely invisible: `cycle_all` filters it out of the per-repo loop, so it costs no `gh` round-trip and gets no auto-spawn / nudge / ticket write. **The filter is skipped when `only_repo` is set** — an explicit gesture at one repo (`cockpit close` from inside a parked worktree) must still reconcile, and the close-queue drain runs either way. The **fast** tick is untouched (network-free local git cells), so an un-park paints correctly and a workspace still open on a parked repo keeps a live statusline. Parking also clears the repo out of the **cmux sidebar** (`app._park_workspaces`, a `@work` thread since it shells out to git + cmux): hiding the row while its workspaces stayed in the sidebar would only move the clutter. It is **workspace-only**, exactly like `c` on a primary checkout — no worktree removed, no branch deleted, nothing uncommitted touched; parking is not teardown. Workspaces are matched **by cwd against the repo's own `worktrees()`**, never by a path-prefix test (a worktree usually lives in a *sibling* directory). Two are always spared: the daemon's own (`self._self_ws` — closing it kills the TUI) and any that isn't `workspace_is_idle` (a running agent mid-turn), the latter reported by toast rather than silently skipped. Un-parking closes nothing and **respawns nothing** — a worktree-managed repo gets its workspaces back from the next slow tick's `_spawn_missing_workspaces`, a `use_worktree: false` one from `n`/`f`. `h` re-renders via `_prime_table()` (local read, no network) — parking, revealing, and un-parking must never cost a fetch. The parked set collapses into **one** trailing disclosure row (`HIDDEN_ROW_KEY`, nested under `HEADER_KEY_PREFIX` so `current_path()` is None and the cursor-skip loop covers it for free), `▸ N hidden` collapsed / `▾ N hidden` expanded. Expansion is **session only** (`app._show_hidden`, deliberately not persisted, so a restart comes back tidy) and renders each parked repo as a dim `(hidden)` **name row with no worktrees** — a parked repo is dormant, so `_gather_inventory` skips it whether or not it's revealed and revealing costs no `git worktree list`. The cursor-skip loop stops at the hidden section (`hidden_start`), so expanding doesn't slide the cursor down through the revealed repos. `h` lives in the footer's **global** group, not `ROW_ACTIONS` — a group header suppresses every row key, and a header (or the disclosure row) is exactly where you reach for it.
- **Updates are brew's job — no in-process self-update.** cockpit is a brew formula, so `brew upgrade cockpit` (or the tap's own update) replaces the installed console script; there is no version check on the tick, no `⬆` header indicator, no `u` key, no re-exec, and no `cockpit update` subcommand. `version.running_version()` (from `pyproject`'s static version via `importlib.metadata`) is display-only (`cockpit --version`).
- **stdout:** all tick prints go through one process-wide `_QueueWriter` — **never** per-tick `redirect_stdout` (the threads race).

### Only the daemon writes the cache; renderers read

`lib/starship.py` field printers are strictly read-only (no gh/git/subprocess/`atomic_write`).

- **Slow tick** (`slow_poll_interval_seconds`, 300s) — `cycle.py::cycle_all`: full reconcile (gh fetch, base-distance, per-PR JSON, PR flat cells, git-state cells, pills).
- **Fast tick** (`fast_poll_interval_seconds`, 30s) — `cockpit.py::_fast_tick`: re-asserts the pidfile (`daemon.reassert_pidfile` — heals a pidfile lost mid-run so `cockpit close`/spawn kicks stay reachable; see the pidfile self-heal note) then network-free republish of git-state (`write_git_state_cache`) + PR flat cells from disk (`republish_pr_caches_from_disk`) + workspace name (`reconcile_workspace_names`) and sidebar-colour (`_tint_repo_workspaces`) reconcile, so the pidfile / `git checkout` / tmpdir wipes / a freshly spawned workspace's name+colour recover in ~30s.

New cell → writer in `cache.py`, call site in the slow tick (decide + snapshot) and/or fast tick (republish). **Never** let a renderer read source state directly — that same-render disagreement is the bug class this avoids.

### `sidebar_color` — cosmetic, cmux-only, per-repo

Applied slow-tick via `_apply_repo_colors` **and** fast-tick via `_tint_repo_workspaces` → `cmux … set-color`, deduped in `pill_state` under `color:<ref>` (the same key + persistent dict, so cmux is touched only on change/restart; the fast pass just closes a freshly spawned workspace's ~300s→~30s colour gap, mirroring the name reconcile). Validated at preflight (`_validate_sidebar_colors`, `sys.exit(2)` on unknown). Valid set = `colors.CMUX_COLOR_ANSI` (= `cmux.WORKSPACE_COLORS`).

### `orgs` is a load-time defaults layer — nothing below `load_config` knows orgs exist

An org (top-level `orgs: {<name>: {<repo defaults>}}`, referenced by a repo's `org` key) is **only** a named block of per-repo defaults for the "many small repos, one organisation" shape. `config.py::apply_org_defaults` merges it into each member repo entry inside `load_config()` — `repo.setdefault(k, v)` per key — so the resolution chain every reader already walks (repo → global → default) gains an org rung with **zero** call-site changes: `sidebar_color` tints the whole org in both the cmux sidebar and the TUI, one `use_worktree: false` covers every member, `branch_prefix`/`tickets`/`review_prs` all inherit. **Do not** add an org-aware reader, an `org_*` config field, or a `repo_org(...)` resolution helper — if a field needs org support it already has it. Four rules:

- **One level deep, repo wins.** A scalar the repo sets beats the org's whole; a *block* (`tickets`, `skills`) unions per **field**, repo winning — the same granularity `_tickets_field`/`_skills_field` already give repo-over-global. It is **not** a whole-block override: that would defeat `tickets.project`, the one field meant to differ *within* an org, since a repo adding it would silently drop the org's `keys` (stops matching its own team) and `api_key_env` (reads the wrong credential). Exactly one level — nothing nests below a block, so **do not** make it recursive. A block is always rebuilt into a fresh dict, never aliased onto the repo: one org block is shared by every member, so handing out the same object would let a mutation of one repo's block reach all its siblings'. Idempotent (re-unioning a merged block with itself is a no-op), which is what lets `preflight.validate_config` call it on a raw dict.
- **Never persisted.** The config *writers* (`registry.register_cwd`, `save_config_value`) re-read `config.json` from disk instead of reusing `load_config()`, so an inherited value can't be baked onto a repo entry. **Do not** introduce a writer that serializes `load_config()`'s dict back to disk.
- **Validated as effective values.** `validate_config` runs `_validate_orgs` (block shape; `name`/`path`/`org` rejected as org defaults; a repo naming an undefined org hard-fails — the silent no-tint/no-opt-out bug) then merges, so every existing `_validate_*` sees the post-merge value and an org-level bad `sidebar_color` fails like a repo-level one.
- **TUI ordering only, no nesting.** `config.py::repos_grouped_by_org` (used by `app._gather_inventory`) renders an org's repos adjacent, each org at its first member's config position; org-less repos keep theirs, so an org-less config is byte-identical to before. There is deliberately **no** org header row (a second nesting level costs cursor-skip, caps, and footer gating for what shared tint already conveys), no cross-repo cmux workspace-group (`_reconcile_sidebar_groups` is per-repo and only touches groups overlapping *this* repo's refs), and no park-the-whole-org key (`h` stays per repo).

### Stacked PRs: one cmux sidebar group + one indented TUI row — derived from `PR.base`, never stored

A [stacked PR](https://docs.github.com/en/pull-requests/how-tos/stacked-pull-requests) chain carries **no** stack id, position, or parent field on GitHub's API — `gh stack` is a local branch-management tool, and the only thing the API exposes is that each PR's base branch is the previous PR's head. So `lib/stacks.py::find_stacks` derives the chain from `PR.base` (`baseRefName`, already selected by the relevant-PR query): zero extra round-trips, no dependency on local `gh stack` state in the worktree, and it works on a coworker's stack too. **Do not** shell out to `gh stack view` per worktree, and **do not** persist a stack — it is inventory, derived every cycle like `git worktree list` (see the "Inventory is derived every cycle" invariant). Chains match on `PR.branch` (already `pr_worktree_branch`-normalized), so a trunk-headed PR's synthesized `pr-<N>-…` branch matches nobody's base — correct, since a merge-the-trunk PR is not a stack member. A stack forking into two children still yields **one** chain (breadth-first from the root): a cmux workspace can live in exactly one group, so overlapping chains are not representable.

Slow-tick `cycle.py::_reconcile_sidebar_groups` renders each chain of ≥2 PRs *that have local workspaces* as one collapsible cmux **workspace group** (`cmux workspace-group`, `square.stack` icon), headed by its own row named **`<tip> (N)`** — the chain's *tip* (its deepest PR, `find_stacks`' last member), not its root, and every member including the tip lists below the header, tip first (`create_workspace_group` lands the caller's first ref at the top). Naming and ordering by the tip is what keeps the sidebar and the TUI reading as the same stack — **do not** re-name the group after the root. cmux-only and best-effort (`workspace-group` is in `cmux.py::_CMUX_ONLY_VERBS`, every verb `check=False`) — limux/none silently skip it. Three rules that are load-bearing:

- **Reconciled against cmux's live `workspace-group list`, not a `pill_state` mirror** (unlike `color:<ref>`) — the group is the derived stack's only representation, so cmux is the authority and a restart re-syncs for free instead of duplicating groups.
- **Matched by member ref, never by name** (`_match_stack_group`): group names are cosmetic and collide across repos (same reason `workspace_name` collides — repo is conveyed by tint), while a `workspace:N` ref identifies exactly one row. Only groups overlapping *this repo's* owned refs are touched, so a group the user built by hand around unrelated workspaces is never claimed, re-membered, or dissolved.
- **The group header is cmux's spawned anchor, kept — never a group member.** `cmux workspace-group create` always spawns a *fresh* workspace to own the group, and the anchor's sidebar row **is** the group header. Re-anchoring onto the stack root (what cockpit used to do) therefore *swallowed* the root's own row: a 4-PR stack rendered three rows under a header that said `(4)`. So `create_workspace_group` keeps the spawned anchor as a dedicated header and every member lists below it, making `_stack_group_name`'s / `_review_group_name`'s count exactly the number of rows folded. Two consequences: the anchor is spawned with `--cwd $HOME` so it sits **outside every registered repo** (inside one, `_reap_workspace_orphans` would reap it and take the group down with it), and `_reconcile_sidebar_groups` **closes it on dissolve** (`ungroup` preserves all members, so an unclosed anchor strands as a loose row) — but only when the anchor isn't one of the repo's owned refs, so a group anchored on a real workspace loses the fold, never the workspace — and it *does* lose the fold every time: an anchor that is one of the repo's own refs is kept out of `_match_stack_group`'s candidates, so the group dissolves and is rebuilt on a throwaway anchor rather than reused (self-healing for a group cockpit made before the anchor was split out, one-shot for a hand-made fold; members are preserved through both). **The anchor outliving every member is its own leak, and needs its own sweep:** close a stack's workspaces (teardown, a respawn under fresh refs) and cmux keeps the group with the anchor as its sole member — at which point `owned & set(g.members)` is empty forever, the "only touch groups overlapping this repo" filter can never reclaim it, and the next cycle builds a *second* group beside the stranded header (four identical `<tip> (N)` rows was the observed shape). So the reconcile also sweeps groups it owns *no* member of, gated on both `icon` in `{square.stack, eyeglasses}` (cockpit is the only thing that sets one) and `members <= {anchor}` — never a fold that still holds a workspace, never one the user built by hand.

Grouping is **cosmetic** — it never spawns a *worktree*, closes a member, nudges, or writes a cell. A stack losing its root (bottom PR merged) leaves the survivors stacked on each other until the group drops below two members, at which point it is `ungroup`ed back into loose rows.

**The TUI shows the same stack as indentation, read off a flat cell.** The table can't see `PR.base` (renderers never read source state), so the daemon writes it: `pr-base` joins the branch-keyed flat cells (`cache.py::_write_pr_flat_cells`, persisted in the PR JSON as `base`, republished by the fast tick). `stacks.py::stack_order` is the renderer-side half of `find_stacks` — same `base` link, but over `(branch, cell)` pairs — returning `(index, depth)` so `worktree_table.py::_stack_rows` sorts each chain contiguously under its **tip** and `_workspace_cell` indents the label behind a `└` (leftmost, ahead of the 🔇/🔔 glyph). **The nesting is exactly one level deep, and the tip heads the chain** — `stack_order` emits the deepest member at depth 0 and every PR it is stacked on at depth 1, in root-first order, mirroring the sidebar group's `<tip> (N)` header + flat member list. A four-PR chain stepping right four times is unreadable at any width and the depth number says nothing the order doesn't, so **do not** restore the per-level cascade (`_workspace_cell` therefore renders one fixed `└` prefix, not a depth-scaled indent). It is keyed by **index, not branch**, so two worktrees reporting the same branch (detached HEADs) each keep a row, and a base cycle from a stale cell falls back to flat rows rather than dropping them. Unlike the cmux group, indentation needs no ≥2 threshold and no workspace — a stacked worktree indents whether or not a session is open on it.

**Coworker reviews fold into one trailing `reviews` group, same machinery.** The same slow-tick pass folds this repo's `not PR.mine` workspaces into a group named `reviews (N)` (`eyeglasses` icon) and re-parks it at the **bottom** of the sidebar every cycle (`cmux.move_workspace_group_to_end` — `--to-index 9999`, which cmux clamps; `workspace-group list` reports no index, so there is nothing to compare against and the move is unconditional). Reviews are the passive pile — someone else's PR I'm reading, never mine to ship (the same `PR.mine` seam that suppresses the nudge and swaps in the review-mode seed prompt) — so they belong out of the way of my own rows. Two rules on top of the three above: **stacks win the overlap** (a coworker PR inside a stack folds with its chain — `desired` is built stacks-first and the reviews list excludes every already-stacked ref, because a workspace can live in exactly one group), and a **lone** review stays a loose row (cmux drops a group the moment it has one member) — but is still parked at the bottom on its own, via `cmux.move_workspace_to_end` (`reorder-workspace --index 9999`, clamped like the group move) after the ungroup sweep, so the passive pile sinks whether or not there's enough of it to fold. It is derived from `PR.mine` every cycle like everything else here — **do not** persist a "this is a review" marker, and **do not** give the fold its own reconcile pass; it is one more entry in the same `desired` list.

### Workspace names track repo + branch (`wt.workspace_name`), re-asserted on both ticks

`wt.label` (`git.py::branch_label`) derives from the *branch*, not the dir basename (`wt.short`): strip `branch_prefix`, drop a leading base segment (`master/`), slugify, drop a leading ticket/PR token (`pe-4608-`) — but never to `""`. The **cmux workspace name** is `wt.workspace_name` = the bare `label` (no `[<repo>]` prefix — repo is conveyed by `sidebar_color` tint in both the cmux sidebar and the TUI table, so the two never double up). `workspace_name` stays a distinct property (one seam for the naming paths) even though it now equals `label`; `wt.repo_name` is still threaded onto the `Worktree` at construction, but only for the `git-repo` cell (`write_git_state_cache`), not the name. Every path that spawns, renames, or matches a workspace **by name** uses `workspace_name` (`spawn_pr_workspace`/`spawn_orphan_workspace`, `reconcile_workspace_names`, `find_cockpit_workspaces`, `_handle_orphans_and_close_stale`, `_reap_workspace_orphans`, `_teardown_worktree`'s name fallback); cwd→path matching (the primary route everywhere) is unaffected. **Consequence:** dropping the prefix means two repos with the *same* branch label produce the same workspace name — a **cosmetic** collision everywhere (cockpit matches by cwd→path, never by name) except the one functional edge of orphan-auto-spawn's name-clash skip (`_reap_workspace_orphans`), which will skip auto-spawning the second same-named orphan. cockpit resolves workspaces by cwd→path, never by name; `cmux.rename_workspace_if_needed` re-asserts the name idempotently (slow tick `_refresh_tracked_pills`/`_refresh_orphan`; fast tick `reconcile_workspace_names`), recovering drift in ~30s. Cosmetic, never a `send`. **Consequence:** to relabel, rename the *branch* — a manual workspace rename is reverted next tick. **Exception:** any **main-branch** worktree — `wt.is_primary` **or** `wt.branch in MAIN_BRANCHES` (`cockpit.lib.constants`) — keeps its custom name (`reconcile_workspace_names` guards on both), so a `master` workspace named e.g. `morning` isn't force-renamed. The branch half of the guard matters in a **bare repo**, where no sibling worktree is ever `is_primary`: a feature worktree temporarily parked on `main` would otherwise be renamed to `main`, colliding with another workspace and breaking switching.

### The daemon creates worktrees in the background — never blocking the tick on `git`

`cycle.py::_spawn_missing_workspaces` shells out via module dispatch (`python -m cockpit.cli new`) in a detached `Popen(start_new_session=True)`:

- **My PR, no worktree** → `cockpit new --pr <n> --repo <name>` (plan-only prompt). Always on.
- **`review_prs` (per-repo, default false)** → every coworker open PR without a worktree → `cockpit new --pr <n> --review --review-command <cmd>`. Discovery: `gh.list_open_pr_heads` (uncapped `is:pr is:open`; the normal query is `author:self`-only). Validated `_validate_repo_bool`. **Dependabot PRs are excluded by default** — they're coworker-authored so they'd flow through this path, but `_spawn_missing_workspaces` skips any candidate `gh.is_dependabot(author)` (GraphQL login `dependabot`, plus the REST `app/dependabot` / `dependabot[bot]` spellings) unless the repo sets `"dependabot": true` (`_validate_repo_bool`). This is the single gate; the "my PR" and orphan paths are `author:self`-gated and never see dependabot. **External (non-collaborator) PRs are also excluded by default** — a fork/outside contributor's PR body and diff are untrusted content, and auto-spawning a Bash-capable review agent on it is a prompt-injection risk on a public repo. `list_open_pr_heads` now also returns each candidate's GraphQL `authorAssociation`; `_spawn_missing_workspaces` skips any candidate whose association isn't `OWNER`/`MEMBER`/`COLLABORATOR` unless the repo sets `"review_external": true` (`config.py::review_external`, validated `_validate_repo_bool` like `dependabot`). This gate is independent of the dependabot gate — both must pass for a candidate to spawn. The seeded first turn is the **configurable** `skills.review` (`config.py::review_command` reader, single-sourced from `REVIEW_COMMAND_DEFAULT`, per-repo → global → default, validated `_validate_skills`). The default is Claude Code's **built-in `/review`** — it ships with every Claude Code install, so it resolves in every spawned review workspace (a personal global skill like `/pr-review` only resolves for its owner; a project skill only when the watched repo is that repo). Override per-repo (or globally) with a personal `"/pr-review"`. The auto-review is **dry-run**: `spawn._review_prompt`'s closing line tells it to report findings and **ask before posting comments or submitting an approve / request-changes verdict** — a human authorizes those, the daemon never auto-posts. **Keep the spawn-layer default in sync with `REVIEW_COMMAND_DEFAULT`** (`spawn.py` imports it for both the `--review-command` argparse default and `_review_prompt`'s param) — don't hardcode a literal command string in `spawn.py`. `skills` has two sibling seams for the same externalize-the-verb pattern, both default `""` (built-in prose, no config needed): `skills.plan` (`config.py::plan_command`) leads `_plan_only_prompt` on a plan-only PR/branch spawn, and `skills.actions` (`config.py::actions_command`) leads `_actions_prompt` on a GitHub-Actions-run-URL spawn — both followed by the source/run/PR context and the shared `plan_tail.txt` no-code/wait-for-approval gate (never externalized) via the shared `command_seed.txt` template. Ticket-fetch spawns (Linear/Jira/Trello/GitHub-issue) are untouched — they keep their own dedicated MCP-fetch-and-rename prompts, not `skills.plan`/`skills.actions`.

Both go through `_bg_spawn_pr`, which guards in-flight launches in `pill_state` (`spawn:<owner>/<name>:<branch>`, TTL `_SPAWN_INFLIGHT_TTL_SECONDS`) against a double-launch; logs to `$COCKPIT_HOME/spawn.log`. Review worktrees then track via the normal `match_worktrees` coworker path; orphan auto-spawn stays `{self_user}/`-gated.

**A coworker's PR is review-mode everywhere — never author-mode.** `PR.mine` (set in `_pr_from_node` from the query layer's `self_user`; defaults **true** so a hand-built PR keeps author-mode) is the single flag, and it gates the two places a tracked coworker worktree would otherwise be told to rewrite someone else's branch:

- **No nudge.** `PR.nudge_issue` requires `mine` alongside its OPEN gate, so `_refresh_tracked_pills`' `others_items` never reach `maybe_nudge` — the author-mode `_NUDGE_DESC` text ("CI is failing — address it", "merge conflicts — rebase and force-push", "unresolved review thread(s) — reply or push fixes") is the PR author's job, not the reviewer's. Because `nudge_issue` is also the source of the `pr-nudge` flat cell, the TUI 🔔 goes quiet on coworker rows in the same breath — bell and nudge can't disagree (the same single-authority reason the OPEN gate lives there). Pills, cells, and the Issue column still render the issue: only the *nudge* is suppressed, never the display.
- **Review-mode seed prompt.** `build_pr_prompt` branches on `mine`: my PR gets the per-`display_issue` action + `pr_authority.txt` (commit/force-push without asking); a coworker's gets `review.txt` led by `skills.review` — the same dry-run seed `spawn._review_prompt` uses for the `review_prs` path, resolved at global level (`review_command()` with no repo entry, since `spawn_pr_workspace` carries a PR + worktree, not the repo block). This matters for the *non*-`review_prs` route: a coworker worktree that already exists but has no workspace is spawned by `_spawn_missing_workspaces` through `spawn_pr_workspace`, which would otherwise hand a review session `pr_authority`'s force-push grant. The TUI's `f` key inherits it — `_pr_from_payload` sets `mine=not p.get("author")` (the cache records a login *only* for a coworker's PR).

**Do not** add a nudge or an authority grant that keys off the worktree's existence alone — a local worktree on a PR branch means "I'm engaged with this PR", not "I own it". Gate on `PR.mine`.

**`use_worktree: false` repos opt out of all of the above.** The flag is a per-repo bool that defaults **true** (absent = normal worktree-managed repo); the *inverse* polarity is deliberate — a repo registered by bare `cockpit new` (no source/`--cwd`/`--repo`) carries `"use_worktree": false` and `_spawn_missing_workspaces` **early-returns** (`if not repo_entry.get("use_worktree", True)`) for it — the user works in-place on the main worktree (often `master`, possibly off-GitHub) and never wants cockpit creating PR/review/orphan worktrees. The row renders **only while a workspace is open on it** (`app._gather_inventory` filters such a repo's worktrees down to those in the per-refresh `workspace_cwds()` set): with nothing open the branch row is unactionable — `f`/`c`/`N` have no session to reach — so the repo collapses to its bare group header, and `n` (on that header) starts one on demand. A backend hiccup (empty `workspace_cwds()`) degrades to the same header-only state, which is recoverable by the same key. Worktree-managed repos are never filtered — their rows stay derived from `git worktree list` + the cell writers, independent of spawning. Registration is `registry.py::register_cwd(use_worktree=False)`: it appends the cwd's main repo to `config.json` (writing `"use_worktree": false` **only** when False — the key is omitted for the default; empty branch prefix when off-GitHub via `gh_self_user`'s try/except; `default_base` from `gh` then git `symbolic-ref` then `"main"`), skips the interactive branch-prefix prompt (irrelevant with no worktree branches), and is idempotent — an already-registered repo is returned untouched, so a bare spawn in a normal managed repo does **not** flip it. Validated `_validate_repo_bool(cfg, "use_worktree")` (polarity-agnostic — any present-but-non-bool value hard-fails). The bare path in `spawn.py::main` then flows through the existing `--cwd` branch (workspace at the repo root, no branch, no worktree). **The `n` row-key branches on it:** a `use_worktree: true` repo cuts a new worktree/branch per `n`; a `use_worktree: false` repo gets **one** named workspace on the checkout (`cockpit new --cwd <repo_path> --name <name>`, no worktree) — the modal picker grays a `use_worktree: false` repo that already has a workspace (policy: one addressable workspace per such repo; `f` reaches it) and prefills the name Input with the repo name. **GOTCHA:** every read is `not repo.get("use_worktree", True)` — a bare `.get("use_worktree")` (no default) treats an unconfigured repo as opted-out and silently stops auto-spawning it. **Do not** let `use_worktree: false` repos reach any auto-spawn — the early return is the single gate.

### Trunk-headed PRs get a synthesized branch — `main`/`master` heads never become the worktree branch

cockpit joins a PR to its worktree, row, and cache by the **head branch name** (`headRefName`) everywhere. A "merge main into `<feature>`" PR breaks that: its head IS the trunk (`main`/`master`), so checking it out clobbers local `main`, collapses onto the primary checkout, and labels the workspace `main`. `gh.py::pr_worktree_branch(number, head, base)` is the **single** normalizer: for a head in `MAIN_BRANCHES` it returns `pr-<N>-<base-slug>` (a distinct, trunk-safe branch carrying the PR number); otherwise the head verbatim (the 99% case, zero change). Applied at the four join points that must agree or the row won't line up: `_pr_from_node` (`PR.branch`), `resolve_pr_branch` (the `cockpit new --pr` checkout branch — fetches `refs/pull/N/head`, never touches local `main`), `list_open_pr_heads` (the `review_prs` candidate branch, so `existing_branches`/no-respawn match), and `_relevant_pr_query`/`_collect_nodes` — which rejoin the synthesized worktree to GitHub **by the embedded number** (`pullRequest(number:)`), since `headRefName: main` can't be the key. `branch_label` already strips the leading `pr-<N>-` token, so the workspace reads as the **base feature** it merges into (`feature/new_onboarding` → `new-onboarding`). The user's own branches carry `branch_prefix` (`khivi/pr-…`) so `_SYNTH_PR_BRANCH_RE` (`^pr-(\d+)-`) never misfires on them. **Do not** re-thread `headRefName` straight into a worktree branch — route it through `pr_worktree_branch`.

### Slack thread source — codename branch, MCP-delegated fetch, no `claude mcp list` probe

`spawn.detect_source` classifies a Slack permalink (`slack.SLACK_URL_RE`) as `slack` mode — a user-initiated source only (never daemon auto-spawned), so it has no cache cell / pill / `docs/state-machine.md` node, same shape as `actions`. A Slack URL carries no human name, so spawn synthesizes a deterministic codename branch (`codename.codename(slack.slack_seed(url))` → `<prefix><adj>-<noun>`). The seed is the thread's **stable identity** (channel id + message ts via `slack_seed`), NOT the raw URL — so query params (`?thread_ts=…&cid=…`) and the `archives` vs `app.slack.com/client` shape don't change the branch, keeping re-spawns idempotent. Cockpit never calls the Slack API: `_slack_prompt` delegates the thread read to the in-session Slack MCP (mirrors `_linear_prompt`), and under `use_slack: true` instructs Claude to append a topic slug to the codename (`cosmic-otter` → `cosmic-otter-fix-oauth`) and rename the workspace. **Never** add a `slack_mcp_available()` / `claude mcp list` pre-flight gate: that probe is unreliable for claude.ai-managed connectors (false-negatives even when live), so a positive-detection gate would silently disable the feature — the prompt's own retry-then-STOP logic handles a genuinely absent connector. `use_slack` (bool, `_validate_global_bool`) gates only the fetch/rename detail; the URL is seeded as context regardless.

### Prompt prose lives in packaged `cockpit/prompts/*.txt`, not Python string lists

Both prompt families render packaged templates via `cockpit.lib.templates.render(name, **slots)` (`str.format` — no escaping needed: rendered bodies have no literal braces, and a `{...}` in a *value* like a PR title is data, never re-parsed): the spawn first-turn prompts (`spawn._linear_prompt` / `_jira_prompt` / `_trello_prompt` / `_github_issue_prompt` / `_slack_prompt` / `_plan_only_prompt` / `_review_prompt` / `_actions_prompt`) and the per-PR / orphan prompts (`lib.prompts.build_pr_prompt` / `build_orphan_prompt`). The split is strict: **templates carry only static prose + `{slots}`; the Python builder owns all control flow and value computation.** The builder computes the interpolated values, picks the template when there's a choice (Slack's two modes are `slack_fetch.txt` vs `slack_context.txt`; `build_pr_prompt` maps `pr.display_issue` → one `pr_action_*.txt` via `_ISSUE_ACTIONS`, gating `pr_authority.txt`), and builds any conditional block in Python to inject as a slot (e.g. `{source_block}`, `{action}`), passing the shared `plan_tail.txt` into spawn templates that end with `{plan_tail}`. A missing slot raises `KeyError` loudly — never a silent stray placeholder. **Do not** re-inline prompt prose into Python lists, and **do not** add conditionals to a `.txt` (no templating engine — pick the template in the builder). `skills.review` (default `/review`), `skills.plan`, and `skills.actions` (both default `""` — built-in prose) still lead their respective prompts as a slash-command name (expanded in-session by Claude Code); only the surrounding context is templated. **Packaging gotcha:** hatchling ships only **VCS-tracked** files, so a new `cockpit/prompts/*.txt` must be `git add`ed or it silently won't land in the wheel (`importlib.resources` then `FileNotFoundError`s on the installed daemon); `tests/test_templates.py` asserts every template resolves.

### The one cache exception: session-scoped cells (written outside the daemon)

`lib.claude.stash_from_stdin` writes `context-<sid>`, `rate-limit-5h-<sid>`, `model-<sid>`, `permission-mode-<sid>`, `transcript-path-<sid>`, `cost-<sid>` from the statusLine stdin (the only place that data exists). Never read by the daemon. **Do not** extend this exception to a new cell.

### Nudge idle-gate: trust the `idle=` pill, NOT cmux's native `Needs input`

`nudge_if_idle` (`lib/cmux.py`) must tell "parked at prompt (safe to `send`)" from "awaiting a y/n permission (unsafe)". cmux native `claude_code=` has `Running`, `Idle`, and the **ambiguous `Needs input`** (fires for both an idle session aged past Notification *and* a pending permission). The gate: block on native `Running`; safe iff the `idle=` pill is present OR native is the unambiguous `Idle`; self-heal a dropped Stop-hook write by re-asserting `idle=` under native `Idle`. The pill (`cockpit/hooks/cmux-idle-pill.sh`) uses a verify+retry loop — its silent loss under cmux contention (`Broken pipe`) was the original bug. **Never** simplify the gate to trust `Needs input`.

### Config surface has three faces — keep them in sync

`cockpit/lib/config.py` is the authoritative reader (default + resolution per field), but it has two documentation mirrors that drift silently: `cockpit/config.example.json` (the sample schema — documentation only, never installed; a fresh install seeds `{"repos": []}`) and `docs/config.md` (the human field reference). **Any change to a config field — new key, renamed key, changed default, new `tickets`/provider field — MUST update all three in the same PR:** the `config.py` reader, the `config.example.json` sample, and the `docs/config.md` table. Adding a reader without the sample+doc entry is the drift this prevents — a field the code honors but nobody can discover. (Provider ticket fields also flow through the provider's `CONFIG_FIELDS` per the `tickets` note below; that's a fourth touch-point for ticket settings specifically.)

### `tickets` config — the one provider selector (replaced the `use_linear` bool)

`tickets` is an **object** with self-describing fields — `{provider: none|linear|github|jira|trello, close_on_merge: bool}` plus, for Linear, `keys: [<team-prefix>]` / `project` / `dev_done_state` / `merge_done_state`, for GitHub, `dev_done_label: <label>` (default `"ready for review"`), for Jira, `keys: [<project-key>]` (the *same* field Linear declares, meaning the same thing — see the routing paragraph) / `site_url` / `email` / `dev_done_status` (default `"Dev Done"`) / `merge_done_status` (default `"Done"`), and for Trello, `board` (routing-only, no default) / `dev_done_list` / `merge_done_list` (the latter two **no default** — a Trello card lives in a *list* / board column with an arbitrary name, so an unset list leaves that feature inert). Every provider credential is **env-only** — config carries the env var's *name*, never its value: `api_key_env` (linear, default `LINEAR_API_KEY`), `token_env` (jira → `JIRA_API_TOKEN`, trello → `TRELLO_API_TOKEN`), `key_env` (trello → `TRELLO_API_KEY`). The bare string `"tickets": "github"` is shorthand for `{provider: github}` (defaults elsewhere). The field *names* carry the meaning — `dev_done_label` is a GitHub issue label, `dev_done_state` is a Linear workflow-state name — so a reader (and cockpit) never has to infer it from the provider. Fields resolve **per-field** repo-block → global-block → default (`config.py::_tickets_field`), so a global `tickets.close_on_merge` (or any field) applies to a repo whose own block omits it — a repo block doesn't have to repeat shared settings. GitHub also has `start_label` (opt-in): when `spawn.py` creates a worktree on a `gh-issue` source, it marks the issue "work started" via `gh issue edit --add-label` (`github_issues.add_label`, `config.github_start_label`) — the one *spawn-time* tracker write, best-effort (a failed label never blocks the spawn), distinct from the slow-tick `close_on_merge` write. Resolved per-repo over global by `config.py::_tickets_block` (the repo entry's whole `tickets` block wins outright); `tickets()` is the global provider, `repo_tickets(cfg, repo_entry)` the per-repo one. The provider selects: the spawn fetch/rename prompt, the `devdone=` pill, the done-on-merge writer, and the TUI ticket columns all gate on `repo_tickets(...)`. `use_linear` is **gone** — preflight (`_validate_tickets`) hard-fails on a leftover key. Back-compat: a repo with the legacy flat `linear_keys` but no `tickets` resolves to `"linear"`, and the legacy flat `linear_keys` / `linear_dev_done_state` / `linear_done_on_merge` / `linear_merge_done_state` keys are still honored as fallbacks (the `tickets` block's `keys` / `dev_done_state` / `close_on_merge` / `merge_done_state` take precedence), so existing Linear configs keep working untouched. `linear_team_keys(cfg, repo_entry)` is the reader for the identifier prefixes (`tickets.keys` → legacy `linear_keys`) — Linear-*named* but provider-neutral in substance, since Jira declares `keys` too; a reader that means "this repo is Linear" must therefore pair it with the resolved provider (`preflight._validate_linear_dev_done` does, else every Jira repo gets warned about an unset `LINEAR_API_KEY`). `cockpit.lib.tickets::provider_for(cfg, repo_entry)` → a `TicketProvider` (or None) is the **single source of truth** mapping the provider onto its strategy (`dev_done_value(cfg, repo_entry)`, `parse_footers`, `fetch_states`, `fetch_titles`, `narrow_repos`); `cycle.py` calls the strategy instead of sprinkling `provider == "github" ? … : …` ternaries. **Do not** re-introduce those ternaries — add a `TicketProvider` field. Settings readers (`ticket_close_on_merge`, `github_dev_done_label`, `linear_*_state`, `linear_team_keys`) source via `_tickets_field`; **do not** add a new top-level `github_*` flat key — extend the `tickets` object. The accepted-field *schema* is owned by each provider — `linear.py` / `github_issues.py` / `jira.py` export `CONFIG_FIELDS` (`(name, kind)` pairs), `tickets.py` composes them with the common fields and validates via `tickets_field_errors` (which also rejects a field that belongs to *another* provider), and `preflight._validate_tickets` just delegates. **Add a new ticket setting** by adding it to the provider's `CONFIG_FIELDS` + a reader in `config.py` — not by editing a hardcoded list in preflight. Note two field names are declared by **two** providers each — `token_env` (jira and trello) and `keys` (linear and jira): `tickets_field_errors` composes the allowed set from the *active* provider only, so a shared name validates under either of its owners and still fails under the others — **do not** flatten the per-provider schemas into one merged dict.

**Ticket→repo routing is two-stage: a free match, then a paid tiebreak.** `cockpit new PE-1234` picks its repo from the identifier alone — `config.find_repos_by_ticket_key` over `tickets.keys` — which is pure, offline, and enough whenever one repo owns the team. It isn't enough in the many-repos-one-team shape: every member declares the same `keys`, so the id matches them all, and the old behaviour (warn, fall back to cwd discovery) silently lands the worktree in whichever repo you happened to be standing in — a *wrong* answer, not a missing one. The discriminator is `tickets.project`, and a Linear identifier names its **team, never its project**, so resolving it costs a GraphQL fetch. Hence the seam: `TicketProvider.narrow_repos(ref, candidates, cfg)`, called by `spawn.py` **only when the free match already returned >1** — the single-match route stays network-free and a config without `project` is byte-identical to before. Three rules: it **never narrows to zero** (no candidate configures a project, the fetch fails, or the resolved project matches nobody → return `candidates` unchanged, so the caller's existing ambiguity path still runs); it groups candidates by **resolved credential** (`linear_api_key_env`, which already walks repo → org → global → default, since `apply_org_defaults` merged the org rung in at `load_config` time) and asks each group with its own key — a team key is *workspace*-scoped, so two orgs can each own an `ENG` team and both match `ENG-1234`, and asking one org's workspace about the other's ticket answers about a **different issue that merely shares an identifier**, which mis-routes the spawn; a project name is therefore only ever matched against repos in the group whose key returned it, groups are tried in config order, first confident hit wins, and a group whose credential is unset is skipped (it can't be asked). That keeps the ordinary single-workspace case at exactly one fetch — extra round-trips appear only when the candidates genuinely span workspaces, which is the only way to answer correctly. **Do not** collapse this back to one key read off `candidates[0]`. Finally it is **routing-only** — no cell, no pill, no decision downstream reads `project` (or Trello's `board`).

**Both stages are provider-shaped, and `spawn.py` must not branch on a provider name to pick them.** Stage two is `narrow_repos`; stage one is whatever the caller can match for free, and `spawn._route_by_ticket(ref, candidates, cfg)` is the one shared tail (narrow only when >1, single survivor wins, >1 prints the ambiguity note and falls back to cwd discovery) both call sites hand their candidates to. Per provider:

- **Linear** — free match `tickets.keys`; tiebreak `tickets.project` (`_linear_narrow_repos`), as above.
- **Jira** — free match `tickets.keys`, the **same field and the same reader** (`linear_team_keys`, Linear-named but provider-neutral in substance): a Jira *project key* IS the identifier prefix, i.e. the analogue of a Linear **team**, not of a Linear project. So Jira declares `keys` in its `CONFIG_FIELDS` and stays `_no_narrow` — **do not** give it a `project` field, and **do not** duplicate `find_repos_by_ticket_key`. The `mode == "linear"` spawn branch runs the lookup for both (Jira keys share Linear's `[A-Z]{2,6}-\d+` shape, so `detect_source` classifies them alike), gated on `provider_for(cfg) is not None` rather than a provider-name test, so `tickets: none` still routes nothing. **The shape gate stays `LINEAR_RE_CI`** — it is `detect_source`'s classifier, so widening it only in `find_repos_by_ticket_key` would be a no-op, and widening it for real reclassifies plain branch names like `feature2-1` as tickets; a Jira key with digits or >6 letters therefore doesn't route (documented `ponytail:` in both places), which is the accepted ceiling until someone hits it.
- **Trello** — **no free match at all**: a card short link (`trello.com/c/aB3xY`) carries no board, no project, no prefix. So the opt-in *is* the discriminator — stage one is "the configured repos that declare a `tickets.board`", and `_trello_narrow_repos` resolves the card's board with one `fetch_card_board`. With no repo declaring a board the candidate set is empty and `cockpit new <card-url>` makes **zero** network calls and routes exactly as before; with one, it routes free (same as a single `keys` match); only ≥2 pays. It mirrors `_linear_narrow_repos`'s three properties exactly, including grouping by **resolved credential** — Trello's is a key+token *pair* (`trello_key_env` + `trello_token_env`), and a board name is *account*-scoped just as a team key is workspace-scoped, so asking one org's account about another's card answers about a different card or 404s.
- **GitHub** — needs neither stage (a `owner/repo#N` ref carries its repo, so `find_repo_by_nwo` never reaches an ambiguous set). `_no_narrow`.

**Per-org credentials come free from the env-*name* indirection.** `config.py` has a name reader + a value resolver per credential (`linear_api_key_env`/`linear_api_key`, `jira_token_env`/`jira_api_token`, `trello_key_env`+`trello_token_env`/`trello_api_key`+`trello_api_token`); the name reader is just another `_tickets_field` call, so it resolves repo → org → global → default and an `orgs: {acme: {tickets: {api_key_env: "LINEAR_API_KEY_ACME"}}}` block covers every member repo with **no** org-aware machinery (see the `orgs` invariant — nothing below `load_config` knows orgs exist). Every call site resolves the *value* per repo and threads it into the leaf (`fetch_ticket_states(…, api_key=…)`, `jira.*(token=…)`, `trello.*(key=…, token=…)`) instead of relying on the leaf's env fallback, which stays only for back-compat. Two rules:

- **The identity caches key on the resolved secret, not the env var name** (`cycle.py::_secret_fingerprint` — sha256[:12] of the value, plus the site/email for Jira). They used to be single-slot on a fingerprint of the one global env var, so with per-org keys org B would read org A's cached viewer id and then silently skip *every* ticket (the viewer gate can never match a foreign id). Same for the Trello key+token pair. `_cached_team_states` still keys on the team UUID alone (globally unique), but takes the api_key for its fetch. The TTL and the never-cache-a-falsy-identity rule are unchanged.
- **Spawned sessions never receive ticket credentials.** `_bg_spawn_pr` passes `env=` os.environ minus `config.credential_env_names(cfg)` — the union of every resolved name across the global block, all repos and all orgs, plus the four defaults. Spawn-time ticket fetch is MCP-delegated (the Linear/Jira/Trello connectors), so an agent has no use for the REST keys, and a `review_prs` session runs over a coworker's untrusted PR body/diff. Strip by *resolved name*, never a `LINEAR_*` prefix guess, and touch nothing else in the env (`PATH`, `COCKPIT_HOME`, `CMUX_*` must pass through or spawning breaks). Preflight's soft warnings name each repo's resolved variable (`_unset_linear_key_envs`) — a warning, log line, or error message carries an env var **name**, never a value.

### `devdone=` pill — the ticket provider is the one auxiliary (read-only) state source

Gated on `repo_tickets(...) != "none"` + a PR-body delivery footer. Delivery is **footer-only** (`provider.parse_footers`): Linear → `Linear: [PE-1234](url)` (`lib.linear.parse_linear_footers`); GitHub → a closing keyword `Closes #123` / `Fixes owner/repo#45` (`lib.github_issues.parse_github_issue_refs`); Jira → `Jira: [PROJ-123](url)` (`lib.jira.parse_jira_footers`, the same strict line-anchored footer as Linear); Trello → `Trello: [title](https://trello.com/c/<shortLink>)` (`lib.trello.parse_trello_footers`, the delivered card's short link) — never a branch-slug or a bare mention, which catch non-delivered tickets (same strict signal as `morning-align`'s `linear_delivery.py`). The `{provider, tickets, fetched_at}` block — each ticket `{id, state, title}`, plus the resolving `provider` name so the block is self-describing (a downstream reader picks Trello's title-over-short-link handle via `cache.ticket_display` without re-reading config; the statusline `pr-ticket` pill and TUI Ticket cell both route through it) — is cached in the PR JSON under the `ticket` key (renamed from the legacy `linear` key, no back-compat: an old on-disk cache blips its `devdone=` pill off for one slow cycle until rewritten, and a provider-less block falls back to the raw id for that cycle); `cycle.py::_prefetch_linear_blocks` decides refetch-vs-carry-forward per PR (`_decide_linear_refetch`: footer-id change or past `linear_state_ttl_seconds`) reading the *prior* snapshot via `ctx.pr_payloads`, then resolves the union of due ids across *all* a repo's PRs via `provider.fetch_states` (Linear: one **batched** GraphQL query per team; GitHub: one `gh issue view` per issue — an issue carrying the dev-done label `github_dev_done_label` (default `"ready for review"`, via `tickets.dev_done_label`) maps to that label so the comparison stays provider-neutral; Trello: one `GET /cards/{id}?list=true` per card resolving its current list name — `lib.trello.fetch_card_lists`). The `title` is a parallel provider-neutral enrichment (`provider.fetch_titles` → `_fetch_ticket_titles`, one fetch per provider on build, carried forward on carry) — the human ticket name a statusline consumer like cship reads from the cache without its own API round-trip; it never feeds a cockpit decision (dev-done keys off `state` only). It runs once before the write loop so each `write_pr_cache` still overwrites against the old file. `_track_dev_done` raises the pill (`apply_devdone_pill`) only when *every* delivered ticket equals `provider.dev_done_value(cfg, repo_entry)` (Linear's `dev_done`/"Dev Done" state / GitHub's primary accepted label / Trello's `dev_done_list` name, casefolded). Passive, never a `send`, absent from `ACTIONABLE_KEYS`. **Do not** drop back to a per-PR fetch fan-out; keep the Linear union batched. A per-source query failure isolates to its own ids (they stay None) — never blanks unrelated tickets.

### done-on-merge — the daemon's only sanctioned tracker *writes*, dispatched per provider

Opt-in (default false, per-repo) via the shared `tickets.close_on_merge` (`config.py::ticket_close_on_merge`, legacy `linear_done_on_merge` flat key honored as fallback). Slow-tick `cycle.py::_transition_merged_tickets` dispatches on `provider.name` to one writer, each fired on `_is_post_merge_stale` independently of teardown (ship even when the worktree is held back), each guarded by a per-run `merged-done:…` marker in `pill_state`, each viewer-gated (never touch a teammate's ticket), each idempotent + logged:

- **Linear** (`_transition_merged_linear`, gated `ticket_close_on_merge` + `linear_team_keys` + a resolved `linear_api_key` (the env var named by `tickets.api_key_env`)): moves the ticket to `linear_merge_done_state` (`tickets.merge_done_state`, default "Done", distinct from `dev_done_state`) via `update_ticket_state` → `issueUpdate`. Per ticket: skip unless assigned to the API-key `viewer`; skip if already at target or `type: canceled` (note "Dev Done"/"Done" are both `completed`, so name-equality decides); else resolve the target UUID (`fetch_team_states`) and mutate. The `viewer` id + per-team state maps are cached across ticks (`_cached_viewer_id`/`_cached_team_states`, TTL `linear_identity_ttl_seconds`; viewer key is a non-secret fingerprint of the *resolved* key, so per-org credentials keep separate slots); the `viewer` fetch is **lazy** (first eligible ticket only).
- **GitHub** (`_transition_merged_github`, gated `ticket_close_on_merge`): runs `gh issue close` on each delivered issue still open and assigned to the `gh` auth login (`github_viewer_login`, cached via `_cached_github_viewer`). GitHub auto-closes same-repo closing-keyword refs on merge, so this mainly catches cross-repo refs and label-only links.
- **Jira** (`_transition_merged_jira`, gated `ticket_close_on_merge` + `tickets.site_url`/`email` + a resolved `jira_api_token` (`tickets.token_env`)): transitions each delivered issue to `jira_merge_done_status` (`tickets.merge_done_status`, default "Done") via the REST transitions API (Jira moves issues by *transition*, not a direct status set — GET available transitions, match the target status name, POST). Per issue: skip unless assigned to the auth user (`fetch_myself` accountId, cached via `_cached_jira_viewer` keyed on a fingerprint of the resolved token + site + email); skip if already at target. Spawn fetch is MCP-delegated (Atlassian connector); the daemon's REST is Basic-auth `base64(email:token)`.
- **Trello** (`_transition_merged_trello`, gated `ticket_close_on_merge` + `tickets.merge_done_list` set + a resolved `trello_api_key`/`trello_api_token` (`tickets.key_env`/`token_env`)): moves each delivered card to the list named `merge_done_list` (no default — an unset list leaves the move off) via `lib.trello.move_card` (resolve the card's board, match the target list name on it, PUT the new `idList`). Per card: skip unless I'm a member (`fetch_myself` member id, cached via `_cached_trello_viewer` keyed on a fingerprint of the resolved key+token); skip if already on the target list. Spawn fetch is MCP-delegated (Trello connector); the daemon's REST is key+token query-auth.

A falsy/failed identity fetch is never cached (retries next tick); a failed write clears the marker to retry. **Precedent for any future daemon tracker write:** opt-in, viewer-gated, idempotent, logged.

## Dev setup and common commands

```bash
# One-time after cloning — wires pre-commit hooks for commit + push stages:
./setup.sh

# Run the test suite (also runs on pre-push via pre-commit):
pytest

# Type-check:
mypy cockpit/

# Lint + format — ALWAYS via the pinned pre-commit hook, scoped to your files:
pre-commit run ruff ruff-format --files <changed paths>
```

**Never lint/format with `uvx ruff` (or a globally-installed `ruff`).** `uvx`
pulls the **latest** ruff, whose rules drift from the version pinned in
`.pre-commit-config.yaml` — running it (especially tree-wide, `ruff format
cockpit/ tests/`) rewrites pre-existing lines in files you never touched to the
newer style, producing unrelated churn that the pinned pre-commit hook then
fights on commit. Bare `ruff` isn't installed here on purpose; the pinned hook
*is* the formatter, and it's what CI enforces. Format only your changed paths
with `pre-commit run ... --files`, not the whole tree.

## Release versioning

The version is **static** in `pyproject.toml` (`[project] version = "..."`), read at runtime via `importlib.metadata` (`version.running_version`, surfaced by `cockpit --version`). There is no self-update path. `ci.yml` skips only `no-commit-to-branch` (local-dev-only).

**Every merge to `main` that ships user-visible behaviour gets a release** — brew is the only delivery path, so an unreleased merge reaches nobody. The semver bump is derived from the conventional-commit types on `main` (`feat` → minor, `fix` → patch), which `pr-title.yml` already enforces on every squash subject.

**The release PR writes itself.** `.github/workflows/release-please.yml` (`googleapis/release-please-action@v4`) keeps one rolling `chore(main): release <version>` PR open, accumulating every conventional commit merged since the last release and maintaining `CHANGELOG.md`. **Merging that PR is the only human step in a release** — it bumps `[project] version`, which is the trigger `tag.yml` watches, so tag → tap → PyPI all follow on their own. Several merges therefore batch into one release rather than cutting a version each, which matters because PyPI refuses a re-upload of a version.

Two settings in that workflow are load-bearing, both for the same GitHub recursion rule that shaped `tag.yml`:

- **`skip-github-release: true`** — left to default, release-please pushes the tag and cuts the GitHub release itself, duplicating `tag.yml` *and* doing it under a token whose pushes don't trigger workflows, so `release.yml`/`publish.yml` would silently never run. `tag.yml` stays the only tagger; release-please only ever writes the PR.
- **`token: COCKPIT_GITHUB_API_TOKEN`** — a PR opened by the default `GITHUB_TOKEN` doesn't trigger workflows, so the release PR would sit forever with none of `main`'s required checks reporting and could never be merged.

State lives in `release-please-config.json` (release type `python`, which updates PEP 621 `[project] version`) and `.release-please-manifest.json` (the last released version — the one file to correct by hand if a release is ever cut out of band).

`CHANGELOG.md` is **release-please's file** from 1.8.0 on — don't hand-edit it. It's excluded from `markdownlint` in `.pre-commit-config.yaml` because release-please writes `*` bullets into a file that was hand-written with `-` ones, and MD004 would fail every release PR.

**`include-component-in-tag: false` is required, not cosmetic.** Left at its default (`true`), release-please names tags `cockpit-v<version>` while `tag.yml` pushes `v<version>` — so it can't find the previous release, treats the repo as never released, and regenerates `CHANGELOG.md` from the entire history (203 entries on the first run, with compare links to tags that don't exist). The tag format has to match `tag.yml`'s even though `skip-github-release` means release-please never pushes one.

`./cut-release.sh <version>` is the **manual fallback**, for when the action is broken or a version has to be forced: it bumps `[project] version`, commits `chore(release): <version>`, opens the PR, and merges it `--squash --admin` (confirming first unless passed `-y`). It refuses a dirty tree, a non-semver argument, `main`/`master`, and a bump to the version already in `pyproject.toml`. Its guard paths are covered by `tests/test_cut_release.py`; the happy path ends in a real merge and is deliberately untested. Using it means `.release-please-manifest.json` must be updated to match, or release-please will propose a bump from the stale baseline.

`.github/workflows/tag.yml` watches `pyproject.toml` on `main`: when the bump lands it reads the new version and pushes `v<version>` at that merge commit (a no-op if the tag already exists, so an unrelated `pyproject.toml` edit does nothing). That tag then fires `release.yml` + `publish.yml`. It pushes with **`COCKPIT_GITHUB_API_TOKEN`, not the default `GITHUB_TOKEN`** — a ref pushed by `GITHUB_TOKEN` doesn't trigger other workflows, so the two downstream jobs would silently never run; the PAT consequently needs `Contents: write` on **this** repo as well as on the tap. Hand-tagging (`git tag v<version> origin/main && git push origin v<version>` on a fetched `origin/main`, never the pre-merge branch tip) still works and is the fallback if the PAT lapses.

The tag must point at a tree whose `pyproject.toml` version equals the tag (minus the `v`) — **both** `release.yml` and `publish.yml` re-read `pyproject.toml` at the tag as their first step and hard-fail on a mismatch, which is what hand-tagging the un-merged branch tip or forgetting the bump trips. The `publish.yml` guard matters most: PyPI refuses a re-upload of a version, so a wrong-versioned wheel there is unrecoverable. On success it hands `mislav/bump-homebrew-formula-action` the tag tarball URL; the action computes the sha256 and **commits the new `url`+`sha256` straight onto `khivi/homebrew-cockpit`'s `main`**, so `brew upgrade cockpit` picks it up with no PR to merge. It authenticates with `COCKPIT_GITHUB_API_TOKEN` (the default `GITHUB_TOKEN` can't reach another repo); `Contents: write` on the tap is all it needs. **`create-branch: false` in `release.yml` is what makes that direct commit happen, and removing it re-breaks releases silently** — the action's `needsBranch` is `inFork || <base branch>.protected || makePR`, and the tap's `main` carries a ruleset so GitHub always reports it `protected: true`. Left to default it therefore branches, then `POST /pulls` 403s (`Resource not accessible by personal access token`) *after* pushing a correct-looking `update-cockpit.rb-<n>` branch — the v1.5.1 and v1.6.0 failure mode, where both tags and both formulas were right and neither reached the tap until a human opened the PR. The tap ruleset only forbids `deletion` + `non_fast_forward`, so the direct commit is permitted. When a release job fails, **check the tap for an orphaned `update-cockpit.rb-*` branch before re-cutting anything** — a leftover branch means the PR fallback ran, i.e. `create-branch: false` went missing. The formula's `resource` blocks are **not** touched — regenerate them by hand on a dependency bump (`brew update-python-resources Formula/cockpit.rb`).

## Commit / PR-title convention

We squash-merge, so the **PR title** becomes the squash commit subject on `main` (the `type(scope): summary (#N)` lines in `git log`). Use [Conventional Commits](https://www.conventionalcommits.org/) for the PR title: `feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert`, optional scope. Local WIP commit messages are unconstrained — they get squashed away.

Enforced by `.github/workflows/pr-title.yml` (`amannn/action-semantic-pull-request`, commitlint's `config-conventional` ruleset) as the required `lint-pr-title` status check on `main`. It runs alone (not in `ci.yml`) so a title edit re-checks the title without re-triggering pytest/mypy.

`main` is guarded by **two** stacked mechanisms, and the second is why a plain `gh pr merge` reports "the base branch policy prohibits the merge" even with everything green: classic **branch protection** requires the `lint-pr-title` + `pre-commit` + `ci` checks, and a **repository ruleset** (`main`, active) additionally requires 1 approving review, code-owner review, resolved threads, and squash-only merges. A solo author can't approve their own PR, so every merge here is `gh pr merge <N> --squash --admin` — admins are exempt from both (`enforce_admins: false`). Check the ruleset with `gh api repos/khivi/cockpit/rulesets`, not just `.../branches/main/protection` — the latter shows the checks but none of the review requirements.

## Test layout

New modules get their own `test_<name>.py` — don't append tests for a new source file to an unrelated test module. Shell hooks under `cockpit/hooks/` are the exception: they live as `tests/test_<hook>.py` with no Python source mirror.

## Test style by layer

- **Leaf modules** (`cockpit/lib/*` wrapping `git`, `gh`, `cmux`, `shutil.which`, `subprocess.run`, etc.) test against the real tool on `tmp_path`. Stubbing the underlying command tests the stub, not the integration.
- **Orchestrators** (`cockpit/orchestrators/*`) compose those leaves. Tests mock collaborator calls (`patch.object(teardown_mod, "remove_worktree", …)`) to assert ordering, guards, and gating without re-validating the leaves underneath.
- **CLI entry-points** (`tests/test_<script>.py` for `cockpit/{cockpit,spawn}.py`, plus `tests/test_cli.py` for the dispatcher) test the argparse / routing layer. Mock at the orchestrator boundary (`patch("cockpit.cockpit.teardown", …)`) or, for the dispatcher, at each module's `main` — the layer below is covered by its own tests, so re-exercising it here adds noise.
- **TUI** (`tests/tui/*`) drive the Textual app headlessly via `App.run_test()`/Pilot (no TTY) with the tick functions and `load_config` injected; card markup is a pure function tested off seeded cache cells. Test the TUI's own scheduling / in-flight gating / log capture, not the reconcile cycle underneath.
- **End-to-end** (`tests/e2e/*`) run the full pipeline against real binaries. No mocking. These are the slowest and most fragile — reserve for genuinely cross-layer behavior (e.g. `cship` + `starship` integration).
