# Privacy & Internal References

This is a public repository. Never include the following in commits, PRs, code comments, or documentation:

- Internal ticket IDs (Linear `ENG-123`, Jira `PROJ-456`, etc.)
- Internal GitHub PR/issue URLs from private repos
- Real names of teammates (use roles instead: "the reviewer", "the on-call engineer")
- Internal Slack channels, wiki URLs, or tool links
- Internal hostnames, service names, or infra identifiers
- Customer names or company-specific identifiers

When writing commit messages or PR descriptions:

- Describe *what* changed and *why*, not which ticket tracks it
- Reference public GitHub issues only (`#123` in this repo)
- If context requires an internal ticket, summarize the requirement instead of linking

Before committing, scan for cases gitleaks can't catch:

- Your team's real ticket prefixes (e.g. `ENG-123`, `LIN-456`)
- `@firstname` references that aren't GitHub handles

## Worktree discipline

Always use a dedicated git worktree for any code change. Never commit directly to `main`/`master` in the primary checkout, and never make in-place edits on a feature branch without a dedicated sibling worktree.

**Why**: The cmux + cockpit workflow keys off the one-worktree-per-branch invariant. In-place edits on the primary checkout pollute its `main` (which must always equal `origin/main`) and break PR-tracking — cockpit derives per-branch state from `git worktree list` and misattributes or drops cells for any branch not isolated in its own worktree.

**How to apply**: Before any Edit or Write, run `git branch --show-current` and `git worktree list`. If HEAD is `main`/`master`, or if the working-tree path is the primary checkout (first entry in `git worktree list`), stop and spawn a worktree via `cockpit new` before touching any file. If HEAD is already a non-main branch in a sibling worktree (not the first entry), proceed — do **not** spawn another worktree.

## Architecture notes

**How to read this (you're an agent editing this repo).** Each `###` is one invariant: the rule, its enforcing `file::symbol`, and the bug it prevents — obey the **Never** / **Do not** lines, they encode paid-for regressions. This is the *invariant* half of the design; `docs/state-machine.md`'s four Mermaid diagrams are the *control-flow* half. Keep both in sync.

### Keep `docs/state-machine.md` in sync — a stale diagram is worse than none

Four diagrams (orientation map, reconcile decision tree, nudge idle-gate, cell data-flow) map the three state sources (GitHub PR, Claude session, cmux workspace; + auxiliary Linear) onto the decision functions. Any change to those functions (`match_worktrees`, `_spawn_missing_workspaces`, `nudge_if_idle`, `_track_dev_done`, `_maybe_autoclose`), the `cache.py` cell writers, tick cadence, or the spawn/teardown/nudge/devdone/color rules MUST update the matching diagram in the same PR.

### Inventory is derived every cycle, never stored

Each cycle re-reads `git worktree list` and cmux's workspace list (`cmux rpc workspace.list` for cwds, `cmux list-workspaces` for names/refs). Only PR payloads are cached (`~/.config/cockpit/cache/<repo>__pr-<N>.json`, a network round-trip). **Never** add a stored identity file — cached-vs-real drift is the bug class this avoids.

### Packaged as the `cockpit` console script — invoke by subcommand, never by file path

- **Dispatch:** `[project.scripts] cockpit = cockpit.cli:main` → `cli.py` routes `watch / setup / teardown / statusline / starship / idle-pill / new / close / nudge` to each module's `main`, plus a top-level `--version`. `watch`/`setup` → `cockpit.cockpit` as `--watch`/`--setup`; `setup` re-wires the statusLine + Claude hooks without starting the daemon. **Add entry points as `cockpit <sub>` in `cli.py`**, not file-path invocations.
- **`teardown`** → `config.teardown_claude_integration`, the inverse of `setup`'s `~/.claude` writes. Run it *before* `brew uninstall` — brew removes only the Cellar binary, leaving the settings.json hooks/statusLine dangling at a now-missing `cockpit`.
- **Distribution:** a **brew formula** whose single source of truth is the tap repo `khivi/homebrew-cockpit` (`Formula/cockpit.rb`; `brew tap khivi/cockpit && brew install cockpit`, macOS + Linuxbrew) — **not** vendored back here (a copy would drift). The release CI (`.github/workflows/release.yml`) bumps the tap's `url`+`sha256` on every `v*` tag. There is **no** Claude Code plugin, marketplace, or self-update path (brew owns updates).
- **Version:** static in `pyproject.toml`, read at runtime via `importlib.metadata` (`version.running_version`). Must be installed on PATH; `preflight._warn_cockpit_not_on_path` soft-warns, never hard-fails.
- **Claude footprint** — three idempotent writes, all made by `cockpit setup`: two `~/.claude/settings.json` entries (the statusLine command + the idle-pill hooks, via `config.install_cship_statusline_if_configured` + `config.install_claude_hooks`) and three files under `~/.claude/commands/` (`config.install_claude_commands`). **`_COCKPIT_HOOKS` is exactly two hooks** — `Stop` → `cockpit idle-pill stop`, `UserPromptSubmit` → `cockpit idle-pill prompt`, both off PATH — because those are the only two with a reader: `nudge_if_idle`'s `idle=` gate. Two families were removed and **must not come back without a reader to point at**. (a) `Stop` → `cockpit statusline`: that command is `statusline.py::main`, and a *Stop* payload carries no `model`/`context_window`/`cost`/`rate_limits`, so of the six cells `lib.claude.stash_from_stdin` writes it reached only `transcript-path` — which the statusLine command already writes on every render — while paying a full cship + starship + `starship.py`×8 render whose stdout Claude Code discards. (b) the three `loop=` hooks (`PreToolUse(ScheduleWakeup|CronCreate|CronUpdate)` → loop-set, `PreToolUse(CronDelete)` / `SessionEnd` → loop-clear): **nothing ever read that pill** — `nudge_if_idle` gates on native `Running`, `idle=` and `parked=` only, so the hooks bought a cmux badge and no behaviour. /loop suppression is unaffected because it never lived there: it is the Stop handler *withholding* `idle=` when the last turn armed a wakeup (`cmux-idle-pill.sh`). Consequently `install_claude_hooks`' drop pass sweeps **every event in the file**, not just `_COCKPIT_HOOKS`' own — a retired hook lives under an event the template no longer names (`PreToolUse`, `SessionEnd`), so iterating the template alone would strand it in the user's settings forever; an event left with no groups is deleted rather than emptied. `_COCKPIT_HOOK_CMD_RE` keeps matching `statusline` for the same reason: that is how an older install's Stop entry gets cleaned out. `cockpit watch` re-asserts on startup (`claude_integration_present` → `install_claude_hooks`), so the sweep reaches an upgraded install without a manual `cockpit setup` — on the next daemon **restart**, not mid-run.
- **`{python}` pin:** generated starship configs use `{python} -m cockpit.cli <sub>` (resolves off-PATH in starship's render env); `{python}` is `sys.executable` pinned at `cockpit setup` time. **Never run setup from inside a worktree venv** (`uv run cockpit setup`) — it bakes the worktree's ephemeral `.venv/bin/python`, which dies on cleanup (the "footer disappeared" bug); re-run `cockpit setup` through the brew-installed console script to re-pin.
- **Pin self-heals on upgrade:** a `brew upgrade` also staleness-breaks the pin (the Cellar libexec path is *versioned*, so the old interpreter vanishes), so `cockpit watch` re-pins on startup via `config.repin_interpreter_if_stale` — a **surgical** rewrite of only the interpreter prefix of `<interp> -m cockpit.cli …` in `~/.config/starship.toml` + the cockpit statusLine, preserving user colour/format edits (unlike `install_starship_default_config`, which re-seeds the whole file). Startup-only: a *running* daemon's `sys.executable` is still the removed path until restart, so a per-tick re-pin couldn't see the new interpreter. So running the daemon after an upgrade needs no manual `cockpit setup`.
- **idle-pill hook:** lives at `cockpit/hooks/cmux-idle-pill.sh` (inside the package, so it ships in the wheel), reached via the `idle-pill` subcommand, which `bash`-execs it (no reliance on the wheel preserving the exec bit).

**Slash commands are user commands, not a plugin.** `cockpit/claude_commands/{cockpit-new,cockpit-close,cockpit-broadcast}.md` (a package data dir with an `__init__.py`, same shape as `cockpit/prompts/`) are thin wrappers that just run `cockpit new $ARGUMENTS` / `cockpit close $ARGUMENTS` / `cockpit broadcast "$ARGUMENTS"`; `/cockpit:review` is not resurrected — it's the built-in `/review` now. **A command template documents the CLI, it never reimplements it** — the broadcast one carries the two things `cockpit broadcast --help` can't say (prefer `--dry` before an unconfirmed message; a leading `/` opens Claude Code's autocomplete in the target composer and the trailing `enter` submits whatever is *highlighted*, so smoke-test a slash command by hand in one workspace before fanning out) and otherwise defers to the subcommand for the fan-out and the idle gate. Its message is a **single positional**, so the wrapper quotes `$ARGUMENTS` — unlike `new`/`close`, whose arguments are flags. The new one carries the same kind of thing: `cockpit new --context` takes an **optional** value (`nargs="?"`), and the bare form means *"summarize this session"* — a job no CLI can do, so the template tells the calling agent to write the summary and substitute it in as the flag's value. `parse_args` **errors** on a bare `--context` (empty `const` sentinel) rather than defaulting to no context: an unexpanded flag reaching the CLI means the substitution didn't happen, and silently spawning a workspace that inherits nothing is the bug that hides. **Do not** teach the CLI to synthesize its own context — the split is the point. `install_claude_commands` (`cockpit/lib/config.py`, called from `cockpit setup` right after `install_claude_hooks`) reads them via `importlib.resources` (same mechanism as `cockpit.lib.templates`, so it works from the installed wheel) and copies them verbatim into `~/.claude/commands/`, backing up an existing file only when its content changes and leaving unrelated user commands untouched. **They install as flat, hyphenated files (`cockpit-new.md` / `cockpit-close.md` / `cockpit-broadcast.md` → `/cockpit-new` / `/cockpit-close` / `/cockpit-broadcast`), not a `cockpit/` subdirectory** — Claude Code's `.claude/commands/` convention names a command from its filename only (`deploy.md` → `/deploy`); the `plugin-name:command` colon-namespacing (`/cockpit:new`) is a plugin-only mechanism keyed off the plugin name, and cockpit isn't a plugin. `uninstall_claude_commands` is the inverse (removes only the bundled files, called from `teardown_claude_integration` alongside `uninstall_claude_hooks`). `tests/e2e/test_wheel_packaging.py` asserts the three `.md` files ride in the built wheel, same as the idle-pill hook script — and, as with `cockpit/prompts/*.txt`, hatchling ships only **VCS-tracked** files, so a new command template must be `git add`ed or `importlib.resources` `FileNotFoundError`s on the installed daemon.

### `cockpit watch` is a Textual TUI, and the TUI *is* the daemon (`cockpit/tui/`)

- **No headless mode:** non-TTY `watch` exits 2. The app owns the pidfile (`daemon.claim_pidfile`/`release_pidfile`), claimed once before the TUI starts. **Pidfile self-heal:** `claim_pidfile` runs exactly once at startup; if the pidfile is later lost mid-run (a racing stale-cleanup in `kick_running`/`claim_pidfile`, or an external `rm`), nothing would otherwise rewrite it and every `cockpit close`/spawn kick reports "no daemon" for the rest of the process's life (they key off `PID_FILE.exists()` alone). The fast tick calls `daemon.reassert_pidfile` to rewrite it when missing/stale (idempotent, never clobbers a *different* live daemon's pidfile), so a lost pidfile recovers in ~30s — the same self-heal pattern as the name/colour/`idle=` re-asserts. **The reclaim must re-create the state *directory*, not just the file** (`daemon._reclaim`): a wipe that takes all of `$COCKPIT_HOME` (one under a swept tmpdir — the very case this heals) makes the read raise `FileNotFoundError`, which is an `OSError`, so the reclaim branch catches it and then the recovery write raises the same error **uncaught**, killing the fast tick instead of healing it. Only the two drift paths pay the `mkdir`; the already-ours path stays syscall-free. It is deliberately not `ensure_state_dirs()` — that also seeds a `config.json`, which is startup's job.
- **Ticks:** slow + fast run in `@work(thread=True)` workers; bodies (`cockpit.cockpit._once_with`/`_fast_tick`) are lock-free, serialized by the app's `_tick_lock` acquired *inside* the worker (blocked → `waiting`, holds → `running`). Startup is slow-first — `_start_fast` only after the first slow completes, so the first republish isn't a no-op vs empty caches.
- **Per-repo table republish:** `cycle_all` writes each repo's cells before fetching the next, so the slow tick hands it an `on_repo_done` hook (`_run_slow` → `_publish_inventory`, the same git+cells read its `finally` runs) fired after each repo — a finished repo surfaces in the table while later repos still round-trip `gh`, instead of all repos landing at once on tick end. The hook is a pure read (`_gather_inventory` + `call_from_thread(_render_table)`); a failing callback is logged and never aborts the remaining repos. **Never** let `on_repo_done` write a cell — only the daemon writes; this is a renderer refresh.
- **Signals:** `loop.add_signal_handler` only (SIGUSR1 → slow kick; SIGTERM/SIGHUP → clean exit). **Never** `signal.signal` — it raises off the main thread.
- **Table is read-only** (`worktree_table.py`, keyed by worktree path; worktrees are grouped under a per-repo group-header row — `HEADER_KEY_PREFIX`, a NUL-led sentinel key that can't collide with a path — with `sidebar_color` tinting both the header and the row labels; no `repo/label` collision prefix and no repo column. **The header and its rows share the Workspace column, so the hierarchy is carried entirely by rendering:** the header is the repo name plus a dim `─` rule filling the column, and every worktree row hangs under it behind `ROW_INDENT` (a stacked row a further `_STACK_INDENT` behind its `└`). Without both, header and row read as siblings. `_RULE_WIDTH` is sized to the *typical* widest row (`ROW_INDENT` + `_STATUS_SLOT` + `_LABEL_MAX` + an ellipsis) and deliberately **not** to the absolute worst case — a stacked row overhangs by exactly its `└` spine (4), and pinning the column four wider on every render for the rows that aren't stacked isn't worth it when Workspace competes with Title for width. `test_a_typical_widest_row_fits_the_header_rule` holds that arithmetic. The status glyph sits in a **fixed-width slot** (`_STATUS_SLOT`) that a glyphless row pays for in blanks (a snoozed row among them): 🔇/🔔 are mutually exclusive but differ in ink width per font, and without the reserved slot a quiet row's label sat three columns left of its belled neighbour's, so the column read ragged. **Do not** drop the padding for the no-glyph case. The Workspace (`_LABEL_MAX`) and Ticket (`_TICKET_MAX`, Trello renders long card *titles* there) cells are ellipsized to keep one long value from starving the trailing Title column; anything a cap truncates **must** stay reachable on that cell's hover tooltip (`row_tooltips`). `current_path()` returns None on a header row so every row action no-ops there, and `current_capabilities()` returns `{HEADER_CAP}` which `FooterBar._skip` reads to hide every row-targeted key; on refresh the cursor auto-skips off a header onto the first worktree row). Reads only daemon-written flat cells (`cache.py::_write_pr_flat_cells`, republished fast): `pr-muted` → 🔇, `pr-nudge` → 🔔 (mute wins — it silences the nudge, so a row can't advertise a bell it won't ring), `pr-snoozed` → the row's membership of the per-repo snoozed fold and **no glyph at all**, while still suppressing the bell exactly as a mute does (see the trailing-folds invariant), `pr-author` → `@login`, `pr-comments` → 💬 count, `pr-base` → the stacked-PR `└` indent (see the stacked-PR invariant). The `pr-nudge` cell is `PR.nudge_issue` — the same actionable-issue value the slow tick's nudge decision reads, so the bell can't disagree with whether a nudge would fire; it clears automatically when the issue resolves (derived, never stored).
- **Row actions** (`f p t d a c C m z n`) live on the app, and — except `n` and `f` (which can spawn a workspace, *not* a cache cell) and `m`/`z` (which re-stamp their own pref, see `_repaint_pref` below) — never touch cmux/the cache. The **footer help text** is gated on three axes: (1) the resolved **backend** (`FooterBar.BACKEND_ACTIONS`, fed `resolve_tool()` at compose): `a`/Ask and `d`/Diff are cmux-only verbs so their hints hide on limux/none; `f`/Focus works on cmux **and** limux (both can spawn — focus is the cmux-only bonus) and hides only on `none` (no backend to spawn into); (2) **workspace presence** — `a`/Ask reaches an *existing* session so its hint shows only when the row **has** one (`ACTION_REQUIRES["ask_row"] = "workspace"`), except on a repo header where it addresses the whole repo; `f`/Focus is **not** workspace-gated — it focuses an existing session or spawns one first, so it shows on any backed row (the old `w`/Open key and its `ACTION_FORBIDS` gate are gone — `f` absorbed the spawn); and (3) the **highlighted row's content** (`FooterBar.ACTION_REQUIRES`, fed `WorktreeTable.current_capabilities()` via `app._refresh_footer_caps` on every row-highlight and table refresh): `p`/Open-PR + `m`/Mute + `z`/Snooze hide on a row with no PR, `t`/Ticket hides on a row with no delivered ticket, `m` reads **Unmute** when the row's PR is muted, and `z` reads **Wake** when it is snoozed / **Expand**–**Collapse** on a snoozed *fold* row (`SNOOZED_CAP`, which also suppresses every other row key there — see the trailing-folds invariant). `c`/`C` further hide on a **workspace-only primary checkout with no workspace** (`primary` cap without `workspace`) — its only close is workspace-only, pointless with nothing to close. Row caps are `{pr, ticket, muted, snoozed, workspace, primary}` tokens: `pr`/`ticket`/`muted`/`snoozed` read from the same daemon-written cells the cells render from (`row_capabilities`: `pr-num`, `pr-muted`, `pr-snoozed`, the cached delivery block) — never a network call; `workspace` reflects live backend state via a **single `workspace_cwds()` read per inventory refresh** (`app._live_workspace_paths`, degrades to empty on backend absence), cached into the row caps so per-keystroke footer gating stays a pure set lookup; `primary` is `wt.is_primary and wt.branch in MAIN_BRANCHES` — a `use_worktree: false` primary checkout sitting on its **default branch**, whose close is workspace-only. A primary checkout parked on a **feature** branch does **not** get the `primary` cap: its close tears the branch down (checkout default + `git branch -D`), so `c`/`C` stay advertised even with no workspace, exactly like a feature row. (The `MAIN_BRANCHES` test is a cheap, call-free "on the default branch" heuristic for the footer hint only — a miss never affects teardown's own authoritative `origin_head_branch` guard.) Caps `None` (empty table) shows the full legend, not an empty one. The `t` key is further gated globally by `show_tickets` (some repo has a provider). The actions stay bound and self-guard (pressing a hidden key still warns) — only the advertised hint follows backend + workspace + row state:
  - `f` focus → the single "take me there" verb (the former `w`/open-workspace folded in — focus was just spawn's trailing step). Ensure the row's worktree has a workspace, spawning one (reusing the daemon's `spawn_pr_workspace`/`spawn_orphan_workspace`, PR-payload-reconstructed via `_pr_from_payload`) when missing, then focus it (`cmux focus`). The cwd-keyed `find_cockpit_workspaces` adopts a freshly-spawned workspace next tick (no double-spawn) and `_dedupe_workspaces` reaps a race dupe. **Works on cmux *and* limux** (both can spawn); on cmux it focuses, on limux (no select verb) the user switches via limux's own UI. Reachable on any backed row including a `use_worktree: false` `master`; slow-kicks after a spawn (a pure focus of an existing session does not). **`use_worktree: false` repos** can host several sessions all rooted at the same checkout cwd, so cwd-matching can't single out "the repo's session" — there `f` resolves by **repo name** (`_workspace_ref_by_name`), switching to a workspace named after the repo, falling back to the cwd match, then a spawn. `p` opens the PR URL. `t`/Open-ticket is **provider-neutral** — it routes through the row's `TicketProvider.ticket_url` (`tickets.provider_for`): GitHub builds the issue URL deterministically from the delivered ref + the PR's repo nwo (parsed from the cached PR URL, no network); Linear reads the exact `Linear: [ID](url)` footer link out of the PR body via `gh.pr_body` (its canonical URL can't be hand-constructed). The delivery block is cached under the `ticket` key for **all** providers.
  - `c` close → `probe_blockers` gate → enqueue `TeardownRequest` → slow kick, so teardown flows through the daemon's `_drain_close_requests`. **Feature worktree:** refuses dirty/unlanded/open-PR, then closes workspace + removes the worktree. The commit half of that gate is **ownership-split** (`worktree_state_blockers`): our own branch uses `git.count_unlanded` — commits flagged by *both* a patch-id check against `origin/<default>` (`git cherry`, so a cherry-picked commit reads as landed) *and* reachability from no remote ref other than `origin/<branch>` (so the commits of whatever branch this one is **stacked on** drop out). A bare `origin/<default>` baseline counted those, which made every branch based on a non-default branch permanently unclosable. Pushing deliberately does **not** clear it — a pushed-but-unmerged branch keeps its worktree. A **coworker's** branch (`is_mine=False`, a PR checked out for review) uses `git.commits_only_local` instead: their work is safe on `origin/<branch>` and the review is over, so only a local review fixup of ours blocks. **Do not** collapse the two — and **do not** re-baseline `count_unlanded` on `origin/<branch>`, which would turn it into a "has it been pushed" test. **Primary checkout** (a `use_worktree: false` repo, `worktree_path == repo_path` / `wt.is_primary`): `teardown` **always** skips `git worktree remove` (git refuses it on a primary checkout, and the user works there in place), then splits on the checkout's branch: (a) **on its default branch** — a **workspace-only close**: the commit guard relaxes (`worktree_state_blockers(is_primary=True)`; the checkout and its branch stay, so unlanded commits are safe), leaving only the dirty guard ("make sure it's all committed"); (b) **on a non-default (feature) branch** — the branch is **torn down**: after the workspace close, HEAD is moved back to the default branch (`checkout_branch`, git refuses `branch -D` of the checked-out ref) and the feature ref is deleted (`delete_local_branch`). Case (b) is **not** relaxed — the branch is going away, so its unlanded commits are not safe; the callers pass `is_primary` to the blockers as `wt.is_primary and on_default` (resolved via `origin_head_branch`; `default is None` off-GitHub keeps it workspace-only, since nothing can be deleted). Callers set `delete_branch = pr_is_merged or (wt.is_primary and not on_default)`; `teardown` reuses a single `origin_head_branch` read for both the relaxation and the `branch != default` delete guard, and the checkout+delete is soft-fail (a failed checkout leaves the branch for a retry, never aborting the already-run workspace close).
  - `C` force-close → overrides the *soft* open-PR block (`forced=True`) but still refuses the *hard* `worktree_state_blockers` (uncommitted; unlanded commits except on a **workspace-only** primary checkout — i.e. one on its default branch, where nothing is removed; a primary checkout on a feature branch is torn down, so its commit guard stands), so force never discards local work. The TUI's `c`/`C` and the `cockpit close` CLI (`cockpit/close.py` — defaults to the cwd's worktree, `--force` overrides the soft open-PR gate) are the two human entry points; both resolve the same `(state, blockers)` and `enqueue` the same `TeardownRequest`, thread `is_primary` into the gate, and the daemon's autoclose/orphan-reap enqueue alongside them — all draining through the one `orchestrators.teardown` path, which detects the primary checkout by `worktree_path == repo_path`. **Closing never runs teardown inline** (no daemon → the marker stays durably queued); only the daemon writes the cache.
  - `m` mute → writes a `NudgePref` (session state, not a cell), repaints via `_repaint_pref` (below) + slow kick to republish the pills.

  **`m` and `z` repaint on the keypress — `app._repaint_pref` → `cache.restamp_pref`, the one row-action cache write.** Every other cell is *derived* from GitHub, git, or cmux, so a renderer must wait for the daemon to go and look; mute and snooze are the opposite — the keypress **is** the source, and the daemon only reads it back out of the pref file. Waiting for the kicked cycle to republish `pr-muted`/`pr-snoozed` was therefore pure lag, and it reads as a dropped keypress: `z` left the row unfolded, un-banded, and the footer still saying "Snooze" (row caps read the same cells) until a full-cycle kick had round-tripped `gh` for *every* repo. So both toggles re-stamp the value the cycle would have written anyway, then `_publish_inventory()` re-renders. Three rules: it writes **both** the flat cells and the PR snapshot's `muted`/`snoozed` fields (cells alone would be reverted ~30s later by the fast tick's `republish_pr_caches_from_disk`, which reads the snapshot); it is a **no-op when the snapshot is missing**, leaving the kicked cycle to build it; and the kick is still sent, because everything *else* the keypress implies — the cmux pills, the trailing `snoozed` fold, the nudge going quiet — genuinely is derived and stays the cycle's job. **Do not** extend this to a cell the daemon derives: that is the same-render-disagreement bug class the sole-writer invariant exists to prevent, and it does not apply to a value the TUI itself authored.
  - `z` snooze → the *event-expiring* sibling of mute, and the answer to "I've read this, it's someone else's turn now". Writes `NudgePref.snoozed` + two wake snapshots read off the **cached** payload (the TUI never calls `gh`), resolved via `_cache_repo_name` — the daemon wrote that payload under the git nwo name, so keying it by the config `name` label matches no file and builds both snapshots from an empty payload, making the next slow tick wake the snooze it had just set — `wake_on` (`nudges.wake_signature` of the PR's `total_from_others` + `review_decision`) and `wake_nudge` (the PR's current `nudge_issue`, `""` for none) — then repaints `pr-snoozed` on the keypress (`_repaint_pref`, which folds the row away — see the trailing-folds invariant — and moves the cursor onto the fold that swallowed it, since `update_inventory` restores by row *index* and would otherwise leave it on whichever worktree slid up into that slot) and **full-cycle** slow-kicks to re-fold the sidebar (see the row-action kick rule: it is the one row key that isn't repo-scoped). It silences the nudge exactly like a mute (`should_nudge` gates on `NudgePref.quiet` = `muted or snoozed`) **and** sinks the row into the sidebar's trailing `snoozed` fold. The two stay **separate fields**, never one tri-state: a mute is indefinite (`cockpit nudge mute` means "shut up"), a snooze auto-clears on an event — different questions, and collapsing them would make the CLI's mute silently self-clear. But `z` **clears any mute** it lands on: mute wins everywhere it's read (glyph, sidebar fold, `quiet`), so leaving both set would silently swallow the snooze *and* its wake; snooze is the strictly narrower ask, so it takes over (press `m` again for an indefinite mute). The auto-wake lives in `cycle.py::_resolve_prefs`, the one point per cycle where prefs are read, so a woken PR un-sinks, regains its 🔔 and nudges again in the same tick. Two events wake it, both riding the fetch the cycle already made:
    - **review activity** — any change to `wake_on`. `total_from_others` (not `unaddressed`) is the comment half so my *own* replies can't wake my own snooze.
    - **new work** — `PR.nudge_issue` differs from `wake_nudge` **and is non-empty**. The asymmetry is load-bearing and is why the two snapshots stay separate fields rather than one signature (equality alone can't express it): CI going red *after* the snooze is my turn again, but an issue the snooze was set *on top of* must not wake it (else `z` is a no-op on exactly the rows most worth snoozing), and an issue *resolving* must not either (nothing to come back to). A pre-existing pref with no `wake_nudge` key reads as `""`, so a currently-failing snoozed PR wakes once after the upgrade — it does have work.

    **Do not** give the snooze a time-based `until` — the event wake condition is the whole point.

The **fast** tick is untouched (network-free local git cells), so an un-park paints correctly and a workspace still open on a parked repo keeps a live statusline.

It is workspace-only, exactly like `c` on a primary checkout — no worktree removed, no branch deleted, nothing uncommitted touched; parking is not teardown. Workspaces are matched **by cwd against the repo's own `worktrees()`**, never by a path-prefix test (a worktree usually lives in a *sibling* directory). Two are always spared: the daemon's own (`self._self_ws` — closing it kills the TUI) and any that isn't `workspace_is_idle` (a running agent mid-turn), the latter reported by toast rather than silently skipped.

On a worktree row it hides: "Hide" beside a highlighted worktree reads as *hide this row* while actually parking every sibling row with it. ### Only the daemon writes the cache; renderers read

`lib/starship.py` field printers are strictly read-only (no gh/git/subprocess/`atomic_write`).

- **Slow tick** (`slow_poll_interval_seconds`, 300s) — `cycle.py::cycle_all`: full reconcile (gh fetch, base-distance, per-PR JSON, PR flat cells, git-state cells, pills).
- **Fast tick** (`fast_poll_interval_seconds`, 30s) — `cockpit.py::_fast_tick`: re-asserts the pidfile (`daemon.reassert_pidfile` — heals a pidfile lost mid-run so `cockpit close`/spawn kicks stay reachable; see the pidfile self-heal note) then network-free republish of git-state (`write_git_state_cache`) + per-worktree session cost (`write_worktree_cost_cache`) + PR flat cells from disk (`republish_pr_caches_from_disk`) + workspace name (`reconcile_workspace_names`) and sidebar-colour (`_tint_repo_workspaces`) reconcile, so the pidfile / `git checkout` / a running agent's spend / tmpdir wipes / a freshly spawned workspace's name+colour recover in ~30s.

New cell → writer in `cache.py`, call site in the slow tick (decide + snapshot) and/or fast tick (republish). **Never** let a renderer read source state directly — that same-render disagreement is the bug class this avoids.

### `cmux events` is a doorbell — it wakes a tick, it is never state

cmux ships a resumable NDJSON event stream (`events.v1`, `cmux events --after/--cursor-file/--reconnect/--name`). An event stream is incremental state by definition, which would collide head-on with "Inventory is derived every cycle, never stored" — so `lib/events.py::watch_workspace_events` reads events as a **trigger only**: an event calls `app._on_workspace_event`, which kicks the **fast** tick, and that tick re-derives every workspace fact from `git worktree list` + `cmux list-workspaces` exactly as the timer would. Nothing downstream ever reads an event payload, so the invariant holds and the win is pure latency — a spawn or close lands in ~0s instead of ~30s, which is what makes `f`/focus and `c`/close feel instant. `_prepare_cycle`'s `workspace_state()` query is **unchanged**; the 30s interval stays the correctness floor, so every failure mode (limux/none, missing `events.v1`, cmux quit, a crashed stream) degrades silently to the pre-event behaviour. The gate is `capabilities.has_capability("events.v1")` paired with `is_cmux()` — the shared probe, never a private `cmux capabilities` read. Five rules:

- **Subscribe to `workspace.created` + `workspace.closed` only** (`WATCHED_NAMES`). Every tick writes pills, colours and names, which cmux reports as `sidebar.metadata.*` / `workspace.renamed` — subscribing to those (or to `--category workspace`) makes the daemon ring its own doorbell forever. Created/closed are the two a *user* causes, and neither is emitted by the fast tick they wake (spawning is slow-tick only), so there is no loop.
- **Debounce lives in the app, not the reader.** `lib/events.py` is a dumb line reader; `_kick_fast` already no-ops unless `_fast_phase == "idle"`, so a burst coalesces for free. The one thing that needs saying is `_events_pending`: an event arriving *during* a fast tick can't be dropped (that tick may have read workspace state before the event happened), so `_run_fast`'s `finally` owes one more kick.
- **The cursor file (`$COCKPIT_HOME/cache/cmux-events.seq`) is cmux's resume bookmark, not a cache cell.** It holds one sequence number, nothing derived, and only cmux reads it — **do not** grow it into stored inventory, and **do not** route it through `cache.py`.
- **The child must die with the TUI.** It is a long-lived subprocess inside the daemon process; `on_unmount` sets `_events_stop`, which both ends the reader and `killpg`s the child (`start_new_session=True`, since killing the leader alone leaves a grandchild holding the stdout pipe and the reader blocks on it forever).
- **A stream that dies instantly gives up** after `_MAX_FAST_EXITS` consecutive sub-`_FAST_EXIT_SECONDS` exits, with backoff between retries — otherwise a cmux that rejects `events` respawns in a tight loop for the daemon's lifetime.

**Do not** feed an event into a decision, a cell, or the slow tick. A close event kicking a *slow* tick would mean a `gh` round-trip per workspace close; the fast tick is network-free, which is why it is the one the doorbell rings.

**The one payload read is the sidebar X, and it is a *gesture*, not state.** Clicking cmux's ✕ on a workspace row is the only close a user can make from outside the TUI, and it means what `c` means — I'm done with this worktree. Derived inventory cannot express it: "the user just closed this" and "this worktree has no workspace yet" are the same observable state, and the latter is the normal pre-spawn condition `_spawn_missing_workspaces` exists to fix — which is exactly why the X used to be a no-op on a tracked worktree (close it, and the next slow tick spawned the workspace straight back). So the event is the only place the gesture exists, and `events.py::_closed_workspace` lifts `workspace_id` + `cwd` off a `workspace.closed` frame into an optional `on_closed` callback beside (never instead of) the doorbell. It stays a gesture, and the distinction is what keeps the invariant intact: the payload is never cached, never written to a cell, never read by a tick, and never consulted twice — it only routes to `app._on_workspace_closed`, which hands the cwd to the same `_close_worktree` the `c` key calls. **Every fact the teardown decision uses is still re-derived there** (`_resolve_worktree` re-reads `git worktree list`, `resolve_pr_state` the PR, `worktree_state_blockers` the tree); the event contributes a path and nothing else. Four rules:

- **`on_closed` is additive and optional.** `on_change` fires for the same frame regardless, so a caller passing nothing gets byte-identical pre-existing behaviour, and a raising handler is caught and logged rather than killing the stream (the doorbell already rang; the tick lands either way).
- **cockpit's own closes must be filtered, and this is the load-bearing half.** The event says nothing about *who* closed a workspace, and cockpit closes them for four reasons that are explicitly not teardown: `h`/park (documented workspace-only), a trailing-fold anchor dissolve, `close_gone_cwd_workspaces`, and teardown's own trailing close. Unfiltered, parking a repo would tear down every worktree in it. `cmux.py::_note_self_close` records the UUID **before** the close (cmux drops a closed workspace from `workspace.list` immediately, so recording after finds nothing) and `was_self_closed` consumes it, TTL `_SELF_CLOSE_TTL_SECONDS`. It lives inside `cmux_close_workspace_best_effort` — the one funnel every close path already goes through — so a **new** close path is filtered for free; **do not** re-implement it per call site. Keyed by **UUID, not cwd**: a `use_worktree: false` repo hosts several workspaces at one checkout, so a cwd key would let cockpit closing one swallow the user's close of its neighbour. cmux-only (limux has no stream, so it never pays the lookup), and an unresolvable `workspace.list` still closes — the blockers gate below is the backstop.
- **It routes to the refusing gate, never to force.** The X is one click with no modifier, so `_close_worktree(cwd, quiet=True)` — no `force`. A dirty tree, unpushed commits, or an open PR refuse **loudly** (a TUI toast naming the blockers) and the worktree survives; the daemon then respawns its workspace next slow tick, which is the visible second signal that nothing was torn down. **Do not** map the X onto `C`.
- **`quiet` suppresses the missing-worktree toast only.** Closing a workspace that isn't one of ours (a hand-made session, a fold anchor rooted at `$HOME`) is the *common* case here, so it must be a silent no-op — but every refusal still toasts, because the X gives no other feedback and a silent one reads as a successful close.

### `sidebar_color` — cosmetic, cmux-only, per-repo

Applied slow-tick via `_apply_repo_colors` **and** fast-tick via `_tint_repo_workspaces` → `cmux … set-color`, deduped in `pill_state` under `color:<ref>` (the same key + persistent dict, so cmux is touched only on change/restart; the fast pass just closes a freshly spawned workspace's ~300s→~30s colour gap, mirroring the name reconcile). Validated at preflight (`_validate_sidebar_colors`, `sys.exit(2)` on unknown). Valid set = `colors.CMUX_COLOR_ANSI` (= `cmux.WORKSPACE_COLORS`).

### `orgs` is a load-time defaults layer — nothing below `load_config` knows orgs exist

An org (top-level `orgs: {<name>: {<repo defaults>}}`, referenced by a repo's `org` key) is **only** a named block of per-repo defaults for the "many small repos, one organisation" shape. `config.py::apply_org_defaults` merges it into each member repo entry inside `load_config()` — `repo.setdefault(k, v)` per key — so the resolution chain every reader already walks (repo → global → default) gains an org rung with **zero** call-site changes: `sidebar_color` tints the whole org in both the cmux sidebar and the TUI, one `use_worktree: false` covers every member, `branch_prefix`/`tickets`/`review_prs` all inherit. **Do not** add an org-aware reader, an `org_*` config field, or a `repo_org(...)` resolution helper — if a field needs org support it already has it. Four rules:

- **One level deep, repo wins.** A scalar the repo sets beats the org's whole; a *block* (`tickets`, `skills`) unions per **field**, repo winning — the same granularity `_tickets_field`/`_skills_field` already give repo-over-global. It is **not** a whole-block override: that would defeat `tickets.project`, the one field meant to differ *within* an org, since a repo adding it would silently drop the org's `keys` (stops matching its own team) and `token_env` (reads the wrong credential). Exactly one level — nothing nests below a block, so **do not** make it recursive. A block is always rebuilt into a fresh dict, never aliased onto the repo: one org block is shared by every member, so handing out the same object would let a mutation of one repo's block reach all its siblings'. Idempotent (re-unioning a merged block with itself is a no-op), which is what lets `preflight.validate_config` call it on a raw dict.
- **Never persisted.** The config *writers* (`registry.register_cwd`, `save_config_value`) re-read `config.json` from disk instead of reusing `load_config()`, so an inherited value can't be baked onto a repo entry. **Do not** introduce a writer that serializes `load_config()`'s dict back to disk.
- **Validated as effective values.** `validate_config` runs `_validate_orgs` (block shape; `name`/`path`/`org` rejected as org defaults; a repo naming an undefined org hard-fails — the silent no-tint/no-opt-out bug) then merges, so every existing `_validate_*` sees the post-merge value and an org-level bad `sidebar_color` fails like a repo-level one.
- **TUI ordering only, no nesting.** `config.py::repos_grouped_by_org` (used by `app._gather_inventory`) renders an org's repos adjacent, each org at its first member's config position; org-less repos keep theirs, so an org-less config is byte-identical to before. There is deliberately **no** org header row (a second nesting level costs cursor-skip, caps, and footer gating for what shared tint already conveys), no cross-repo cmux workspace-group (`_reconcile_sidebar_groups` is per-repo and only touches groups overlapping *this* repo's refs), and no park-the-whole-org key (`h` stays per repo).

### Stacked PRs: one cmux sidebar group + one indented TUI row — derived from `PR.base`, never stored

A [stacked PR](https://docs.github.com/en/pull-requests/how-tos/stacked-pull-requests) chain carries **no** stack id, position, or parent field on GitHub's API — `gh stack` is a local branch-management tool, and the only thing the API exposes is that each PR's base branch is the previous PR's head. So `lib/stacks.py::find_stacks` derives the chain from `PR.base` (`baseRefName`, already selected by the relevant-PR query): zero extra round-trips, no dependency on local `gh stack` state in the worktree, and it works on a coworker's stack too. **Do not** shell out to `gh stack view` per worktree, and **do not** persist a stack — it is inventory, derived every cycle like `git worktree list` (see the "Inventory is derived every cycle" invariant). Chains match on `PR.branch` (already `pr_worktree_branch`-normalized), so a trunk-headed PR's synthesized `pr-<N>-…` branch matches nobody's base — correct, since a merge-the-trunk PR is not a stack member. A stack forking into two children still yields **one** chain (breadth-first from the root): a cmux workspace can live in exactly one group, so overlapping chains are not representable.

Slow-tick `cycle.py::_reconcile_sidebar_groups` renders each chain of ≥2 PRs *that have local workspaces* as one collapsible cmux **workspace group** (`cmux workspace-group`, `square.stack` icon), headed by its own row named **`<tip> (N)`** — the chain's *tip* (its deepest PR, `find_stacks`' last member), not its root, and every member including the tip lists below the header, tip first (`create_workspace_group` lands the caller's first ref at the top). Naming and ordering by the tip is what keeps the sidebar and the TUI reading as the same stack — **do not** re-name the group after the root. cmux-only and best-effort (`workspace-group` is in `cmux.py::_CMUX_ONLY_VERBS`, every verb `check=False`) — limux/none silently skip it. Three rules that are load-bearing:

- **Reconciled against cmux's live `workspace-group list`, not a `pill_state` mirror** (unlike `color:<ref>`) — the group is the derived stack's only representation, so cmux is the authority and a restart re-syncs for free instead of duplicating groups.
- **Matched by member ref, never by name** (`_match_stack_group`): group names are cosmetic and collide across repos (same reason `workspace_name` collides — repo is conveyed by tint), while a `workspace:N` ref identifies exactly one row. Only groups overlapping *this repo's* owned refs are touched, so a group the user built by hand around unrelated workspaces is never claimed, re-membered, or dissolved.
- **The group header is cmux's spawned anchor, kept — never a group member.** `cmux workspace-group create` always spawns a *fresh* workspace to own the group, and the anchor's sidebar row **is** the group header. Re-anchoring onto the stack root (what cockpit used to do) therefore *swallowed* the root's own row: a 4-PR stack rendered three rows under a header that said `(4)`. So `create_workspace_group` keeps the spawned anchor as a dedicated header and every member lists below it, making `_stack_group_name`'s / `_review_group_name`'s count exactly the number of rows folded. Two consequences: the anchor is spawned with `--cwd $HOME` so it sits **outside every registered repo** (inside one, `_reap_workspace_orphans` would reap it and take the group down with it), and `_reconcile_sidebar_groups` **closes it on dissolve** (`ungroup` preserves all members, so an unclosed anchor strands as a loose row) — but only when the anchor isn't one of the repo's owned refs, so a group anchored on a real workspace loses the fold, never the workspace — and it *does* lose the fold every time: an anchor that is one of the repo's own refs is kept out of `_match_stack_group`'s candidates, so the group dissolves and is rebuilt on a throwaway anchor rather than reused (self-healing for a group cockpit made before the anchor was split out, one-shot for a hand-made fold; members are preserved through both). **The anchor outliving every member is its own leak, and needs its own sweep:** close a stack's workspaces (teardown, a respawn under fresh refs) and cmux keeps the group with the anchor as its sole member — at which point `owned & set(g.members)` is empty forever, the "only touch groups overlapping this repo" filter can never reclaim it, and the next cycle builds a *second* group beside the stranded header (four identical `<tip> (N)` rows was the observed shape). So the reconcile also sweeps groups it owns *no* member of, gated on both `icon == square.stack` (cockpit is the only thing that sets one) and `members <= {anchor}` — never a fold that still holds a workspace, never one the user built by hand. The `eyeglasses` and `moon.zzz` half of that sweep is `_reconcile_review_groups`', which owns every review- and snooze-iconed group outright and so reaps a stranded anchor without needing the `members <= {anchor}` test at all.

The dedicated anchor also sets the **minimum fold size, and it is one, not two**: cmux drops a group only when the *anchor* is its last workspace, so `create_workspace_group` refuses only an **empty** ref list (it used to refuse `< 2`, a leftover from before the anchor was split out of the members). Callers impose their own floor where the concept has one — a single PR is not a stack, so `_reconcile_sidebar_groups` still skips a chain of one — but the reviews fold deliberately has none.

**A snoozed stack sinks by its tip, and the move fires on the transition only.** A snoozed stack never joins the `snoozed` fold — `_pile(…, stacked)` keeps it as its own group — so the group's *position* is the only thing left to say "not my turn", and without it a chain the TUI had already sunk sat in the live area looking active. So `_reconcile_sidebar_groups` sinks a chain (`move_workspace_group_to_end`) when its **tip**'s `NudgePref.snoozed` is set, the same discriminator `worktree_table._row_band` bands rows by, and lifts it back (`move_workspace_group_to_start`) when that wakes. Four rules:

- **The two directions are asymmetric, and that asymmetry is the whole design.** The **sink** is unconditional every cycle, exactly like the trailing folds' own `--to-index 9999`, so it *self-heals*: a `broadcast` waking every session, cmux reordering on activity, or a hand drag is undone on the next slow tick (≤`slow_poll_interval_seconds`, since this is slow-tick-only). The **lift** is deduped in `pill_state` under `stack-park:<repo>:<tip PR>` (like `color:<ref>`) and fires only on the transition out of a sink cockpit itself made; an unknown key reads as live. Making *both* unconditional is the obvious implementation and it is wrong — it pins every live stack group to the top of the sidebar and fights the user's own ordering. Making both transition-only is also wrong: the sink stops self-healing. **Do not** collapse them into one symmetric rule. Known ceiling: `pill_state` is process-local, so a daemon restart while a stack is sunk loses the lift's memory of it and a later wake won't raise it (`workspace-group list` reports no index, so the position can't be read back); re-snoozing and waking recovers it.
- **The marker is keyed by the cmux *group ref* (`stack-park:<group ref>`), never by the chain's tip PR.** The tip is `present[-1]` — the deepest member that currently has a workspace — so it **changes** when the tip merges and its worktree is torn down, while the group itself lives on (it matches by member overlap, not by name or tip). A tip-keyed marker is orphaned at exactly that moment: the surviving chain, now live, looks unsunk and stays pinned at the bottom for good — the precise failure the lift exists to prevent. The group ref instead dies with the group, so `_reconcile_sidebar_groups`' dissolve loop **pops the key** and a chain that reforms is built on a fresh ref rather than inheriting a stale `"end"` and lifting a live group to the top on its first cycle. Both halves are regression-tested; **do not** re-key this on anything that outlives or under-lives the group.
- **The lift is still not optional.** Inventory is derived and nothing records where a group *used* to sit, so a sink with no matching lift buries a chain permanently the moment its snooze wakes; the lift is a fixed top rather than a restore, which is the price of storing nothing.
- **It keys on the tip, not any member** (one snoozed dependency can't bury the active chain stacked on top of it), and this pass runs **before** `_reconcile_review_groups`, whose own `--to-index 9999` moves therefore land the reviews and snoozed piles *below* a sunk stack — a chain I've read still outranks a loose pile. **Do not** sink a stack by moving its members into the `snoozed` fold: a workspace lives in exactly one group, and that would split the chain.

Grouping is **cosmetic** — it never spawns a *worktree*, closes a member, nudges, or writes a cell. A stack losing its root (bottom PR merged) leaves the survivors stacked on each other until the group drops below two members, at which point it is `ungroup`ed back into loose rows.

**The TUI shows the same stack as indentation, read off a flat cell.** The table can't see `PR.base` (renderers never read source state), so the daemon writes it: `pr-base` joins the branch-keyed flat cells (`cache.py::_write_pr_flat_cells`, persisted in the PR JSON as `base`, republished by the fast tick). `stacks.py::stack_order` is the renderer-side half of `find_stacks` — same `base` link, but over `(branch, cell)` pairs — returning `(index, depth)` so `worktree_table.py::_stack_rows` sorts each chain contiguously under its **tip** and `_workspace_cell` indents the label behind a `└` (leftmost, ahead of the 🔇/🔔 glyph). **The nesting is exactly one level deep, and the tip heads the chain** — `stack_order` emits the deepest member at depth 0 and every PR it is stacked on at depth 1, in root-first order, mirroring the sidebar group's `<tip> (N)` header + flat member list. A four-PR chain stepping right four times is unreadable at any width and the depth number says nothing the order doesn't, so **do not** restore the per-level cascade (`_workspace_cell` therefore renders one fixed `└` prefix, not a depth-scaled indent). It is keyed by **index, not branch**, so two worktrees reporting the same branch (detached HEADs) each keep a row, and a base cycle from a stale cell falls back to flat rows rather than dropping them. Unlike the cmux group, indentation needs no ≥2 threshold and no workspace — a stacked worktree indents whether or not a session is open on it.

### Reviews and snoozed PRs sink to the bottom — TUI row bands + two trailing cmux folds

Both surfaces answer the same question — *is this my turn?* — and both derive it every
cycle from the same flat cells, never a stored marker. The table expresses it as row
**order** (three bands per repo); the cmux sidebar expresses it as two collapsed
**groups** parked at the bottom, per *org*.

**The snoozed band collapses behind a per-repo `▸ N snoozed` disclosure row, and that is why a snoozed row carries no glyph.** Sinking a row is only half an answer: the row I've explicitly deferred still spends a full line saying so, and reclaiming those lines is the whole point of snoozing. So `update_inventory` renders band 2 folded (`_split_snoozed`, `SNOOZED_KEY_PREFIX`, session-only expansion in `app._show_snoozed`) — the table's own version of the sidebar's `<org> snoozed (N)` group, per *repo* rather than per org because the table groups by repo header and has no org row. Six rules:

- **`z` opens it — one key, three meanings, read off the cursor row** (`app.action_snooze_row`, the same shape as `h`): on a `▸ N snoozed` row it expands/collapses (`SNOOZED_CAP`, relabelled Expand/Collapse by `FooterBar._label`), anywhere else it snoozes or wakes. **Do not** hang this off `h` or a new key — `z` is where the rows went, so `z` is how you get them back, and `h` must stay about *repos*. Enter and a **single** click toggle it too (`SnoozedToggle`, sharing `_disclosure_message` with the hidden row): a disclosure triangle that needs a double-click doesn't read as one.
- **The fold row carries `SNOOZED_CAP` and deliberately **not** `HEADER_CAP`.** `HEADER_CAP` hides *every* row key including `z` itself, and it is what advertises `h` — which parks the whole repo, an alarming thing to offer from a row standing for one section of it. So `FooterBar._skip` suppresses each row key except `snooze_row` on that cap, and the global keys stay, exactly as on a group header. It early-returns *before* `ACTION_REQUIRES`, since the fold row has no `pr` cap and `z` would otherwise gate itself away.
- **The cursor-skip loop must stop there**, so the fold row keys off its own sentinel (`\x00snz:`) rather than nesting under `HEADER_KEY_PREFIX` the way `HIDDEN_ROW_KEY` does. It is the row `z` acts on and the row a snooze lands the cursor on; skipping past it would make a repo whose rows are *all* snoozed unreachable. `current_path()` returns None on every sentinel alike (`_is_sentinel`), so row actions still no-op there.
- **A snooze moves the cursor onto the fold that swallowed the row** (`app._follow_snoozed_row`, after `_repaint_pref`'s render). `update_inventory` restores the cursor by row *index*, so a row folding away leaves it on whichever unrelated worktree slid up into that slot — indistinguishable from a dropped keypress. It **asks the table** (`move_cursor_to_key` on the row's own path, falling back to the fold key) rather than predicting from the pref: "I snoozed it and the fold is shut" does *not* imply the row folded away, since a snooze on a stack member below the tip folds nothing, and predicting would then yank the cursor onto a fold whose count didn't change — the same failure inverted. A wake, or a snooze into an already-open fold, therefore lands on the row itself for free.
- **The fold takes a stack whole.** `_split_snoozed` partitions at *chain* granularity, not per row, so a tip that folds away takes its members with it and a snooze below the tip folds nothing — the same tip rule the bands already follow, for the same reason.
- **Snooze therefore has no row glyph — but it still suppresses the 🔔.** `_status_glyph` keeps its `snoozed` branch and *returns blanks* from it: `pr-nudge` is `PR.nudge_issue` and is never blanked for a snoozed PR, so a snooze that later goes CI-red would light a bell `should_nudge` will never ring (it gates on `quiet = muted or snoozed`). **Dropping the glyph must not drop the suppression** — that regression shipped once and `test_a_snoozed_row_shows_no_bell` pins it. The blank slot is still paid in full, so a row inside the fold aligns with the rest, and 🔇 still wins there for the row that is muted *and* snoozed (reachable by `m` after `z` — `z` clears a mute, `m` does not clear a snooze), matching `row_tooltips`' order. `pr-snoozed` stays load-bearing (banding, fold membership, this suppression, the `snoozed` row cap behind `z`/Wake); only the glyph went. Expansion is **session-only**, like `_show_hidden`: the *snooze* persists in its `NudgePref`, peeking at the pile doesn't, so a restart comes back folded.

**The TUI renders the trailing folds as row order, in three bands per repo.** The sidebar sinks reviews and snoozed PRs to the bottom; the table used to leave them interleaved in `git worktree list` order, so a repo whose rows are mostly PRs I'd already said "not my turn" to buried the one row that wanted me. So `_stack_rows` sorts its chains by `worktree_table.py::_row_band` — **0** my live queue, **1** a coworker's PR I'm reviewing (`pr-author`, which the daemon populates only for a coworker's PR), **2** one I've snoozed (`pr-snoozed`, which then folds away per the rule above) — reading the same flat cells the row already renders from, no network and nothing stored. Four rules: **snooze outranks review** (a coworker PR I've read sinks past the ones I haven't, matching the sidebar's stacks → snoozed → reviews precedence); the sort is **stable**, so within a band the stack / `git worktree list` order is untouched; a chain bands by its **tip** (the depth-0 row heading the group), **never by its deepest member** — a snoozed *tip* sinks its whole chain rather than splitting it, while a snooze on a member *below* the tip moves nothing, because one snoozed dependency must not bury the active stack sitting on top of it (contiguity under the tip is what keeps table and sidebar reading as the same stack; the sidebar sinks the same chain by the same tip rule, just by a different mechanism — `_pile(…, stacked)` excludes every ref already folded into a stack group, so a stack with ≥2 local workspaces never reaches the `snoozed` **fold**, and its whole group is moved to the bottom instead, per the park rule above); and **mute is deliberately not a band** — 🔇 means "stop nudging me about a PR I'm working on", not "not my turn", so a muted row stays in the queue. Bands are **per repo**, never cross-repo: the table groups by repo header and has no org row (see the `orgs` invariant's TUI-ordering rule), unlike the sidebar folds, which are per *org*. Parked repos are unaffected — they already trail in the `▸ N hidden` disclosure row.

**Coworker reviews fold into one trailing `<org> reviews (N)` group — per *org*, so it is the one fold that spans repos.** `not PR.mine` workspaces go into a group with the `eyeglasses` icon, re-parked at the **bottom** of the sidebar every cycle (`cmux.move_workspace_group_to_end` — `--to-index 9999`, which cmux clamps; `workspace-group list` reports no index, so there is nothing to compare against and the move is unconditional). Reviews are the passive pile — someone else's PR I'm reading, never mine to ship (the same `PR.mine` seam that suppresses the nudge and swaps in the review-mode seed prompt) — so they belong out of the way of my own rows.

The pile is keyed by `_review_bucket_key` = the repo's **`org`**, or its `name` when it has none (an org-less repo therefore keeps its own bucket, i.e. the old per-repo behaviour). An org is a team and a team's PRs are one review queue however many repos they span; bucketing per repo scattered that one queue across as many folds as the org has repos. The bucket name leads the header (`Reality Defender reviews (2)`) because several piles coexist and `reviews (N)` twice over says nothing about whose.

That key is why this is the **one** fold with its own reconcile pass, and the one exception to "sidebar groups are reconciled inside the per-repo cycle": a repo alone can't tell whether its lone review has siblings elsewhere in the org. So `_reconcile_sidebar_groups` only *collects* — appending each repo's unstacked `not PR.mine` refs (and its owned refs) to a `ReviewFolds` accumulator threaded down from `cycle_all` — and the cross-repo `_reconcile_review_groups` drains it once, after every repo, alongside the other repo-spanning sweeps (so a repo-scoped `only_repo` kick skips it and passes `folds=None`). Ownership splits cleanly along the icon: the per-repo pass filters review-iconed groups out of its `all_groups` entirely and never creates, renames, or dissolves one, while *every* review-iconed group is the cross-repo pass's (nothing else sets the icon) — so a fold matching no bucket is dissolved, which reaps a stranded anchor-only header for free, no separate `strays` list needed. Three rules on top of the three above: **stacks win the overlap** (a coworker PR inside a stack folds with its chain — the reviews contribution is computed where `stacked` is known and excludes every already-stacked ref, because a workspace can live in exactly one group); a **lone** review folds too — `<org> reviews (1)` is a real group, and the queue should read the same at one review as at five, so there is no minimum and no loose-row fallback; and the drop-departed-members loop guards on `folds.owned` (the union of every repo's live workspace refs), not on the bucket — a member that stopped being a review is cockpit's to remove, a hand-added foreign workspace is the user's. It is derived from `PR.mine` + `org` every cycle like everything else here — **do not** persist a "this is a review" marker, and **do not** add an org-aware config field for it (`org` is already just a defaults layer; see the `orgs` invariant).

**An incomplete cycle suspends the dissolve — `ReviewFolds.partial`, and it guards the one irreversible thing this pass does.** Every other move here is additive or idempotent; dissolving is not, because it closes the fold's anchor workspace. The buckets are built from `ctx.tracked`, i.e. from the `gh` fetch, so a repo that never reached `_reconcile_sidebar_groups` leaves its org's bucket **absent** — and an absent bucket is indistinguishable from "this org has no reviews any more". Two paths get there and both are routine: `_prepare_cycle` returns None (a transient `list_relevant_prs` failure, a missing path, an unresolvable nwo, cmux down) and `cycle_all`'s per-repo `except`. Both now set `folds.partial`, and `_reconcile_review_groups` skips its dissolve loop when it is set — the re-park, rename, and re-member passes still run, so a repo that *did* report keeps getting its pile pushed to the bottom. Without it a network blip reads as a decision: an hour of GitHub SSH refusals had the daemon tear down all four folds and close their anchors on every failing cycle and rebuild them from scratch on every good one, reshuffling the sidebar each time and burning ~180 groups in one session (diagnosed off `cmux events`, where each death is `workspace.reordered` → `workspace.closed <anchor>` ×4, ~130ms apart — the `ungroup_workspaces` + `cmux_close_workspace_best_effort` pair). **Do not** re-key this on the bucket being empty rather than on the cycle being complete: an empty bucket is exactly the ambiguous case, so that guard would be a no-op on the bug it exists to stop. The cost is that a genuinely stranded anchor-only header waits for the next healthy cycle — cosmetic, and cheap beside closing a live fold. `cycle_all` sets the flag even when the repo raised *after* folding; over-conservative on purpose, since a deferred reap is free and a wrong dissolve is not.

**Snoozed PRs fold into a second trailing `<org> snoozed (N)` group, below reviews.** Not new machinery — the *same* accumulator and the *same* pass: `ReviewFolds` carries a second `snoozed` bucket dict beside `buckets`, and `_reconcile_review_groups` walks `_TRAILING_FOLDS` = `((buckets, eyeglasses, reviews-namer), (snoozed, moon.zzz, snoozed-namer))`, applying the identical match/rename/re-member/dissolve logic to each family. Membership is `NudgePref.snoozed` (TUI `z`), bucketed by the same `_review_bucket_key`, and it holds **my** PRs as well as coworkers' — snoozing is about whose turn it is, not whose PR it is. Four rules on top of the reviews ones:

- **Precedence on overlap is stacks → snoozed → reviews.** A workspace lives in exactly one group; a coworker PR I've already read belongs in the waiting pile, not the to-read queue, so the snoozed refs are resolved first and the reviews contribution excludes them (both computed in `_reconcile_sidebar_groups`, where `stacked` is known).
- **Order comes from the pass order, not a rank field.** Each `move_workspace_group_to_end` is `--to-index 9999`, so every move lands its target below everything moved before it. Walking `_TRAILING_FOLDS` reviews-first therefore leaves snoozed bottom-most — the most passive pile lowest. **Do not** reorder that tuple expecting the names to sort it out.
- **The two families are matched separately.** `_match_stack_group` keys on member overlap and is icon-blind, so each family is handed only its own groups — otherwise a PR moving from `reviews` to `snoozed` could let one pile claim the other's fold and re-icon it.
- **The per-repo pass must filter *both* icons out of `all_groups`.** It owns stacks only; a snooze-iconed group matches no `desired` stack, so leaving it in that list dissolves the fold on every single cycle.

Like reviews, a **lone** snooze folds (`<org> snoozed (1)` is a real group — the dedicated anchor is what makes a one-member fold possible), and the state is derived every cycle — **do not** persist a "this is snoozed" sidebar marker. The `NudgePref` is the state; the fold is only its rendering.

**Both trailing piles are born collapsed — and the collapse is create-time only, never a per-cycle re-assert.** cmux creates every group *expanded* (`workspace-group create --json` reports `is_collapsed: false`), so a pile that is by definition not-my-turn pops open on the very tick that builds it and the user re-collapses it by hand. `create_workspace_group(collapsed=True)` (the `collapse` verb, fired after the icon, best-effort like every other group verb) is the same statement the `--to-index 9999` sink already makes in the other dimension — position says *bottom*, the fold says *shut*. Only `_reconcile_review_groups` passes it: a **stack** is the live queue, so it keeps the `collapsed=False` default and its members stay visible as rows. The create-time restriction is load-bearing and is **not** the sink's self-healing shape — expanding a fold to read a review is a deliberate gesture, not drift, so a per-cycle collapse would slam it shut within `slow_poll_interval_seconds`. It also needs no `pill_state` marker (unlike the stack-park lift): creation *is* the transition, and an existing fold is re-membered in place (`add`/`remove`), never rebuilt, so it keeps whatever state the user left it in. **Do not** promote this to an unconditional re-assert, and **do not** read `is_collapsed` back to "correct" a fold — cockpit does not own that state after create.

### Workspace names track repo + branch (`wt.workspace_name`), re-asserted on both ticks

`wt.label` (`git.py::branch_label`) derives from the *branch*, not the dir basename (`wt.short`): strip `branch_prefix`, drop a leading base segment (`master/`), slugify, drop a leading ticket/PR token (`pe-4608-`) — but never to `""`. The **cmux workspace name** is `wt.workspace_name` = the bare `label` (no `[<repo>]` prefix — repo is conveyed by `sidebar_color` tint in both the cmux sidebar and the TUI table, so the two never double up). `workspace_name` stays a distinct property (one seam for the naming paths) even though it now equals `label`; `wt.repo_name` is still threaded onto the `Worktree` at construction, but only for the `git-repo` cell (`write_git_state_cache`), not the name. Every path that spawns, renames, or matches a workspace **by name** uses `workspace_name` (`spawn_pr_workspace`/`spawn_orphan_workspace`, `reconcile_workspace_names`, `find_cockpit_workspaces`, `_handle_orphans_and_close_stale`, `_reap_workspace_orphans`, `_teardown_worktree`'s name fallback); cwd→path matching (the primary route everywhere) is unaffected. **Consequence:** dropping the prefix means two repos with the *same* branch label produce the same workspace name — a **cosmetic** collision everywhere (cockpit matches by cwd→path, never by name) except the one functional edge of orphan-auto-spawn's name-clash skip (`_reap_workspace_orphans`), which will skip auto-spawning the second same-named orphan. cockpit resolves workspaces by cwd→path, never by name; `cmux.rename_workspace_if_needed` re-asserts the name idempotently (slow tick `_refresh_tracked_pills`/`_refresh_orphan`; fast tick `reconcile_workspace_names`), recovering drift in ~30s. Cosmetic, never a `send`. **Consequence:** to relabel, rename the *branch* — a manual workspace rename is reverted next tick. **Exception:** any **main-branch** worktree — `wt.is_primary` **or** `wt.branch in MAIN_BRANCHES` (`cockpit.lib.constants`) — keeps its custom name (`reconcile_workspace_names` guards on both), so a `master` workspace named e.g. `morning` isn't force-renamed. The branch half of the guard matters in a **bare repo**, where no sibling worktree is ever `is_primary`: a feature worktree temporarily parked on `main` would otherwise be renamed to `main`, colliding with another workspace and breaking switching.

### The daemon creates worktrees in the background — never blocking the tick on `git`

`cycle.py::_spawn_missing_workspaces` shells out via module dispatch (`python -m cockpit.cli new`) in a detached `Popen(start_new_session=True)`:

- **My PR, no worktree** → `cockpit new --pr <n> --repo <name>` (plan-only prompt). Always on.
- **`review_prs` (per-repo, default false)** → every coworker open PR without a worktree → `cockpit new --pr <n> --review --review-command <cmd>`. Discovery: `gh.list_open_pr_heads` (uncapped `is:pr is:open`; the normal query is `author:self`-only). Validated `_validate_repo_bool`. **Dependabot PRs are excluded by default** — they're coworker-authored so they'd flow through this path, but `_spawn_missing_workspaces` skips any candidate `gh.is_dependabot(author)` (GraphQL login `dependabot`, plus the REST `app/dependabot` / `dependabot[bot]` spellings) unless the repo sets `"dependabot": true` (`_validate_repo_bool`). This is the single gate; the "my PR" and orphan paths are `author:self`-gated and never see dependabot. **External (non-collaborator) PRs are also excluded by default** — a fork/outside contributor's PR body and diff are untrusted content, and auto-spawning a Bash-capable review agent on it is a prompt-injection risk on a public repo. `list_open_pr_heads` now also returns each candidate's GraphQL `authorAssociation`; `_spawn_missing_workspaces` skips any candidate whose association isn't `OWNER`/`MEMBER`/`COLLABORATOR` unless the repo sets `"review_external": true` (`config.py::review_external`, validated `_validate_repo_bool` like `dependabot`). This gate is independent of the dependabot gate — both must pass for a candidate to spawn. The seeded first turn is the **configurable** `skills.review` (`config.py::review_command` reader, single-sourced from `REVIEW_COMMAND_DEFAULT`, per-repo → global → default, validated `_validate_skills`). The default is Claude Code's **built-in `/review`** — it ships with every Claude Code install, so it resolves in every spawned review workspace (a personal global skill like `/pr-review` only resolves for its owner; a project skill only when the watched repo is that repo). Override per-repo (or globally) with a personal `"/pr-review"`. The auto-review is **dry-run**: `spawn._review_prompt`'s closing line tells it to report findings and **ask before posting comments or submitting an approve / request-changes verdict** — a human authorizes those, the daemon never auto-posts. **Keep the spawn-layer default in sync with `REVIEW_COMMAND_DEFAULT`** (`spawn.py` imports it for both the `--review-command` argparse default and `_review_prompt`'s param) — don't hardcode a literal command string in `spawn.py`. `skills` has two sibling seams for the same externalize-the-verb pattern, both default `""` (built-in prose, no config needed): `skills.plan` (`config.py::plan_command`) leads `_plan_only_prompt` on a plan-only PR/branch spawn, and `skills.actions` (`config.py::actions_command`) leads `_actions_prompt` on a GitHub-Actions-run-URL spawn — both followed by the source/run/PR context and the shared `plan_tail.txt` no-code/wait-for-approval gate (never externalized) via the shared `command_seed.txt` template. Ticket-fetch spawns (Linear/Jira/Trello/GitHub-issue) are untouched — they keep their own dedicated MCP-fetch-and-rename prompts, not `skills.plan`/`skills.actions`.

Both go through `_bg_spawn_pr`, which guards in-flight launches in `pill_state` (`spawn:<owner>/<name>:<branch>`, TTL `_SPAWN_INFLIGHT_TTL_SECONDS`) against a double-launch; logs to `$COCKPIT_HOME/spawn.log`. Review worktrees then track via the normal `match_worktrees` coworker path; orphan auto-spawn stays `{self_user}/`-gated.

**A worktree younger than `_SPAWN_ADOPT_GRACE_SECONDS` (120s) is not adopted — `_too_young_to_adopt`, and it guards *both* paths that attach a workspace to an existing worktree.** `cockpit new` materialises the worktree and creates its workspace as two separate steps of a *separate process*, so there is a window in which the worktree is real on disk and its workspace does not exist yet. A poll landing inside it sees a worktree no workspace covers and spawns a second one — two cmux workspaces on one worktree, each starting its own Claude, each seeded with the same task, each registering its own `/session-coordination` entry. Observed at 2s (worktree + workspace at 13:01:40, `cockpit new` exits 13:01:42, poll adopts at 13:01:42, duplicate workspace at 13:01:43); the `refs/pull/N/head` fetch that precedes `git worktree add` can stretch it much further on a large repo, hence a grace generous beyond the measured window. Four rules:

- **Both call sites, not just the orphan one.** The `cockpit new --pr` form races identically, and there the worktree matches an open PR before its workspace exists — so it is the *matched-PR* branch (`spawn_pr_workspace`) that spawns the duplicate, not the orphan branch. Gating only the path a given repro happened to take leaves the sibling broken.
- **Age, deliberately not a lock or a spawn-side registration.** Those close the window rather than shrink it, but both mean cross-process state on disk — stored identity, which the inventory-is-derived rule exists to forbid — plus a stale-lock failure mode where a crashed `cockpit new` strands its worktree unadopted forever. `git.worktree_age_seconds` derives from the filesystem on every call and needs no cleanup. It is the same helper (and the same "how long since I made this worktree" question) as the 4h `orphan_nudge_grace_seconds`.
- **It fails open.** `worktree_age_seconds` returns `inf` for an unstattable path, which reads as old enough and spawns: a filesystem hiccup silently withholding a workspace forever is worse than the duplicate this prevents. **Do not** invert that test.
- **Not configurable, and not `_bg_spawn_pr`'s problem.** A per-repo field would cost the three-faces config sync for a value nobody tunes. And the two *creating* paths (my-PR / `review_prs`) have no worktree yet, so there is no age to read — their double-launch guard is the in-flight key above, which is process-local to the daemon and therefore cannot see a user-typed `cockpit new` at all. That blindness is exactly why the grace is needed.

**A coworker's PR is review-mode everywhere — never author-mode.** `PR.mine` (set in `_pr_from_node` from the query layer's `self_user`; defaults **true** so a hand-built PR keeps author-mode) is the single flag, and it gates the two places a tracked coworker worktree would otherwise be told to rewrite someone else's branch:

- **No nudge.** `PR.nudge_issue` requires `mine` alongside its OPEN gate, so `_refresh_tracked_pills`' `others_items` never reach `maybe_nudge` — the author-mode `_NUDGE_DESC` text ("CI is failing — address it", "merge conflicts — rebase and force-push", "unresolved review thread(s) — reply or push fixes") is the PR author's job, not the reviewer's. Because `nudge_issue` is also the source of the `pr-nudge` flat cell, the TUI 🔔 goes quiet on coworker rows in the same breath — bell and nudge can't disagree (the same single-authority reason the OPEN gate lives there). Pills, cells, and the Issue column still render the issue: only the *nudge* is suppressed, never the display.
- **Review-mode seed prompt.** `build_pr_prompt` branches on `mine`: my PR gets the per-`display_issue` action + `pr_authority.txt` (commit/force-push without asking); a coworker's gets `review.txt` led by `skills.review` — the same dry-run seed `spawn._review_prompt` uses for the `review_prs` path, resolved at global level (`review_command()` with no repo entry, since `spawn_pr_workspace` carries a PR + worktree, not the repo block). This matters for the *non*-`review_prs` route: a coworker worktree that already exists but has no workspace is spawned by `_spawn_missing_workspaces` through `spawn_pr_workspace`, which would otherwise hand a review session `pr_authority`'s force-push grant. The TUI's `f` key inherits it — `_pr_from_payload` sets `mine=not p.get("author")` (the cache records a login *only* for a coworker's PR).

**Do not** add a nudge or an authority grant that keys off the worktree's existence alone — a local worktree on a PR branch means "I'm engaged with this PR", not "I own it". Gate on `PR.mine`.

**`use_worktree: false` repos opt out of all of the above.** The flag is a per-repo bool that defaults **true** (absent = normal worktree-managed repo); the *inverse* polarity is deliberate — a repo registered by bare `cockpit new` (no source/`--cwd`/`--repo`) carries `"use_worktree": false` and `_spawn_missing_workspaces` **early-returns** (`if not repo_entry.get("use_worktree", True)`) for it — the user works in-place on the main worktree (often `master`, possibly off-GitHub) and never wants cockpit creating PR/review/orphan worktrees. The row renders **only while a workspace is open on it** (`app._gather_inventory` filters such a repo's worktrees down to those in the per-refresh `workspace_cwds()` set): with nothing open the branch row is unactionable — `f`/`c`/`N` have no session to reach — so the repo collapses to its bare group header, and `n` (on that header) starts one on demand. A backend hiccup (empty `workspace_cwds()`) degrades to the same header-only state, which is recoverable by the same key. Worktree-managed repos are never filtered — their rows stay derived from `git worktree list` + the cell writers, independent of spawning. Registration is `registry.py::register_cwd(use_worktree=False)`: it appends the cwd's main repo to `config.json` (writing `"use_worktree": false` **only** when False — the key is omitted for the default; empty branch prefix when off-GitHub via `gh_self_user`'s try/except; `default_base` from `gh` then git `symbolic-ref` then `"main"`), skips the interactive branch-prefix prompt (irrelevant with no worktree branches), and is idempotent — an already-registered repo is returned untouched, so a bare spawn in a normal managed repo does **not** flip it. Validated `_validate_repo_bool(cfg, "use_worktree")` (polarity-agnostic — any present-but-non-bool value hard-fails). The bare path in `spawn.py::main` then flows through the existing `--cwd` branch (workspace at the repo root, no branch, no worktree). **The `n` row-key branches on it:** a `use_worktree: true` repo cuts a new worktree/branch per `n`; a `use_worktree: false` repo gets **one** named workspace on the checkout (`cockpit new --cwd <repo_path> --name <name>`, no worktree) — the modal picker grays a `use_worktree: false` repo that already has a workspace (policy: one addressable workspace per such repo; `f` reaches it) and prefills the name Input with the repo name. **GOTCHA:** every read is `not repo.get("use_worktree", True)` — a bare `.get("use_worktree")` (no default) treats an unconfigured repo as opted-out and silently stops auto-spawning it. **Do not** let `use_worktree: false` repos reach any auto-spawn — the early return is the single gate.

### Trunk-headed PRs get a synthesized branch — `main`/`master` heads never become the worktree branch

cockpit joins a PR to its worktree, row, and cache by the **head branch name** (`headRefName`) everywhere. A "merge main into `<feature>`" PR breaks that: its head IS the trunk (`main`/`master`), so checking it out clobbers local `main`, collapses onto the primary checkout, and labels the workspace `main`. `gh.py::pr_worktree_branch(number, head, base)` is the **single** normalizer: for a head in `MAIN_BRANCHES` it returns `pr-<N>-<base-slug>` (a distinct, trunk-safe branch carrying the PR number); otherwise the head verbatim (the 99% case, zero change). Applied at the four join points that must agree or the row won't line up: `_pr_from_node` (`PR.branch`), `resolve_pr_branch` (the `cockpit new --pr` checkout branch — fetches `refs/pull/N/head`, never touches local `main`), `list_open_pr_heads` (the `review_prs` candidate branch, so `existing_branches`/no-respawn match), and `_relevant_pr_query`/`_collect_nodes` — which rejoin the synthesized worktree to GitHub **by the embedded number** (`pullRequest(number:)`), since `headRefName: main` can't be the key. `branch_label` already strips the leading `pr-<N>-` token, so the workspace reads as the **base feature** it merges into (`feature/new_onboarding` → `new-onboarding`). The user's own branches carry `branch_prefix` (`khivi/pr-…`) so `_SYNTH_PR_BRANCH_RE` (`^pr-(\d+)-`) never misfires on them. **Do not** re-thread `headRefName` straight into a worktree branch — route it through `pr_worktree_branch`.

### Slack thread source — codename branch, MCP-delegated fetch, no `claude mcp list` probe

`spawn.detect_source` classifies a Slack permalink (`slack.SLACK_URL_RE`) as `slack` mode — a user-initiated source only (never daemon auto-spawned), so it has no cache cell / pill / `docs/state-machine.md` node, same shape as `actions`. A Slack URL carries no human name, so spawn synthesizes a deterministic codename branch (`codename.codename(slack.slack_seed(url))` → `<prefix><adj>-<noun>`). The seed is the thread's **stable identity** (channel id + message ts via `slack_seed`), NOT the raw URL — so query params (`?thread_ts=…&cid=…`) and the `archives` vs `app.slack.com/client` shape don't change the branch, keeping re-spawns idempotent. Cockpit never calls the Slack API: `_slack_prompt` delegates the thread read to the in-session Slack MCP (mirrors `_linear_prompt`), and under `use_slack: true` instructs Claude to append a topic slug to the codename (`cosmic-otter` → `cosmic-otter-fix-oauth`) and rename the workspace. **Never** add a `slack_mcp_available()` / `claude mcp list` pre-flight gate: that probe is unreliable for claude.ai-managed connectors (false-negatives even when live), so a positive-detection gate would silently disable the feature — the prompt's own retry-then-STOP logic handles a genuinely absent connector. `use_slack` (bool, `_validate_global_bool`) gates only the fetch/rename detail; the URL is seeded as context regardless.

**This rule is repo-wide, not Slack's alone — every MCP-delegated spawn seeds its prompt unconditionally.** Linear was the one exception (`linear.linear_mcp_available`, a `claude mcp list` probe gating `_linear_prompt`) and it hit exactly the predicted false-negative, so it is **removed**: `claude mcp list` health-checks each server by *connecting* to it, and a claude.ai-managed connector handshakes asynchronously — ~6s typically, 30s+ when several worktrees spawn at once — so it reported Linear absent while the connector was live. The gate then printed "Linear MCP not detected" and downgraded the spawn to the generic plan prompt, dropping the ticket fetch on precisely the setup the feature targets. The history is the argument: the probe's timeout was already bumped 3s → 15s chasing the same false negative, which bought a slower wrong answer, and its own docstring still claimed "No network — a local config dump" while a comment ten lines above described the health-check. Cost of removal is nil — `prompts/linear.txt` carries the same retry-then-STOP step as `prompts/jira.txt`, which is what handles a genuinely absent connector, in-session where the tools actually are. `tests/test_spawn.py::test_spawn_never_shells_out_to_claude_mcp_list` pins both halves (the symbol is gone; a Linear spawn shells out to no `claude`). **Do not** reintroduce a pre-flight for any provider — Jira, Trello, GitHub and Slack never had one, and raising the probe's timeout only buys a slower wrong answer (it was already bumped 3s → 15s chasing this).

### Prompt prose lives in packaged `cockpit/prompts/*.txt`, not Python string lists

Both prompt families render packaged templates via `cockpit.lib.templates.render(name, **slots)` (`str.format` — no escaping needed: rendered bodies have no literal braces, and a `{...}` in a *value* like a PR title is data, never re-parsed): the spawn first-turn prompts (`spawn._linear_prompt` / `_jira_prompt` / `_trello_prompt` / `_github_issue_prompt` / `_slack_prompt` / `_plan_only_prompt` / `_review_prompt` / `_actions_prompt`) and the per-PR / orphan prompts (`lib.prompts.build_pr_prompt` / `build_orphan_prompt`). The split is strict: **templates carry only static prose + `{slots}`; the Python builder owns all control flow and value computation.** The builder computes the interpolated values, picks the template when there's a choice (Slack's two modes are `slack_fetch.txt` vs `slack_context.txt`; `build_pr_prompt` maps `pr.display_issue` → one `pr_action_*.txt` via `_ISSUE_ACTIONS`, gating `pr_authority.txt`), and builds any conditional block in Python to inject as a slot (e.g. `{source_block}`, `{action}`), passing the shared `plan_tail.txt` into spawn templates that end with `{plan_tail}`. A missing slot raises `KeyError` loudly — never a silent stray placeholder. **Do not** re-inline prompt prose into Python lists, and **do not** add conditionals to a `.txt` (no templating engine — pick the template in the builder). `skills.review` (default `/review`), `skills.plan`, and `skills.actions` (both default `""` — built-in prose) still lead their respective prompts as a slash-command name (expanded in-session by Claude Code); only the surrounding context is templated. **Packaging gotcha:** hatchling ships only **VCS-tracked** files, so a new `cockpit/prompts/*.txt` must be `git add`ed or it silently won't land in the wheel (`importlib.resources` then `FileNotFoundError`s on the installed daemon); `tests/test_templates.py` asserts every template resolves.

### The one cache exception: session-scoped cells (written outside the daemon)

`lib.claude.stash_from_stdin` writes `context-<sid>`, `rate-limit-5h-<sid>`, `model-<sid>`, `permission-mode-<sid>`, `transcript-path-<sid>`, `cost-<sid>` from the statusLine stdin (the only place that data exists). Never read by the daemon, with **one** exception in one direction: the daemon *reads* `cost-<sid>` to derive `wt-cost` (below). **Do not** extend this exception to a new cell — a new value that only the statusLine can see still belongs here, but the daemon must never *write* one.

### `wt-cost` — session cost folded onto a worktree, the daemon's bridge across the two keyings

The TUI's `$` column is the total USD every Claude Code session rooted at a worktree has spent. The data already exists — `stash_from_stdin` caches Claude Code's own pre-computed `total_cost_usd` per session — but it is keyed by **session id** while every table row is keyed by **worktree path**, so something has to join them. `cache.py::write_worktree_cost_cache` does, on the **fast** tick (`cockpit.py::_fast_tick`, beside `write_git_state_cache`): it sums the `cost-<sid>` cells for the sids under that worktree's Claude Code project directory into one `wt-cost-<cwd>` cell. Renderers read only that cell, so the "never let a renderer read source state" invariant holds — the table never globs `~/.claude/projects` on a render. Fast-tick rather than slow: the number only moves while a session is live, so a 300s cadence would visibly lag the work. Four rules:

- **The join is Claude Code's project-directory slug, and it is walked forwards only.** `~/.claude/projects/<slug>/` names a session's cwd with every non-alphanumeric character collapsed to `-` (so `/` and `.` both do: `…/repo/.bare` → `-Users-…-repo--bare`), case preserved. That map is **lossy** — two paths can slug to one directory — so `_claude_project_slug` is only ever applied worktree-path → directory. **Do not** try to recover a path from a slug, and do not reverse-map the `transcript-path-<sid>` cells to find a row's sessions.
- **The stem is `wt-cost`, deliberately not `cost`.** A shared stem would make a `cost-*` glob match both a session id and a path slug — which is exactly what `cost_reporting_available` globs, so the gate would latch itself on off cockpit's own derived value.
- **The column is gated on the data, never on the plan.** The statusLine blob carries no subscription tier, and some plans report `total_cost_usd: 0` for every session, so "should this column exist" can only be answered by asking whether *any* session has ever reported a non-zero cost (`cache.cost_reporting_available`, read once at `app.compose`). No config field, no `cockpit setup` question, nothing to keep in sync across the three config faces. **Do not** add one, and **do not** try to detect the plan.
- **Blank is not zero.** The cell is written `""` (not `"0"`) for a costless worktree and the row renders an empty cell, because an absent number means "never reported" (no statusLine installed, a session predating the cache, a plan that writes zeros) just as often as it means free. A row that can't tell those apart says nothing rather than claiming the work was free.

### Nudge idle-gate: trust the `idle=` pill, NOT cmux's native `Needs input`

`nudge_if_idle` (`lib/cmux.py`) must tell "parked at prompt (safe to `send`)" from "awaiting a y/n permission (unsafe)". cmux native `claude_code=` has `Running`, `Idle`, and the **ambiguous `Needs input`** (fires for both an idle session aged past Notification *and* a pending permission). The gate: block on native `Running`; safe iff the `idle=` pill is present OR native is the unambiguous `Idle`; self-heal a dropped Stop-hook write by re-asserting `idle=` under native `Idle`. The pill (`cockpit/hooks/cmux-idle-pill.sh`) uses a verify+retry loop — its silent loss under cmux contention (`Broken pipe`) was the original bug. **Never** simplify the gate to trust `Needs input`.

**The gate is factored out as a *verdict*, and every caller uses that one function.** `_idle_skip_reason(status_lines)` returns why a `send` would be refused (or None), in the guard order `nudge_if_idle` itself applies; `nudge_if_idle` gates on it and reports it through the optional `skips` dict, `cockpit broadcast` prints those reasons per workspace, and `rest_skip_reason(ref)` is the public one-read wrapper a *display* caller uses — the TUI's `a` modal, warning you before you type into a session that will refuse the message. The point is that the warning and the decision are computed by the same code and cannot disagree. **Do not** re-derive the verdict from raw signals at a call site: an earlier version of the `a` hint did exactly that and promptly got the guard order wrong, testing `parked=` *before* the at-rest check, so a mid-turn parked session reported the wrong cause. The display caller is still advisory only — the gate re-checks at send time and stays the authority, because a turn can end while you type.

**Every message is collapsed to one line before the send — `cmux.one_line`, and it is delivery correctness, not cosmetics.** `cmux send` synthesizes keypresses; it does **not** do a bracketed paste. Its own help says "Escape sequences: `\n` and `\r` send Enter, `\t` sends Tab", and probing cmux 0.64.22 confirms *both* spellings of a newline — the literal two-character `\n` **and** a real 0x0A byte in the argv — arrive as **Enter**. In a Claude Code composer Enter means submit, so an un-normalized multi-line message does not deliver one prompt containing newlines: it submits the first fragment as its own truncated prompt and the remainder as a second. This was a live bug, not a hypothetical — `cockpit broadcast 'fix the \n handling'` sent a bare `fix the` to every idle session and `handling` as a follow-up, and it fails silently (a mangled send just prints). No escape survives (`\\` arrives as two literal backslashes and the Enter still fires), so collapsing is the only faithful delivery. Three rules: it lives **inside `nudge_if_idle`**, the one funnel every send path already goes through — the same single-funnel reason `_note_self_close` lives inside `cmux_close_workspace_best_effort`, so a **new** send path is covered for free; **do not** re-implement it per call site. It runs **before the `dry` print**, so `--dry` reports the text that would actually land rather than the raw input. And it is why the TUI's `a` modal is an **`Input`, never a `TextArea`** (`AskScreen`) — the widget is where the constraint is honest, one line in / one prompt out. **Re-probe before relaxing any of this**: it turns on cmux not having grown a bracketed-paste mode.

### `cockpit broadcast` reuses the nudge gate — no second send path, no cache cell

`cockpit/broadcast.py` fans a line of text out to every idle workspace (`lib.cmux.workspace_cwds()`, self-excluded by default) by calling `nudge_if_idle(ref, message, tag="broadcast")` per ref with no `pref_key` — the same idle gate documented above, just invoked without the PR mute/snooze check (a broadcast isn't a PR nudge). It is a one-shot user gesture: it writes no cache cell, pill, or `pill_state`, and skipped refs are only printed, never queued for retry. **Do not** give it its own send path, its own idle check, or a cache cell — extend `nudge_if_idle` if the gate itself needs to change.

### Nudge prefs are keyed per repo — a PR number alone is not an identity

`NudgePref` (mute + snooze + `last_nudge_at`, `lib/nudges.py`) persists one JSON file per PR at `$COCKPIT_HOME/cache/nudges/<repo>__<number>.json`, named by `nudges.pref_key(repo_name, pr_number)`. `repo_name` is the git **nwo name** — the same key the PR cache files use (`cache._repo_slug`), so the two agree on what identifies a repo. Every entry point threads it: `cycle._resolve_prefs(ctx.name, prs)`, `maybe_nudge(..., pref_key=…)` → `nudge_if_idle(..., pref_key=…)` → `should_nudge` / `record_nudge`, the TUI's `_resolve_row_pref` (via `_cache_repo_name`, **not** the config `name` label), and `cockpit nudge`'s `_resolve_pr` (which resolves the repo from the cwd and exits 2 rather than falling back to a bare number).

Keyed by number alone — the original shape — two repos' PR #10 shared one file, so a mute or snooze on one silenced both, and **each repo's cycle woke the other's snooze every tick**: `_resolve_prefs` compares the stored `wake_on` against the *live* PR, and a signature describing a different PR can essentially never match. **Do not** add a `load_pref(pr_number)`-style call site that invents a key without a repo, and **do not** default `repo_name` to `""` — an empty repo silently re-shares the file.

`load_pref` falls back to reading a legacy bare-`<number>.json` when the per-repo file is absent, so an existing mute survives the re-key; it is deliberately **never unlinked** (several repos may still read the same one) and the next `save_pref` writes the per-repo file. `list_prefs()` is keyed by file **stem**, so `cockpit nudge list` renders `repo#N` (or a bare `#N` for a not-yet-migrated legacy file).

### Backend capability gate — probed once at startup, warns and degrades, never dies

`lib/tool.py::resolve_tool` answers *which* backend is in effect and checks presence only (`shutil.which`), so a cmux too old for a verb cockpit shells out to used to surface as a mid-cycle no-op from a `check=False` call. `lib/capabilities.py` answers whether that cmux is new enough, on **two independent axes**, because cmux exposes them separately: the **CLI verbs** in `REQUIRED_VERBS` (`send`, `send-key`, `list-status`, `list-workspaces`, `new-workspace` — each mapped to the tier it disables, so the warning can say what's lost) and the negotiated **capability ids** in `REQUIRED_CAPABILITIES` (`workspace.read_state.v1`, `terminal.input.ordered.v1`, `events.v1`, `workspace.groups.v1`). There is no machine-readable list of *verbs*, so verbs are parsed out of the `Commands:` section of `cmux --help` (marked `ponytail:`; a parse miss degrades to a warning, never a die) — cmux *does* ship one of RPC **methods** (`cmux capabilities` returns a 303-entry `methods` array that `parse_capabilities` discards), so the swap is available for anything reachable via `cmux rpc`, but not for the CLI surface this gate covers. Six rules:

- **`capabilities`'s own absence from the verb list is the too-old signal**, reported as its own warning and explicitly *not* as "this cmux offers no capabilities" — the verb is never run in that case, so the empty capability set is "couldn't ask", not "answered nothing". An empty *verb* set is likewise "cmux isn't answering" and warns about nothing at all: a version verdict needs a version to have been read.
- **Warn, never die.** `preflight._validate_workspace_backend` follows `_warn_unresolvable_base`'s precedent, not `_validate_sidebar_colors`' — the git+gh half of the dashboard works with no backend at all (`_cache_only`), so a *partial* one must still start. **Do not** promote any of these to `sys.exit(2)`.
- **Cached in `capabilities.probe` (`lru_cache`), never in `resolve_tool`** — that stays uncached per call so tests can vary PATH and config without cache leakage (its docstring says so). Tests clear the probe via an autouse `probe.cache_clear()` fixture.
- **Daemon-only.** Called from `preflight()` under `if not for_setup` — `cockpit setup` may be about to install or upgrade the backend, and the two probe subprocesses shouldn't ride every non-daemon entry point. Skipped outright when the resolved backend isn't cmux (limux/`none` already warn for themselves).
- **`has_capability(id)` is the gate for features built on the baseline** — pair it with the existing `is_cmux()` / `BACKEND_ACTIONS` check, don't replace it.
- **Every entry in either dict must name a tier cockpit actually HAS**, and the two axes are not interchangeable. A required id for an unbuilt feature tells the user to upgrade cmux for nothing: `terminal.replay.v1` ("screen preview") gated the row-terminal peek that was dropped plan-only, and `notification.feed.v1` gated a feed cockpit reads with **no** verb (`notify`, `list-notifications`, `jump-to-unread`, `mark-notification-read`, `dismiss-notification`, `clear-notifications` are all uncalled) — both removed, and `test_required_capabilities_only_name_tiers_cockpit_actually_has` pins them out. Conversely `workspace.groups.v1` is required *because* the verb axis structurally cannot cover `workspace-group`: that verb is **absent from `cmux --help`'s `Commands:` list** (`grep -c` → 0) though fully documented under its own `--help`, so `parse_verbs` can't see it and a `REQUIRED_VERBS` entry would report it permanently missing — while it powers every sidebar fold. **Do not** add `workspace-group` to `REQUIRED_VERBS`, and **do not** narrow its capability to `group_actions`/`group_create` (the umbrella's absence means no folds at all; the narrower pair adds warning noise without a distinct failure mode). `REQUIRED_VERBS` gates 5 of the 15 verbs cockpit invokes — the rest are best-effort `_CMUX_ONLY_VERBS`, capability-gated, or self-gating. The full map is `docs/cmux-surface-audit.md`, and its live half is `tests/e2e/test_cmux_surface.py` (skips without cmux): that module holds the classification of every unused verb as data and fails by name when a cmux upgrade ships one nobody has bucketed. **Do not** write verb counts into prose here or in the doc — they are derived, they move every cmux release, and a stale count in five places is what that test exists to prevent.

### `$COCKPIT_HOME` may be inside a file-sync folder — write pid-scoped, warn on conflicts

`~/.config/cockpit` is commonly a symlink into Dropbox/iCloud/Drive (mine is), which breaks two assumptions:

- **The temp file in `config.py::_atomic_write_text` carries `os.getpid()`** (as `daemon_signal.enqueue` already did). `os.replace` is atomic, so a fixed `<name>.tmp` never yields a *torn* file — it yields a **wrong** one: several cockpit processes write these concurrently (the daemon, a `cockpit close` CLI, a detached `cockpit new`), and two sharing one scratch path each `os.replace` it in turn, so the loser's whole content lands under the winner's name. A synced directory widens the window, because a write can block on the sync client. The temp is unlinked when the write fails — on a synced dir, litter is uploaded and propagated everywhere. **Do not** go back to a fixed suffix, and **do not** re-inline the write (`save_tui_theme` used to carry its own copy).
- **`preflight._warn_sync_conflicts` surfaces a conflicted copy and cannot do more.** Two machines editing one synced file is resolved *outside* the process, after the write returns, by renaming one side to `config (conflicted copy 2026-08-25).json`. Nothing reads that file, so the edit is silently gone and the only symptom is a setting that "didn't take". It matches **only** `conflicted copy` and `.sync-conflict-`: iCloud's `<name> 2.json`, Drive's `<name> (1).json` and OneDrive's `<name>-<machine>.json` are indistinguishable from ordinary filenames, and a false alarm trains the user to ignore a warning that means real data loss. Warn, never die — it records a *past* lost write.

### Config surface has three faces — keep them in sync

`cockpit/lib/config.py` is the authoritative reader (default + resolution per field), but it has two documentation mirrors that drift silently: `cockpit/config.example.json` (the sample schema — documentation only, never installed; a fresh install seeds `{"repos": []}`) and `docs/config.md` (the human field reference). **Any change to a config field — new key, renamed key, changed default, new `tickets`/provider field — MUST update all three in the same PR:** the `config.py` reader, the `config.example.json` sample, and the `docs/config.md` table. Adding a reader without the sample+doc entry is the drift this prevents — a field the code honors but nobody can discover. (Provider ticket fields also flow through the provider's `CONFIG_FIELDS` per the `tickets` note below; that's a fourth touch-point for ticket settings specifically.)

### `tickets` config — the one provider selector (replaced the `use_linear` bool)

`tickets` is an **object** with self-describing fields — `{provider, close_on_merge, dev_done, merge_done}` plus per-provider extras. The bare string `"tickets": "github"` is shorthand for `{provider: github}`. **The field table, defaults, and env-var names live in `docs/config.md`** — per the three-faces rule above, that file is the reference and this section is only the invariants. Nine of them:

- **One field per concept, across every provider.** `dev_done` / `merge_done` each replaced one spelling per provider (`_state` / `_label` / `_status` / `_list`), and `token_env` replaced Linear's `api_key_env`. The former argument — that the suffix told you what kind of value to supply without consulting the provider — lost to the fact that `provider` is declared in the same block, usually the line above, so the suffix only restated a field already set. **Do not** re-split these per provider. (`project` (linear) and `board` (trello) are *not* the same concept and stay distinct: one breaks a tie among repos that already matched, the other is the whole route. Trello keeps `key_env` **and** `token_env` because it authenticates with both.)
- **The superseded spellings are not read — they hard-fail.** `_tickets_field` takes no alias parameter, and `preflight._check_legacy` rejects each old name (`_LEGACY_TICKET_FIELDS`) with its replacement in the message. Accepting both silently would leave the *effective* schema permanently twice the documented one, and would let a typo'd canonical name fall through to a legacy one and read as configured. The check lives in preflight rather than in `tickets_field_errors` because that function only knows a field is unknown *for the active provider* — it can't tell a rename from a typo, so it would report one as the other. It reads the block one level down from the flat-key check, and both run per repo *and* globally; `validate_config` merges `orgs` first, so a superseded spelling on a shared org block is caught on every member repo. **Do not** re-add an alias arg — add a `_LEGACY_TICKET_FIELDS` entry instead.
- **Resolution is per-field**, repo-block → global-block → default (`config.py::_tickets_field`), so a global `tickets.close_on_merge` (or any field) applies to a repo whose own block omits it — a repo block doesn't have to repeat shared settings. Provider selection itself resolves per-repo over global by `config.py::_tickets_block` (the repo entry's whole `tickets` block wins outright); `tickets()` is the global provider, `repo_tickets(cfg, repo_entry)` the per-repo one.
- **The provider selects four things** — the spawn fetch/rename prompt, the `devdone=` pill, the done-on-merge writer, and the TUI ticket columns all gate on `repo_tickets(...)`. **`spawn.py`'s half of that is deferred, and both halves of the deferral are paid-for regressions.** Every ticket source (`trello` / `gh-issue` / `linear`, the last covering Jira too) records a `ticket_source` tuple at classification time and is resolved into a prompt in **one** block after the mode branches, via a `(detect_source mode, resolved provider)` → builder table (`spawn.py::_TICKET_PROMPTS` — add a provider by adding its pair, never by branching on a provider name at the call site; the pair is two-dimensional because `linear` mode can't tell Linear from Jira and a Trello URL is an unambiguous *source* that still only earns its fetch prompt when the target repo tracks work in Trello). (a) It reads `repo_tickets`, **never** the global `tickets()`: a provider declared on the repo entry — or on a shared `orgs` block, the many-repos-one-team shape this feature exists for — is invisible to the global reader, so every ticket spawn into such a repo silently lost its fetch+rename prompt and came up on a bare branch (a codename one like `solar-viper` naming nothing at all). (b) It runs **after** every routing hop, because the repo isn't known before then: a `gh-issue` URL routes via `nwo_hint` *after* its mode branch, and Trello/Linear route via `_route_by_ticket` *inside* theirs, so an earlier read resolves the cwd's repo rather than the target's. `_repo_entry_or_none` is the resolver, so an unroutable repo falls through rather than aborting an otherwise-fine spawn. **The ticket-key routing gate is per-repo for the same reason** — `any(provider_for(cfg, r) ...)` over the *candidates* (`find_repos_by_ticket_key`'s matches), not `provider_for(cfg)` over the global block, which switched routing off for exactly the org-level configs that need it; Trello's sibling gate (`trello_board`) was already per-repo, and this is the same question. **When no pair matches** (provider mismatch, or `tickets: none`) the spawn falls through to `_plan_only_prompt(..., source=<ticket ref>)`, which seeds the bare Trello/Slack URL, `PE-1234` identifier, or `owner/repo#N` issue ref. That is not decoration: the fallback fires precisely because cockpit *can't* fetch the ticket for you, so handing over the link is the only thing left it can do — **do not** drop the `source` slot.
- **Credentials are env-only** — config carries the env var's *name*, never its value.
- **`start_label` is the one *spawn-time* tracker write** (GitHub, opt-in): when `spawn.py` creates a worktree on a `gh-issue` source it marks the issue "work started" via `gh issue edit --add-label` (`github_issues.add_label`, `config.github_start_label`), best-effort — a failed label never blocks the spawn. Distinct from the slow-tick `close_on_merge` write.
- **`use_linear` is gone, and so are the flat `linear_*` keys** the block replaced — `linear_keys` / `linear_dev_done_state` / `linear_done_on_merge` / `linear_merge_done_state` (now `tickets.keys` / `dev_done` / `close_on_merge` / `merge_done`). All five **hard-fail** in preflight (`_validate_tickets` → `_check_legacy`, `_LEGACY_TICKET_KEYS`, the same shape as `_LEGACY_SKILL_KEYS`) naming the field to move to, rather than being silently ignored — every one of them *disables* something the moment it stops being read (`linear_keys` stops routing a `PE-1234` spawn and stops the devdone pill; `linear_done_on_merge` quietly stops writing to the tracker), and a config error read once beats a feature that goes quiet forever. There is consequently **no** fallback path left in any reader: `repo_tickets` is `tickets.provider` or `"none"`, full stop — **do not** re-add a "guess the provider from a sibling field" rule, since `keys` is Jira's field too and the guess would be wrong half the time.
- **`linear_team_keys` is Linear-*named* but provider-neutral in substance**, since Jira declares `keys` too (`tickets.keys`). A reader that means "this repo is Linear" must therefore pair it with the resolved provider — `preflight._validate_linear_dev_done` does, else every Jira repo gets warned about an unset `LINEAR_API_KEY`.
- **`tickets::provider_for(cfg, repo_entry)` → a `TicketProvider` (or None) is the single source of truth** mapping the provider onto its strategy (`dev_done_value`, `parse_footers`, `fetch_states`, `fetch_titles`, `narrow_repos`); `cycle.py` calls the strategy instead of sprinkling `provider == "github" ? … : …` ternaries. **Do not** re-introduce those ternaries — add a `TicketProvider` field.

**Extending the schema.** The accepted-field *schema* is owned by each provider — `linear.py` / `github_issues.py` / `jira.py` / `trello.py` export `CONFIG_FIELDS` (`(name, kind)` pairs), `tickets.py` composes them with the common fields and validates via `tickets_field_errors` (which also rejects a field belonging to *another* provider), and `preflight._validate_tickets` just delegates. **Add a new ticket setting** by adding it to the provider's `CONFIG_FIELDS` + a reader in `config.py` — not by editing a hardcoded list in preflight, and **not** as a new top-level `github_*` flat key. Settings readers (`ticket_close_on_merge`, `github_dev_done`, `linear_dev_done` / `linear_merge_done`, `linear_team_keys`) all source via `_tickets_field`. Several field names are declared by more than one provider — `dev_done` (all four), `merge_done` and `token_env` (linear, jira, trello), `keys` (linear, jira): `tickets_field_errors` composes the allowed set from the *active* provider only, so a shared name validates under each of its owners and still fails under the others — **do not** flatten the per-provider schemas into one merged dict.

**Ticket→repo routing is two-stage: a free match, then a paid tiebreak.** `cockpit new PE-1234` picks its repo from the identifier alone — `config.find_repos_by_ticket_key` over `tickets.keys` — which is pure, offline, and enough whenever one repo owns the team. It isn't enough in the many-repos-one-team shape: every member declares the same `keys`, so the id matches them all, and the old behaviour (warn, fall back to cwd discovery) silently lands the worktree in whichever repo you happened to be standing in — a *wrong* answer, not a missing one. The discriminator is `tickets.project`, and a Linear identifier names its **team, never its project**, so resolving it costs a GraphQL fetch. Hence the seam: `TicketProvider.narrow_repos(ref, candidates, cfg)`, called by `spawn.py` **only when the free match already returned >1** — the single-match route stays network-free and a config without `project` is byte-identical to before. Three rules: it **never narrows to zero** (no candidate configures a project, the fetch fails, or the resolved project matches nobody → return `candidates` unchanged, so the caller's existing ambiguity path still runs); it groups candidates by **resolved credential** (`linear_api_key_env`, which already walks repo → org → global → default, since `apply_org_defaults` merged the org rung in at `load_config` time) and asks each group with its own key — a team key is *workspace*-scoped, so two orgs can each own an `ENG` team and both match `ENG-1234`, and asking one org's workspace about the other's ticket answers about a **different issue that merely shares an identifier**, which mis-routes the spawn; a project name is therefore only ever matched against repos in the group whose key returned it, groups are tried in config order, first confident hit wins, and a group whose credential is unset is skipped (it can't be asked). That keeps the ordinary single-workspace case at exactly one fetch — extra round-trips appear only when the candidates genuinely span workspaces, which is the only way to answer correctly. **Do not** collapse this back to one key read off `candidates[0]`. Finally it is **routing-only** — no cell, no pill, no decision downstream reads `project` (or Trello's `board`).

**Both stages are provider-shaped, and `spawn.py` must not branch on a provider name to pick them.** Stage two is `narrow_repos`; stage one is whatever the caller can match for free, and `spawn._route_by_ticket(ref, candidates, cfg)` is the one shared tail (narrow only when >1, single survivor wins, >1 prints the ambiguity note and falls back to cwd discovery) both call sites hand their candidates to. Per provider:

- **Linear** — free match `tickets.keys`; tiebreak `tickets.project` (`_linear_narrow_repos`), as above.
- **Jira** — free match `tickets.keys`, the **same field and the same reader** (`linear_team_keys`, Linear-named but provider-neutral in substance): a Jira *project key* IS the identifier prefix, i.e. the analogue of a Linear **team**, not of a Linear project. So Jira declares `keys` in its `CONFIG_FIELDS` and stays `_no_narrow` — **do not** give it a `project` field, and **do not** duplicate `find_repos_by_ticket_key`. The `mode == "linear"` spawn branch runs the lookup for both (Jira keys share Linear's `[A-Z]{2,6}-\d+` shape, so `detect_source` classifies them alike), gated on `provider_for(cfg) is not None` rather than a provider-name test, so `tickets: none` still routes nothing. **The shape gate stays `LINEAR_RE_CI`** — it is `detect_source`'s classifier, so widening it only in `find_repos_by_ticket_key` would be a no-op, and widening it for real reclassifies plain branch names like `feature2-1` as tickets; a Jira key with digits or >6 letters therefore doesn't route *from its bare form* (documented `ponytail:` in both places), which is the accepted ceiling until someone hits it — it does classify and seed a prompt from an issue **URL**, where the key is positional (see below).
- **Trello** — **no free match at all**: a card short link (`trello.com/c/aB3xY`) carries no board, no project, no prefix. So the opt-in *is* the discriminator — stage one is "the configured repos that declare a `tickets.board`", and `_trello_narrow_repos` resolves the card's board with one `fetch_card_board`. With no repo declaring a board the candidate set is empty and `cockpit new <card-url>` makes **zero** network calls and routes exactly as before; with one, it routes free (same as a single `keys` match); only ≥2 pays. It mirrors `_linear_narrow_repos`'s three properties exactly, including grouping by **resolved credential** — Trello's is a key+token *pair* (`trello_key_env` + `trello_token_env`), and a board name is *account*-scoped just as a team key is workspace-scoped, so asking one org's account about another's card answers about a different card or 404s.
- **GitHub** — needs neither stage (a `owner/repo#N` ref carries its repo, so `find_repo_by_nwo` never reaches an ambiguous set). `_no_narrow`.

**A ticket URL is a first-class source, for every provider.** Pasting the link is the actual gesture — you copy it out of the tracker, you don't retype the id — and every provider but Linear and Jira already classified one, so those two fell through to `branch` mode and `git worktree add -b <the whole URL>` died on `not a valid branch name`. `detect_source` now matches `linear.LINEAR_ISSUE_URL_RE` (`linear.app/<workspace>/issue/<ID>/…`) and `jira.JIRA_ISSUE_URL_RE` (the `/browse/<KEY>` permalink and the `/jira/…/issues/<KEY>` board deep link, host-agnostic for Server/Data Center) into the **same `linear` mode as the bare id**, extracting the identifier so everything downstream — branch name, repo routing, seeded prompt — is byte-identical to typing it by hand. **Do not** pass a Linear/Jira URL through verbatim the way `slack`/`trello` mode does: those two are codename-branch sources whose *content* the spawned Claude reads via MCP, whereas a Linear/Jira branch is derived from the identifier, so the URL must be reduced at classification time. In the URL the key is **positional**, so unlike the bare form it needs no `[A-Za-z]{2,6}` shape guard against colliding with a branch name — which is why a `R2D2-7`-shaped Jira key classifies from a URL and not from a bare token.

**Per-org credentials come free from the env-*name* indirection.** `config.py` has a name reader + a value resolver per credential (`linear_api_key_env`/`linear_api_key`, `jira_token_env`/`jira_api_token`, `trello_key_env`+`trello_token_env`/`trello_api_key`+`trello_api_token`); the name reader is just another `_tickets_field` call, so it resolves repo → org → global → default and an `orgs: {acme: {tickets: {token_env: "LINEAR_API_KEY_ACME"}}}` block covers every member repo with **no** org-aware machinery (see the `orgs` invariant — nothing below `load_config` knows orgs exist). Every call site resolves the *value* per repo and threads it into the leaf (`fetch_ticket_states(…, api_key=…)`, `jira.*(token=…)`, `trello.*(key=…, token=…)`) instead of relying on the leaf's env fallback, which stays only for back-compat. Two rules:

- **The identity caches key on the resolved secret, not the env var name** (`cycle.py::_secret_fingerprint` — sha256[:12] of the value, plus the site/email for Jira). They used to be single-slot on a fingerprint of the one global env var, so with per-org keys org B would read org A's cached viewer id and then silently skip *every* ticket (the viewer gate can never match a foreign id). Same for the Trello key+token pair. `_cached_team_states` still keys on the team UUID alone (globally unique), but takes the api_key for its fetch. The TTL and the never-cache-a-falsy-identity rule are unchanged.
- **Spawned sessions never receive ticket credentials.** `_bg_spawn_pr` passes `env=` os.environ minus `config.credential_env_names(cfg)` — the union of every resolved name across the global block, all repos and all orgs, plus the four defaults. Spawn-time ticket fetch is MCP-delegated (the Linear/Jira/Trello connectors), so an agent has no use for the REST keys, and a `review_prs` session runs over a coworker's untrusted PR body/diff. Strip by *resolved name*, never a `LINEAR_*` prefix guess, and touch nothing else in the env (`PATH`, `COCKPIT_HOME`, `CMUX_*` must pass through or spawning breaks). Preflight's soft warnings name each repo's resolved variable (`_unset_linear_key_envs`) — a warning, log line, or error message carries an env var **name**, never a value.

### `devdone=` pill — the ticket provider is the one auxiliary (read-only) state source

Gated on `repo_tickets(...) != "none"` + a PR-body delivery footer. Delivery is **footer-only** (`provider.parse_footers`): Linear → `Linear: [PE-1234](url)` (`lib.linear.parse_linear_footers`); GitHub → a closing keyword `Closes #123` / `Fixes owner/repo#45` (`lib.github_issues.parse_github_issue_refs`); Jira → `Jira: [PROJ-123](url)` (`lib.jira.parse_jira_footers`, the same strict line-anchored footer as Linear); Trello → `Trello: [title](https://trello.com/c/<shortLink>)` (`lib.trello.parse_trello_footers`, the delivered card's short link) — never a branch-slug or a bare mention, which catch non-delivered tickets (same strict signal as `morning-align`'s `linear_delivery.py`). The `{provider, tickets, fetched_at}` block — each ticket `{id, state, title}`, plus the resolving `provider` name so the block is self-describing (a downstream reader picks Trello's title-over-short-link handle via `cache.ticket_display` without re-reading config; the statusline `pr-ticket` pill and TUI Ticket cell both route through it) — is cached in the PR JSON under the `ticket` key (renamed from the legacy `linear` key, no back-compat: an old on-disk cache blips its `devdone=` pill off for one slow cycle until rewritten, and a provider-less block falls back to the raw id for that cycle); `cycle.py::_prefetch_linear_blocks` decides refetch-vs-carry-forward per PR (`_decide_linear_refetch`: footer-id change or past `linear_state_ttl_seconds`) reading the *prior* snapshot via `ctx.pr_payloads`, then resolves the union of due ids across *all* a repo's PRs via `provider.fetch_states` (Linear: one **batched** GraphQL query per team; GitHub: one `gh issue view` per issue — an issue carrying the dev-done label `github_dev_done_label` (default `"ready for review"`, via `tickets.dev_done`) maps to that label so the comparison stays provider-neutral; Trello: one `GET /cards/{id}?list=true` per card resolving its current list name — `lib.trello.fetch_card_lists`). The `title` is a parallel provider-neutral enrichment (`provider.fetch_titles` → `_fetch_ticket_titles`, one fetch per provider on build, carried forward on carry) — the human ticket name a statusline consumer like cship reads from the cache without its own API round-trip; it never feeds a cockpit decision (dev-done keys off `state` only). It runs once before the write loop so each `write_pr_cache` still overwrites against the old file. `_track_dev_done` raises the pill (`apply_devdone_pill`) only when *every* delivered ticket equals `provider.dev_done_value(cfg, repo_entry)` (Linear's `dev_done`/"Dev Done" state / GitHub's primary accepted label / Trello's `dev_done` list name, casefolded). Passive, never a `send`, absent from `ACTIONABLE_KEYS`. **Do not** drop back to a per-PR fetch fan-out; keep the Linear union batched. A per-source query failure isolates to its own ids (they stay None) — never blanks unrelated tickets.

### done-on-merge — the daemon's only sanctioned tracker *writes*, dispatched per provider

Opt-in (default false, per-repo) via the shared `tickets.close_on_merge` (`config.py::ticket_close_on_merge`). Slow-tick `cycle.py::_transition_merged_tickets` dispatches on `provider.name` to one writer, each fired on `_is_post_merge_stale` independently of teardown (ship even when the worktree is held back), each guarded by a per-run `merged-done:…` marker in `pill_state`, each viewer-gated (never touch a teammate's ticket), each idempotent + logged:

- **Linear** (`_transition_merged_linear`, gated `ticket_close_on_merge` + `linear_team_keys` + a resolved `linear_api_key` (the env var named by `tickets.token_env`)): moves the ticket to `linear_merge_done_state` (`tickets.merge_done`, default "Done", distinct from `dev_done`) via `update_ticket_state` → `issueUpdate`. Per ticket: skip unless assigned to the API-key `viewer`; skip if already at target or `type: canceled` (note "Dev Done"/"Done" are both `completed`, so name-equality decides); else resolve the target UUID (`fetch_team_states`) and mutate. The `viewer` id + per-team state maps are cached across ticks (`_cached_viewer_id`/`_cached_team_states`, TTL `linear_identity_ttl_seconds`; viewer key is a non-secret fingerprint of the *resolved* key, so per-org credentials keep separate slots); the `viewer` fetch is **lazy** (first eligible ticket only).
- **GitHub** (`_transition_merged_github`, gated `ticket_close_on_merge`): runs `gh issue close` on each delivered issue still open and assigned to the `gh` auth login (`github_viewer_login`, cached via `_cached_github_viewer`). GitHub auto-closes same-repo closing-keyword refs on merge, so this mainly catches cross-repo refs and label-only links.
- **Jira** (`_transition_merged_jira`, gated `ticket_close_on_merge` + `tickets.site_url`/`email` + a resolved `jira_api_token` (`tickets.token_env`)): transitions each delivered issue to `jira_merge_done_status` (`tickets.merge_done`, default "Done") via the REST transitions API (Jira moves issues by *transition*, not a direct status set — GET available transitions, match the target status name, POST). Per issue: skip unless assigned to the auth user (`fetch_myself` accountId, cached via `_cached_jira_viewer` keyed on a fingerprint of the resolved token + site + email); skip if already at target. Spawn fetch is MCP-delegated (Atlassian connector); the daemon's REST is Basic-auth `base64(email:token)`.
- **Trello** (`_transition_merged_trello`, gated `ticket_close_on_merge` + `tickets.merge_done` set + a resolved `trello_api_key`/`trello_api_token` (`tickets.key_env`/`token_env`)): moves each delivered card to the list named `merge_done` (no default — an unset list leaves the move off) via `lib.trello.move_card` (resolve the card's board, match the target list name on it, PUT the new `idList`). Per card: skip unless I'm a member (`fetch_myself` member id, cached via `_cached_trello_viewer` keyed on a fingerprint of the resolved key+token); skip if already on the target list. Spawn fetch is MCP-delegated (Trello connector); the daemon's REST is key+token query-auth.

A falsy/failed identity fetch is never cached (retries next tick); a failed write clears the marker to retry. **Precedent for any future daemon tracker write:** opt-in, viewer-gated, idempotent, logged.

## Dev setup and common commands

```bash
# One-time after cloning — wires pre-commit hooks for commit + push stages:
./setup.sh

# Run the test suite serially — right for a single test or a small selection:
pytest tests/test_spawn.py::test_linear_key_routes_to_matching_repo_without_repo_flag

# Run the WHOLE suite — always pass -n auto. Half the wall clock is idle time
# waiting on the real git/gh/cmux subprocesses, so it parallelises near-linearly
# (115s -> 16s on an 18-core laptop, -> ~32s on a 4-core CI runner). The
# pre-push hook and CI already pass it; `addopts` deliberately does not, since
# worker boot costs ~2s and that is pure tax on the single-test line above:
pytest -n auto

# Type-check:
mypy cockpit/

# Lint + format — ALWAYS via the pinned pre-commit hook, scoped to your files:
pre-commit run ruff ruff-format --files <changed paths>
```

**Never lint/format with `uvx ruff` (or a globally-installed `ruff`).** `uvx`
pulls the **latest** ruff, whose rules drift from the version pinned in
`.pre-commit-config.yaml` — running it (especially tree-wide, `ruff format
cockpit/ tests/`) rewrites pre-existing lines in files you never touched to the
newer style, producing unrelated churn that the pinned pre-commit hook then
fights on commit. Bare `ruff` isn't installed here on purpose; the pinned hook
*is* the formatter, and it's what CI enforces. Format only your changed paths
with `pre-commit run ... --files`, not the whole tree.

## Release versioning

The version is **static** in `pyproject.toml` (`[project] version = "..."`), read at runtime via `importlib.metadata` (`version.running_version`, surfaced by `cockpit --version`). There is no self-update path. `ci.yml` skips only `no-commit-to-branch` (local-dev-only).

**Every merge to `main` that ships user-visible behaviour gets a release** — brew is the only delivery path, so an unreleased merge reaches nobody. The semver bump is derived from the conventional-commit types on `main` (`feat` → minor, `fix` → patch), which `pr-title.yml` already enforces on every squash subject.

**The release PR writes itself.** `.github/workflows/release-please.yml` (`googleapis/release-please-action@v4`) keeps one rolling `chore(main): release <version>` PR open, accumulating every conventional commit merged since the last release and maintaining `CHANGELOG.md`. **Merging that PR is the only human step in a release** — it bumps `[project] version`, which is the trigger `tag.yml` watches, so tag → tap → PyPI all follow on their own. Several merges therefore batch into one release rather than cutting a version each, which matters because PyPI refuses a re-upload of a version.

Five settings in that workflow are load-bearing — the first four for the same GitHub recursion rule that shaped `tag.yml`, the last because two runs can't share one release branch:

- **`skip-github-release: true`** — left to default, release-please pushes the tag and cuts the GitHub release itself, duplicating `tag.yml` *and* doing it under a token whose pushes don't trigger workflows, so `release.yml`/`publish.yml` would silently never run. `tag.yml` stays the only tagger; release-please only ever writes the PR.
- **`skip-labeling: true`** — the **required** companion to the above, and the subtlest thing in the release path. release-please keeps release state in a **label on the merged release PR**: it opens the PR as `autorelease: pending` and flips it to `autorelease: tagged` in the release step — precisely the step `skip-github-release` turns off. So the label never flips, and every later run finds a still-`pending` merged PR and aborts at `There are untagged, merged release PRs outstanding` *before* proposing the next version. This wedged the pipeline after v1.8.0: 1.9.0's PR was never opened and a merged feature sat unshipped, and it cannot self-heal — the abort repeats on every push forever. **The state is the label, not a GitHub Release**: cutting the missing Release for the tag looks like the fix and does nothing (we tried it). Turning labeling off leaves no pending PR to find; the version baseline still comes from `.release-please-manifest.json` + the git tags, which is all this workflow reads. If it ever wedges again, look at `gh pr view <release-pr> --json labels` first — and clear a stale `autorelease: pending` by hand, since `skip-labeling` only stops *new* ones.
- **`if: "!startsWith(github.event.head_commit.message, 'chore(main): release')"`** — the job skips the push that *merged* the release PR, because this workflow re-runs on the very commit it causes and races `tag.yml` there. Both fire on that sha; `tag.yml` pushes `v<version>` roughly a minute later, so when release-please starts, **the tag for the release just merged does not exist yet**. With no baseline tag it treats the repo as never released and regenerates `CHANGELOG.md` from the entire history — the same failure `include-component-in-tag: false` prevents, arrived at from the other direction. That produced PR #309: `chore(main): release 1.10.0` with a 225-line changelog replaying long-shipped PRs, on a `main` with **zero** commits since v1.9.0. It looks plausible because the version comes from `.release-please-manifest.json`, not from a tag — right only by accident. This is structural, not a one-off: every release ends in exactly this push. Nothing is ever releasable on it (the release PR just consumed every pending commit), so the guard loses no coverage and the next real feature merge opens a correct, tag-bounded PR. It keys off the **commit subject**, which is reliable here — we squash-merge, `pr-title.yml` enforces the title, and release-please always names its PR `chore(main): release <version>` — so **do not** set `pull-request-title-pattern` in `release-please-config.json` without updating the guard to match. `cut-release.sh` commits `chore(release): <version>` (different prefix) and still triggers a run, which is correct: it tags out of band. If a bogus whole-history release PR ever appears again, check whether the guard still matches the subject on `main` before touching anything else.
- **`token: COCKPIT_GITHUB_API_TOKEN`** — a PR opened by the default `GITHUB_TOKEN` doesn't trigger workflows, so the release PR would sit forever with none of `main`'s required checks reporting and could never be merged.
- **`concurrency: {group: release-please, cancel-in-progress: false}`** — two runs can't share the release branch. Every run force-updates `release-please--branches--main--components--cockpit` to a freshly built commit, so two merges landing seconds apart start two runs racing that one ref; the loser dies on `Error updating ref` **after** writing its commit but **before** updating the PR's title and body. Merging #337 and #336 back-to-back did exactly that: the branch carried a correct 1.17.0 `pyproject` + manifest + `CHANGELOG.md` while the PR still advertised `chore(main): release 1.16.1` listing only #334. **That is the dangerous shape, because we squash-merge** — the PR title becomes the subject on `main`, so an unnoticed merge would have committed "release 1.16.1" over a tree containing 1.17.0. (`tag.yml` reads `pyproject.toml`, so the *tag* would still have been right; only the log would lie — but a release log that lies is exactly what nobody re-derives later.) Serializing costs a minute of queueing and makes the last run to finish the one that writes the PR. **`cancel-in-progress` stays `false`** — cancelling would kill a run mid-ref-update, which is the failure this exists to prevent. If a release PR's title ever disagrees with its own `CHANGELOG.md` again, **fix the title before merging** and check for a failed run on the same sha.

State lives in `release-please-config.json` (release type `python`, which updates PEP 621 `[project] version`) and `.release-please-manifest.json` (the last released version — the one file to correct by hand if a release is ever cut out of band).

`CHANGELOG.md` is **release-please's file** from 1.8.0 on — don't hand-edit it. It's excluded from `markdownlint` in `.pre-commit-config.yaml` because release-please writes `*` bullets into a file that was hand-written with `-` ones, and MD004 would fail every release PR.

**`include-component-in-tag: false` is required, not cosmetic.** Left at its default (`true`), release-please names tags `cockpit-v<version>` while `tag.yml` pushes `v<version>` — so it can't find the previous release, treats the repo as never released, and regenerates `CHANGELOG.md` from the entire history (203 entries on the first run, with compare links to tags that don't exist). The tag format has to match `tag.yml`'s even though `skip-github-release` means release-please never pushes one.

`./cut-release.sh <version>` is the **manual fallback**, for when the action is broken or a version has to be forced: it bumps `[project] version`, commits `chore(release): <version>`, opens the PR, and merges it `--squash --admin` (confirming first unless passed `-y`). It refuses a dirty tree, a non-semver argument, `main`/`master`, and a bump to the version already in `pyproject.toml`. Its guard paths are covered by `tests/test_cut_release.py`; the happy path ends in a real merge and is deliberately untested. Using it means `.release-please-manifest.json` must be updated to match, or release-please will propose a bump from the stale baseline.

`.github/workflows/tag.yml` watches `pyproject.toml` on `main`: when the bump lands it reads the new version, pushes `v<version>` at that merge commit, then cuts the GitHub Release for it (both halves independently idempotent, so an unrelated `pyproject.toml` edit does nothing). That tag then fires `release.yml` + `publish.yml`. The Release is **presentation only** — a notes page, read by nothing in the pipeline; it is *not* what keeps release-please unwedged (`skip-labeling` is). It pushes with **`COCKPIT_GITHUB_API_TOKEN`, not the default `GITHUB_TOKEN`** — a ref pushed by `GITHUB_TOKEN` doesn't trigger other workflows, so the two downstream jobs would silently never run; the PAT consequently needs `Contents: write` on **this** repo as well as on the tap. Hand-tagging (`git tag v<version> origin/main && git push origin v<version>` on a fetched `origin/main`, never the pre-merge branch tip) still works and is the fallback if the PAT lapses.

The tag must point at a tree whose `pyproject.toml` version equals the tag (minus the `v`) — **both** `release.yml` and `publish.yml` re-read `pyproject.toml` at the tag as their first step and hard-fail on a mismatch, which is what hand-tagging the un-merged branch tip or forgetting the bump trips. The `publish.yml` guard matters most: PyPI refuses a re-upload of a version, so a wrong-versioned wheel there is unrecoverable. On success it hands `mislav/bump-homebrew-formula-action` the tag tarball URL; the action computes the sha256 and **commits the new `url`+`sha256` straight onto `khivi/homebrew-cockpit`'s `main`**, so `brew upgrade cockpit` picks it up with no PR to merge. It authenticates with `COCKPIT_GITHUB_API_TOKEN` (the default `GITHUB_TOKEN` can't reach another repo); `Contents: write` on the tap is all it needs. **`create-branch: false` in `release.yml` is what makes that direct commit happen, and removing it re-breaks releases silently** — the action's `needsBranch` is `inFork || <base branch>.protected || makePR`, and the tap's `main` carries a ruleset so GitHub always reports it `protected: true`. Left to default it therefore branches, then `POST /pulls` 403s (`Resource not accessible by personal access token`) *after* pushing a correct-looking `update-cockpit.rb-<n>` branch — the v1.5.1 and v1.6.0 failure mode, where both tags and both formulas were right and neither reached the tap until a human opened the PR. The tap ruleset only forbids `deletion` + `non_fast_forward`, so the direct commit is permitted. When a release job fails, **check the tap for an orphaned `update-cockpit.rb-*` branch before re-cutting anything** — a leftover branch means the PR fallback ran, i.e. `create-branch: false` went missing. The formula's `resource` blocks are **not** touched — regenerate them by hand on a dependency bump (`brew update-python-resources Formula/cockpit.rb`).

### PyPI is the second tag consumer — trusted publishing

The same `v*` tag also fires `.github/workflows/publish.yml`, which builds an sdist + wheel and uploads them to PyPI as the **`cmux-cockpit`** distribution (bare `cockpit` collides with Red Hat's Cockpit web console; the import package and the `cockpit` console script are unchanged). It runs *independently* of `release.yml` — a failed publish does not hold back the brew release, and vice versa, so a green tap PR is not evidence PyPI succeeded. Check both.

Auth is [PyPI Trusted Publishing](https://docs.pypi.org/trusted-publishers/) (OIDC): there is **no** PyPI token in this repo, in GitHub secrets, or in fnox. GitHub mints a short-lived token at publish time (`id-token: write`) and `pypa/gh-action-pypi-publish` exchanges it. PyPI matches four claims exactly — Owner `khivi`, Repository `cockpit`, Workflow `publish.yml`, Environment `pypi`.

The publisher is now registered and `cmux-cockpit 1.8.0` is live. Earlier `publish.yml` runs failed with `invalid-publisher` — the OIDC token was valid but no pending publisher existed on PyPI to match it; this was fixed browser-side (one-time) at <https://pypi.org/manage/account/publishing/>, not by editing `publish.yml` (which was always correct). Because `invalid-publisher` fails *before* upload, no version was consumed, so the blocked v1.8.0 run was recovered with a plain `gh run rerun <run-id>` — no re-tag, no bump. Future tags publish automatically. If a publish ever fails again, **do not** touch `publish.yml`; check the pending-publisher claims first. See `docs/pypi-publishing.md` for the full setup walkthrough.

## Commit / PR-title convention

We squash-merge, so the **PR title** becomes the squash commit subject on `main` (the `type(scope): summary (#N)` lines in `git log`). Use [Conventional Commits](https://www.conventionalcommits.org/) for the PR title: `feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert`, optional scope. Local WIP commit messages are unconstrained — they get squashed away.

Enforced by `.github/workflows/pr-title.yml` (`amannn/action-semantic-pull-request`, commitlint's `config-conventional` ruleset) as the required `lint-pr-title` status check on `main`. It runs alone (not in `ci.yml`) so a title edit re-checks the title without re-triggering pytest/mypy.

`main` is guarded by **two** stacked mechanisms, and the second is why a plain `gh pr merge` reports "the base branch policy prohibits the merge" even with everything green: classic **branch protection** requires the `lint-pr-title` + `pre-commit` + `ci` checks, and a **repository ruleset** (`main`, active) additionally requires 1 approving review, code-owner review, resolved threads, and squash-only merges. A solo author can't approve their own PR, so every merge here is `gh pr merge <N> --squash --admin` — admins are exempt from both (`enforce_admins: false`). Check the ruleset with `gh api repos/khivi/cockpit/rulesets`, not just `.../branches/main/protection` — the latter shows the checks but none of the review requirements.

## Test layout

New modules get their own `test_<name>.py` — don't append tests for a new source file to an unrelated test module. Shell hooks under `cockpit/hooks/` are the exception: they live as `tests/test_<hook>.py` with no Python source mirror.

## Test style by layer

- **Leaf modules** (`cockpit/lib/*` wrapping `git`, `gh`, `cmux`, `shutil.which`, `subprocess.run`, etc.) test against the real tool on `tmp_path`. Stubbing the underlying command tests the stub, not the integration.
- **Orchestrators** (`cockpit/orchestrators/*`) compose those leaves. Tests mock collaborator calls (`patch.object(teardown_mod, "remove_worktree", …)`) to assert ordering, guards, and gating without re-validating the leaves underneath.
- **CLI entry-points** (`tests/test_<script>.py` for `cockpit/{cockpit,spawn}.py`, plus `tests/test_cli.py` for the dispatcher) test the argparse / routing layer. Mock at the orchestrator boundary (`patch("cockpit.cockpit.teardown", …)`) or, for the dispatcher, at each module's `main` — the layer below is covered by its own tests, so re-exercising it here adds noise.
- **TUI** (`tests/tui/*`) drive the Textual app headlessly via `App.run_test()`/Pilot (no TTY) with the tick functions and `load_config` injected; card markup is a pure function tested off seeded cache cells. Test the TUI's own scheduling / in-flight gating / log capture, not the reconcile cycle underneath.
- **End-to-end** (`tests/e2e/*`) run the full pipeline against real binaries. No mocking. These are the slowest and most fragile — reserve for genuinely cross-layer behavior (e.g. `cship` + `starship` integration).
